Key points

What matters most, in order.

1

DWG is an explicit dependency choice

The viewer core does not register LibreDWG. The demo does, with GPL obligations and acknowledged compatibility/memory limits; the proprietary replacement has separate terms.

2

Local parsing does not mean zero network

Local input stays in the inspected browser parsing path, but default fonts/templates use a mutable CDN source. Cloud-drive and AI plugins change the privacy boundary; origin-derived API-key encryption is not a secret-backed vault.

3

Snapshots and partial opens are not CAD fidelity

HTML exports are display artifacts; DXF serialization is not proof of lossless DWG round-trip. Whole-file allocation, partial-open recovery and missing durable persistence require explicit acceptance tests.

Useful browser-first workflow

Layers, measurement, editing commands, diff viewing and HTML/PDF/SVG output sit around a reusable CAD database/viewer abstraction. SVG import is explicitly lossy; format acceptance is not universal compatibility.

Sharing boundary

Single-file HTML embeds a compressed display snapshot and runtime. Separate package mode loads manifests/chunks. Preserve originals and validate exported DXF in an independent reader.

File → whole ArrayBuffer → external database/converter → entities → shared Three.js geometry/material batches. Progressive rendering and cooperative yields improve responsiveness but do not impose a global memory budget.

Security and recovery

No pre-read size rejection was found in the inspected local paths. SVG reference cycles are guarded, and failure handling exists, but partial geometry is not proof of complete parsing. Optional AI key encryption derives its key from public origin data.

Verdict

The call, and why.

⚠️ Interesting
