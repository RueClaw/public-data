What It Is

SlowBooks targets owners who want locally controlled records and familiar QuickBooks-style workflows without an application subscription. The desktop launcher wraps a local web application; native company files use SQLite, while the optional Docker setup uses PostgreSQL. The same application includes a multi-user server mode and scoped API tokens.

The breadth is unusual: invoices and payments, bills, bank statement imports, inventory, class/job reporting, nonprofit terminology, tax forms and optional external integrations. For a solo service business, invoicing, expenses, bank reconciliation and standard reports are the relevant core. Payroll, merchant integrations and AI increase both the sensitive-data footprint and validation burden; they are not prerequisites for bookkeeping.

Key Features and Financial Correctness

### Real double-entry controls

app/services/accounting.py centralizes Decimal half-up cent rounding, rounds invoice lines before summing, rejects negative or dual-sided journal lines, checks debit/credit equality, and enforces closing dates at journal creation. app/models/transactions.py adds a database CHECK requiring each stored split to be strictly debit-only or credit-only. Reversals preserve class/job/cost dimensions. Those are substantive safeguards.

Limits matter: balance equality is an application-level cross-row invariant, not a shown database-wide constraint. Journal insertion also updates cached account balances through read-modify-write without an account row lock in that helper; simultaneous PostgreSQL postings deserve a targeted concurrency test before multi-user reliance. Payment paths do take document row locks (app/routes/payments.py), but that is not evidence all concurrency cases are safe. This is a static risk observation, not a reproduced lost-update incident. A balanced ledger also cannot establish correct account classification or tax treatment.

### Reconciliation is tied to the ledger

app/services/reconciliation.py reconciles journal lines for a chosen bank account, carries the prior completed statement balance, rejects backward statement dates and stamps completed lines. Completion rejects differences above half a cent. This is considerably stronger than marking imported CSV rows reconciled independently of the ledger. Statement-import deduplication and matching still require real bank-specific trials; no connection or bank statement was tested here.

### Invoicing, exports and migration

Invoice/payment posting and reversal tests exercise the document-to-ledger relationship. IIF export sanitizes tabs/newlines, neutralizes spreadsheet formula-like text, and includes invoices, payments, bills and other selected records. CSV/PDF reports are useful for accountant handoff. A successful import or balanced trial balance does not prove all historical documents, tax flags, foreign currency and outstanding allocations migrated correctly. Compare opening balances, A/R and A/P aging, taxes and a bank statement independently.

### Audit trail is useful, not immutable

app/services/audit.py uses ORM flush hooks to retain old/new values with the acting user, preserves Decimal amounts as strings, redacts password hashes and avoids copying binary document contents. This provides operational traceability but is not a separately protected evidence store: direct database edits can bypass ORM hooks and a database administrator can modify local history.

Document hashing covers canonical company/form inputs. The inspected document-audit model has a content hash and actor/time metadata but no previous-hash link or external signature. Keep trusted copies of issued forms and backups; a printed hash alone cannot prove that a PDF was never edited or that its tax figures were lawful.

Architecture and Security

A large modular monolith organizes routes, services, schemas, models and templates around one FastAPI application. Core journal logic is shared, while many orchestration decisions remain in route handlers. Request-scoped database sessions roll back on errors; caller-owned commits let related financial writes share a transaction. Desktop packaging and server mode introduce distinct storage and lifecycle paths that must be tested separately.

app/main.py implements central session/token authentication, coarse admin/bookkeeper/read-only policies, restricted HR routes, explicit CORS origins, HTTPS options and startup checks against the public development encryption key. app/services/settings_service.py encrypts designated integration credentials with Fernet and provides redaction helpers. This is more nuanced than the stale SECURITY.md note suggesting SMTP passwords simply remain in settings: current code encrypts them. Field encryption is not full-database encryption; exported records, documents and backups remain sensitive.

Concrete deployment concern: docker-compose.yml publishes both application and PostgreSQL ports without a loopback host binding, supplies a known fallback database password, disables forced HTTPS by default, and enables a flag that skips transport checks on the assumption traffic stays on-host. Standard Docker port publishing is not localhost-only. Host firewall behavior was not tested, but the configuration does not enforce the stated boundary. Bind explicitly to loopback or a deliberately restricted interface, remove unnecessary database publication, set unique credentials and establish TLS before LAN exposure. No exploitation or live deployment was attempted.

Concrete recovery concern: app/services/backup_service.py uses SQLite's online backup API, a good consistency choice, and PostgreSQL dump/restore tooling. Its PostgreSQL restore invokes pg_restore with clean/if-exists, but without single-transaction or exit-on-error options; partial changes can remain after failure. It also bases a nonzero-result error decision on matching stderr text. Rehearse recovery into a disposable database rather than discovering failure on the only copy of business books. Preserve encryption keys separately and verify restored secrets remain readable.

Self-Hosting Notes and Solo-Business Acceptance Gate

Do not start with production financial or employee data. Prefer a single-user, offline evaluation; leave AI, bank feeds and public payment pages disabled until their data flows are understood. Server operation needs an explicit network boundary, role tests, backups and restore testing; do not use default Compose publication as proof of isolation.

Before replacing QuickBooks for a solo business:
1. Run a parallel month: invoice, partial payment, credit/void, expense, sales tax and bank reconciliation; compare reports and balances with the current books.
2. Validate every imported opening balance and outstanding invoice/bill, including taxes and foreign currency if used.
3. Restore a real backup into an isolated copy and verify documents, history, settings and encryption keys; keep independent/off-device copies.
4. Export the ledger and accountant-facing reports, and prove the receiving tool can use them. Retain original migration exports.
5. Have a qualified reviewer check payroll/tax outputs before use. License section 6 explicitly disclaims professional advice and filing certification; generated forms and NACHA files are not filing/payment execution or legal validation.

Go/no-go: Promising for a non-payroll solo-business trial; not a deploy recommendation from static inspection. Use a more established accounting workflow if there is no capacity to reconcile, test recovery and validate upgrades.
