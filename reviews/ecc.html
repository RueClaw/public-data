ECC packages a proposed engineering cycle: plan, test, implement, review, verify, remember and improve. Most specialist behavior lives in Markdown instructions consumed by an existing coding harness. For example, the planner declares Read/Grep/Glob tools and an Opus model; search-first guides investigation of existing packages and tools before implementation. Those declarations only constrain execution to the extent that the receiving harness implements them.

The executable layer is significant. The npm CLI dispatches setup, selective install, catalog/profile, memory, repair/uninstall, session inspection and control-pane operations. Claude Code is the primary supported integration; Codex has native plugin/config paths, while other adapters expose narrower capabilities. The README advertises 71 agents, 314 skills and 98 legacy command shims; these are upstream catalog counts, not independently certified behavior or quality scores. Overview and support matrix.

1. A large workflow catalog with useful engineering discipline

The research-before-coding, planning, TDD, review and verification material is reusable. The value is reducing repeated process design, not guaranteeing that an LLM followed the process. Domain-specific and security-related skill labels are not certifications. Instruction-only adapters cannot enforce Claude-style hooks. Start with a narrow workflow rather than advertise hundreds of unrelated skills to every session. Evidence: `skills/search-first/SKILL.md`, `agents/planner.md` and the README support matrix.

2. Managed installation is materially better than blind copying

The implementation separates install planning, application, state recording, diagnosis, repair and uninstall. Install-state validation rejects unknown fields and records operations; lifecycle logic uses content hashes and containment checks, and includes preservation of drifted/symlinked copies in relevant uninstall/migration paths. Hook consent explicitly discloses automatic source writes, command/process changes, transcript-derived LLM egress, MCP activity, permission gates and persistent records. This is unusually useful disclosure, but not a universal rollback guarantee for external side effects.

The legacy shell entry point automatically runs npm install with --ignore-scripts when node_modules is missing. That prevents dependency lifecycle scripts at that step, not registry access or subsequent runtime code execution. Auto-update pulls current repository changes and reinstalls recorded selections: an update changes trusted executable bytes and deserves review. Evidence: `scripts/lib/install-state.js`, `scripts/lib/install-lifecycle.js`, `scripts/lib/install/hook-consent.js`, `install.sh`, `scripts/auto-update.js`.

3. Hooks contain real checks, but are not a sandbox

GateGuard inspects tool/transcript evidence and distinguishes first-touch edits, destructive shell operations and routine commands. Config protection tries to prevent agents from weakening lint/format checks instead of fixing code. The dispatcher bounds input and fails closed on truncation for selected GateGuard/MCP checks; other paths intentionally return no opinion or skip unavailable helpers. Profiles default to standard and hooks can be disabled through configuration/environment.

This is defense in depth under a trusted operator, not an independent authorization kernel. A process with the user's filesystem/environment authority can influence configuration; the underlying harness still owns permissions, sandboxing and tool availability. Do not interpret a hook timeout, successful install or a security-scanner score as proof of containment. Evidence: `hooks/hooks.json`, `scripts/hooks/run-with-flags.js`, `scripts/lib/hook-flags.js`, `scripts/hooks/gateguard-fact-force.js`, `scripts/hooks/config-protection.js`.

Host harness versus ECC

The CLI dispatches local subprocesses; manifests select files and adapters; the host harness discovers instructions and invokes hooks. Hooks may read transcripts, run formatters/checks, inspect MCP services and write session state. There is no single ECC permission boundary covering every adapter and optional service.

The sampled Codex worker preserves the operator's configured sandbox and accepts only never/on-request approval policies. It canonicalizes the task-file path into its current worktree before invocation. Noninteractive never means no approval prompts, not no tool execution. The separately named yolo profile still specifies workspace-write rather than danger-full-access; naming alone would have produced the wrong security conclusion. User-install defaults use on-request and workspace-write, with live web search. Evidence: `scripts/orchestrate-codex-worker.sh`, `.codex/user-config.example.toml`, `.codex/yolo.config.toml`.

Important finding: session summaries can use existing provider authentication

The session-end path may trigger an LLM summary when remaining context is low or at a configured message interval (default 50). The helper extracts recent conversation text and starts claude --model haiku -p by default, reusing existing Claude authentication and inheriting the process environment. It has a recursion guard, deadline budget and mechanical fallback, but the inspected invocation does not explicitly disable tools, MCP or inherited CLI configuration. Conversation text is concatenated into the summarization prompt rather than submitted to a separately sealed no-tool evaluator.

Therefore “local memory” does not imply offline processing or no additional model usage. The installed hook consent does disclose this egress. For sensitive workloads, deliberately disable LLM summarization or verify the helper's effective provider, tools and configuration in an isolated pilot. This is a trust-boundary concern from static inspection, not a demonstrated exploit. Evidence: `scripts/hooks/session-end.js`, `scripts/lib/llm-summary.js`.

Providers, credentials and network access

The core content does not require an ECC-hosted account, but the selected coding harness generally uses its own provider account. The optional Python layer resolves Claude/OpenAI/Ollama/Atlas/Astraflow providers and saved provider/model configuration; its tool executor invokes registered Python callables directly. It sanitizes model-facing exception text, while raw exceptions remain in trusted logs. Application authors must impose their own tool schema validation, approval and isolation boundaries.

MCP examples include local package execution, unpinned npx packages, @latest entries, hosted endpoints and credential placeholders. Copying an entire example is a supply-chain and authorization decision, not harmless documentation setup. The opt-in Itô bridge is an external authenticated compute workflow, not free bundled inference; hosted ECC Pro/GitHub App is separate from this MIT tree. No provider, compute reservation, paid service or MCP connection was tested. Evidence: `src/llm/providers/resolver.py`, `src/llm/tools/executor.py`, `mcp-configs/mcp-servers.json`, `.codex/user-config.example.toml`.

Local dashboards are a trusted-machine boundary

The web dashboard explicitly describes loopback-only, unauthenticated operation. The control pane defaults to 127.0.0.1 and enables actions unless disabled. Shared Host/Origin checks help against DNS rebinding and browser-origin misuse, but accept absent Origin and compare hostnames rather than authenticating users; they are not tenant isolation or a general same-origin/token authorization scheme. Keep these operator surfaces off public proxies and shared untrusted hosts. Evidence: `scripts/dashboard-web.js`, `scripts/lib/control-pane/server.js`, `scripts/lib/loopback-guard.js`.

Memory, retention and recovery

Memory Vault: project/team scopes live under the project's .ecc/memory, user scope under the user's .ecc/memory. Default recall is project+team. New entries are create-only and unreviewed; types/statuses and sizes are constrained. Reads are bounded (including file-count and aggregate-byte limits), use non-symlink/regular-file checks, and enforce trusted-root containment. Creation requests owner-only directories/files, project memory is ignored by Git, and known secret patterns are rejected. The MCP wrapper makes user scope opt-in and uses a server-owned harness identity. These are meaningful controls. Evidence: `scripts/lib/memory-vault.js`, `scripts/lib/memory-vault-format.js`, `scripts/memory-mcp.mjs`.

Not a secret store or automatic knowledge approval: regexes recognize selected token/private-key formats, not all confidential prose, PII or novel credentials. Markdown storage is plaintext, and “unreviewed” is provenance, not a guarantee against prompt injection when recalled. No general TTL/encrypted-at-rest policy was established for the sampled vault. Backups, manual review, retention and deletion across every store remain operator responsibilities.

Continuous learning is separate: hook observation stores scrubbed tool input/output in JSONL; a background observer can transform observations into project/global instincts and later skills. Its checked-in observer setting is disabled by default. The observer uses a model subprocess with Read/Write allowed tools; it is not neural-weight training. Archives preserve rotated/processed observations, so rotation must not be confused with secure erasure. The skill's “100% reliable” hook-capture language is too strong: the implementation explicitly skips observation when a shell/helper is unavailable or fails. Evidence: `skills/continuous-learning-v2/config.json`, `skills/continuous-learning-v2/hooks/observe.sh`, `skills/continuous-learning-v2/agents/observer-loop.sh`, `scripts/hooks/observe-runner.js`.

Recovery is layered: mechanical session-summary fallback, saved handoffs, recorded install state and diagnosis/repair tools help continuity. They do not undo already-issued external API actions, restore every manually changed config, or prove a model-generated summary is accurate. The Rust alpha uses SQLite as its cross-process state source; its own documentation says the overall product and release packaging are unfinished.

Tests and maturity

The main CI definition has Linux Node 18/20/22 lanes, Windows/macOS Node 22 lanes, package-manager compatibility lanes, exact packed-artifact installation lifecycle checks, component/schema validators, Python lint/type/unit tests, coverage gates, signature/advisory checks and supply-chain IOC scanning. Actions are SHA-pinned in the sampled workflow and checkout credential persistence is disabled. Tests include memory boundary, read-completeness, MCP, summary and observer regressions. These are stronger maintenance signals than a prompt-only repository.

The public CI run for this exact SHA reported success: run 42296108996. That is upstream status, not a locally reproduced result or a claim that every optional integration works. The security job blocks high runtime npm advisories, not all development dependency advisories. No independent dependency audit, registry-to-source reproducibility check, complete license inventory or release-binary verification was performed.

Observed GitHub metadata: 299,049 stars, 44,184 forks and 241 open issues/PRs combined; these are transient popularity/activity counts, not evidence of safety. The latest reviewed source is newer than the 2.2.3 release. README caveats include optional Bash/Python requirements, macOS shell limitations and native-Windows observer/memory issues; code includes related fixes, but this review did not resolve those reports experimentally. Node 18 compatibility is a stated minimum, not a recommendation to deploy an obsolete runtime. Prefer a maintained supported Node release and test the exact host/harness combination. Evidence: `.github/workflows/ci.yml`, `tests/lib/memory-vault.test.js`, `package.json`, `README.md`.

Verification limits

This is a source-based architectural review, not penetration testing or a complete audit of the 314-skill catalog. No reviewed source was installed or executed, no host credentials or private data were used, and no model calls were made. Source/API access and upstream CI status were verified; behavior, performance, platform parity and recovery remain to be independently reproduced. No code was extracted from the repository.

There is no single production server to deploy. Keep the source/release version explicit, inspect the chosen adapter's effective permissions, preview the managed install plan, and preserve existing settings. Begin with a small no-hooks/selective profile; enable hooks only after reviewing their disclosed effects. Do not bulk-import MCP examples or assume opt-in observer behavior applies to every summary hook.

A useful pilot should measure task success, review defects, tokens/cost and wall time against the same harness without ECC. Exercise uninstall with modified user files, interrupted session recovery, oversized hook inputs, secret-bearing synthetic transcripts, memory-scope separation and provider-denied/offline operation. Keep dashboards local, pin external executables, and set a retention policy for vaults, summaries, observations, archives and databases. None of these deployment steps was performed during this review.

Verdict

The call, and why.

⚠️ Interesting

Selectively pilot the workflow layer, not the entire catalog as a trusted operating system. Strong managed installation and memory safeguards coexist with provider-backed summaries, executable hooks, uneven adapter parity and an unfinished Rust alpha.
