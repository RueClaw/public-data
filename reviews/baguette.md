# Baguette (tddworks/baguette)

**Repo:** https://github.com/tddworks/baguette
**License:** Apache-2.0 source; MIT idb-derived helper notices; Apple framework and model-asset rights require separate care.
**Reviewed:** 2026-11-20 (UTC)
**Revision:** 481680f37b46d4b59749d4c9333486bc3f17a959 — main, whole-repository static review with focused inspection of server, plugin, device, capture and release boundaries.
**Verification:** Static source/document/test inspection only. No builds, tests, devices, services, installations or live security probes were run.
**Stack:** Swift, SwiftPM, Hummingbird/NIO, Objective-C/C, VideoToolbox/SceneKit, plain browser JavaScript.
**What it is:** A Mac-hosted CLI and browser control surface for iOS simulators, cable-connected iPhones and Android emulators—not an AI model, agent runtime or isolated hosted device cloud.

## Verdict

⚠️ **Interesting — a strong local mobile-development workbench, not a shared security boundary.** The unified device/ability model, usable capture pipeline and explicit plugin provenance are compelling. Pilot it on dedicated test devices with a pinned Xcode/tool version; do not expose its HTTP control service to untrusted users or assume plugin capability declarations sandbox native programs. Private Apple APIs, newly added transports and asset-provenance questions keep it short of an unconditional deployment recommendation.

## What It Is

Baguette lets developers and automation harnesses boot devices, send gestures, inspect accessibility, capture screens and recordings, and manipulate simulated camera, motion, location and network conditions. The browser adds a device list, focus view, multi-device farm, bezels and 3D presentation. Its useful abstraction is “ask this device for an ability,” not “pretend every device implements every simulator feature.” Unsupported operations name the device and fail.

The README's broad feature table primarily describes simulators. Cable iPhones need pairing with Xcode, Developer Mode, an unlocked device and mounted developer disk image; their input support is narrower. Android emulators use SDK tools and emulator control interfaces. The separate Wi-Fi DeviceTwin companion is a **view-only preview**, requiring the user to start an iOS broadcast; it is not the same thing as wired phone control. ## Stack and Architecture

| Layer | Implementation and consequence |
|---|---|
| Entry points | ArgumentParser commands and Hummingbird HTTP/WebSocket routes share device operations. |
| Domain | BaguetteDevice defines identity, chrome and fine-grained abilities; family adapters live under Devices/Simulator, iPhone, Android and CompanionPhone. |
| Apple integration | Runtime private-framework discovery plus CoreDevice/UniversalHID weak linking and a C ABI bridge; symbols and capabilities depend on the installed Xcode stack. |
| Capture | IOSurface/CoreVideo/VideoToolbox, JPEG or H.264 frames, SceneKit for 3D rendering; browser WebCodecs/canvas and recording controls. |
| WebRTC | A separate WebRTCKit target owns signaling, ICE-lite, DTLS-SRTP, RTP/RTCP, resend/pacing and congestion logic using NIO SSL/BoringSSL. |
| Extensions | Declarative plugin manifests/panels; executable argv dispatched as host subprocesses, installed through pinned Git “bakeries.” |
| Persistence | Files and JSON registries, device state, capture outputs and browser localStorage; no central multi-tenant database. |

The package split is substantive: device roles are separated from CLI/server orchestration, and WebRTCKit knows about media transport rather than simulator internals. Mockable protocols and thin system seams make deterministic testing possible. However, Server.swift still contains over 2,500 lines of routing, streaming and trust logic; the architecture is not uniformly small. Apple symbol bindings, guest injection and a custom WebRTC implementation add maintenance burden beyond the tidy domain model. [[Package.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Package.swift), [Sources/Server/Server.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Server/Server.swift), [Sources/Devices/Android/Internal/Kit/AndroidTool.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Devices/Android/Internal/Kit/AndroidTool.swift)]

## Key Features and Claim Checks

- **One interface, explicit capability failures:** worth adopting as a design pattern. The route tree is /devices/:udid; older /simulators paths remain deprecated aliases, so integrations should expect migration rather than freeze the old spelling.
- **Capture and presentation:** screenshots, recordings, accessibility and interactive streaming are backed by real modules, not only demos. “60 fps” is a configuration/marketing ceiling, not a verified universal delivered rate. The WebRTC design records an end-to-end Chrome run at 38–40 fps and says congestion control was tested on a simulated link, not yet a real throttled one. This review did not reproduce those measurements.
- **New remote-view transport:** reviewed main includes unreleased WHEP/WebRTC work after v0.3.0. It supports H.264 High profile, with browser fallback where negotiation fails; host IPv4 candidates only, **no STUN/TURN**, and a UDP port per viewer. It is not a turnkey internet relay. Docs specify a 30-second connectivity-check expiry and a separate WebSocket control path.
- **Simulated world controls:** injected Objective-C libraries alter guest app behavior, including camera, CoreMotion and URLSession-related network conditioning. This is valuable testing instrumentation, not proof that all OS/device network traffic experiences a faithful network emulator. DYLD_INSERT_LIBRARIES changes are merged per library, rather than one feature erasing another's entry.

## Security, Consent and Privacy Boundaries

### Loopback defenses are not login or tenant isolation

The default service is 127.0.0.1:8421. Its server checks Host, Origin and Sec-Fetch-Site, including loopback DNS-rebinding rejection. Explicit allowed hosts are trusted for both Host and cross-origin browser access, ignoring ports; credentialed CORS reflects allowed origins. This is meaningful browser protection, and BrowserTrustRouterTests covers both accepted and denied routes.

But requests without Origin are deliberately allowed, and there is no general user login, per-device owner ACL or tenant session boundary in this control path. Any local program able to reach it shares the operator's authority; non-browser clients on a broadly bound interface do too. A wildcard allowed-host entry expands which web pages may control devices. **Never treat CORS, a UDID, a viewer ID or a private network address as authentication.** Add separately managed access control and encrypted transport if remote operation is necessary; avoid sharing one server between mutually untrusted users. The project's own security policy excludes deliberately broad exposure on untrusted networks. [[Sources/Server/Server.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Server/Server.swift) (trust checks and middleware), [Tests/BaguetteTests/Server/Router/BrowserTrustRouterTests.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Tests/BaguetteTests/Server/Router/BrowserTrustRouterTests.swift), [SECURITY.md](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/SECURITY.md)]

### Plugins are trusted local programs

There are good safeguards: scan/install does not execute plugin commands; browser installation is restricted to already-trusted bakeries; adding trust stays a terminal operation; installs demand the recorded commit instead of silently substituting HEAD. Per-invocation grants carry declared capabilities, are revoked on completion, and invalid presented tokens fail closed. The child environment forwards PATH and explicit Baguette context rather than the full parent environment. Commands get a ten-second timeout followed by termination/escalation.

These grants govern **requests that identify themselves as plugins**, not the process. PluginAccess treats an absent/empty token as anonymous, and plugin docs candidly explain that a child can call the ordinary local API, run other executables or read user files. No OS sandbox is established by the dispatcher. Tokens are not bound to one device in PluginGrants. A trusted plugin is therefore broad host trust, not a least-privilege app store. Git checkout also retains the host environment except for disabling terminal prompts, so source fetching remains subject to normal Git configuration and credential behavior. Plugin stdout accumulation is not visibly byte-capped in the dispatcher, despite the time limit. [[Sources/Plugins/Plugin/PluginDispatch.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Plugins/Plugin/PluginDispatch.swift), [Sources/Plugins/Plugin/PluginAccess.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Plugins/Plugin/PluginAccess.swift), [Sources/Plugins/Plugin/PluginGrants.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Plugins/Plugin/PluginGrants.swift), [Sources/Plugins/Bakery/Internal/GitCheckout.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Plugins/Bakery/Internal/GitCheckout.swift), [docs/features/plugins/README.md](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/docs/features/plugins/README.md)]

### Sensitive device contents and outbound flows

Screens, accessibility labels, app logs, pasteboards, notifications, app preferences and uploaded media can contain credentials or personal data. A connected automation harness gets consequential device actions, not just pictures; there is no per-tap human approval layer. Use synthetic accounts and spare test devices, and gate destructive actions in the calling harness.

DeviceTwin requires a user-started broadcast and iOS recording indication, which is real capture consent. Its “pair” flow is entering an address: the inspected hello checks UDID consistency, not cryptographic device identity. Plain HTTP/WS remote use does not protect screen or control traffic. WebRTC encrypts media with DTLS-SRTP but does not by itself authenticate the ordinary HTTP signaling/control surface. [[Sources/Server/ServerDeviceTwinRoutes.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Server/ServerDeviceTwinRoutes.swift), [Companion/DeviceTwin/Wire/Sources/TwinTransport.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Companion/DeviceTwin/Wire/Sources/TwinTransport.swift), [docs/features/device-twin/README.md](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/docs/features/device-twin/README.md)]

No model provider, inference API key or token-metered AI service is required for the core tool. Expected external flows include package/release retrieval, Git bakery fetches, optional asset sources, and whatever the tested apps or trusted plugins do. This is not a blanket no-egress guarantee. Costs are primarily Apple hardware, storage, device/SDK maintenance, concurrent encoding and network bandwidth; the WebRTC docs describe one encoder per viewer. Any external agent or remote-access service adds its own data policy and possible costs.

### Upload handling has guards, not service quotas

Upload routes strip supplied path components, validate extensions and resolve devices; camera staging validates its per-device slot. Ordinary uploads use unique temporary directories with deferred cleanup. The body cap is nevertheless **1 GiB collected in memory per request**, with no tenant quota established in that handler. Concurrent uploads/viewers are an operational resource risk on a shared service. The static inspection did not establish archive-decoder or malformed-media safety for all downstream parsers. [[Sources/Server/ServerFileRoutes.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Server/ServerFileRoutes.swift), [Sources/Device/Abilities/Camera/Internal/CameraSourceStaging.swift](https://github.com/tddworks/baguette/blob/481680f37b46d4b59749d4c9333486bc3f17a959/Sources/Device/Abilities/Camera/Internal/CameraSourceStaging.swift)]

## Persistence, Retention and Recovery

- **Plugin provenance:** the public docs describe a Baguette home containing trusted-bakery and installed-plugin JSON registries, cached checkouts and installed plugin directories. Registry writes are atomic and corrupted JSON is surfaced rather than silently interpreted as empty. A process-wide lock protects in-process read/modify/write, but the code explicitly says separate processes remain unserialized. Atomic file replacement is not a multi-file transaction or a backup.
- **Captures and browser state:** image/video exports and redirected logs are ordinary user-controlled files; browser localStorage retains capture/view preferences. App installs, Photos imports, preferences and other device mutations remain in the target device independently of the viewer.
- **Temporary does not mean erased:** camera sources outlive the upload until replacement or camera teardown clears the slot. Normal upload cleanup is best-effort. A crash, a never-started camera or filesystem errors can leave residue; no complete crash-time purge or secure-erasure guarantee was established.
- **No comprehensive restore contract found:** plugin remove/update and feature-specific stop/delete operations exist, but they do not constitute a global rollback of device state or an encrypted, versioned backup/export system. Before a pilot, keep known-good binaries/resource bundles, trusted-plugin pins and relevant test-device snapshots/backups. Avoid concurrent registry writers; test stop/reconnect/relaunch and restore on disposable devices after upgrades. Revoking a grant does not undo a program's filesystem or device side effects.

## Installation, Dependencies and Licensing

The documented baseline is Apple Silicon, macOS 15+, Xcode 26 and Swift 6.4 for the current source workflow; Package.swift has a 6.1 tools-version declaration, which is not proof that every older compiler builds this revision. Android needs its SDK tools too. This is not a Linux server merely because it exposes HTTP. The Homebrew formula installs the executable beside its resource bundle and uses an archive checksum; its smoke test only checks --help.

SwiftPM declares ArgumentParser, Mockable, Hummingbird, HummingbirdWebSocket and NIO SSL, with Package.resolved recording dependencies. Builds compile/stage guest helpers; committed resource binaries are not independently proven equivalent to source by this review. Release automation builds arm64, produces checksums and publishes archives, but the inspected workflow does not demonstrate Developer ID notarization or signed provenance attestations. CI actions use mutable version tags and setup-swift@latest. Checksums from the same release are useful integrity metadata, not independent publisher authenticity. No dependency advisory scan was run. Only the latest release receives security fixes per SECURITY.md.

The root Apache-2.0 license permits reuse subject to its notices, modification and patent terms. HingeControl carries an MIT idb/Meta notice that must be preserved. Do not assume this grants rights to Apple's private frameworks, DeviceKit artwork or every bundled USDZ model: several model definitions have null downloadURL and sha256 fields, while the Duo definition points to an installed Xcode resource. The package comment promising downloaded SHA-256-verified large assets is not proof of provenance for all shipped assets. Verify the origin and redistribution rights of each model before repackaging; no assets were extracted for this review. ## Maturity and Verification

Public GitHub metadata retrieved 2026-11-20 reported creation on 2026-05-01, last push on 2026-11-20, 2,302 stars, 132 forks and 13 open issues/PRs combined. These are discovery signals, not reliability evidence. The latest release endpoint reported **v0.3.0, published 2026-11-19**; this review covers the later main SHA above, including unreleased WebRTC changes.

There is substantial test and documentation infrastructure: 484 files under Tests (including fixtures, **not a test-case count**), JS node:test, Swift tests with coverage, doc/changelog checks, and an Xcode compatibility workflow. Sampled router tests explicitly verify anonymous access, foreign-origin rejection, rebinding checks, CORS and invalid plugin grants. Coverage configuration excludes resources and low-level system seams, so unit coverage cannot prove private-framework or real-device compatibility. The presence of workflows is not a claim that all current jobs pass; no full CI result audit was completed.

**Actually verified:** anonymous public source and metadata accessibility, exact Git revision, named source paths, implementation/doc distinctions, release metadata, license texts and static test assertions. **Not verified:** buildability, test pass rates, actual device control, latency/fps, real-network congestion recovery, cryptographic implementation correctness, plugin containment, asset rights, dependency vulnerabilities or crash recovery. No upstream instructions were executed.

## Comparison and Practical Fit

| Option | Prefer it when | Tradeoff relative to Baguette |
|---|---|---|
| Xcode Simulator + simctl | Official Apple lifecycle/debug workflows are sufficient | Less integrated browser/farm interaction, but fewer added components. |
| Appium + XCUITest / UiAutomator2 | Repeatable cross-platform test assertions and established automation protocols matter most | More setup; Baguette is a direct interactive device/capture workbench, not a replacement test runner. |
| Maestro | Declarative mobile UI test flows are the primary requirement | Different workflow emphasis; Baguette provides lower-level control and visual inspection. |
| scrcpy + adb | Android mirroring/control is the whole job | Narrower platform scope and simpler fit; no need to adopt an Apple-centric host stack. |
| idb / AXe | Existing iOS automation integrations already work on the required OS | Check exact compatibility; Baguette specifically targets changed iOS 26 HID behavior, a claim that still needs local validation. |

These are functional alternatives, not comparative benchmarks. Related public reading: [phoneuse](phoneuse.md), a different Linux-to-iPhone AirPlay/HID approach; it is not interchangeable with Baguette's Mac/private-framework architecture.

**Adoption gate:** one dedicated Mac, one synthetic test device, loopback-only service, plugins disabled until individually audited, pinned tool/Xcode versions, verified capture cleanup and restore, then a hardware-specific performance and compatibility smoke test. Useful to pilot and study; not ready to expose as a multi-tenant device cloud merely by adding a reverse proxy.
