What It Is

Sunlight preserves the positions of windows on an effectively unbounded canvas, with pan/zoom, minimap, snapping, saved layouts, desktop files/widgets and picture-in-picture tiles. It can hand a selected window back to normal native interaction. This is specifically Spacefarm's macOS project, not another product named Sunlight or a generic remote-desktop agent. The canonical source is the repository above; binaries and update feeds live separately in spacefarm-digital/sunlight-releases.

The public requirements are macOS 15+ and Apple silicon, with administrator authorization for live windows. No Linux, Windows or Intel-Mac support is established. Stage Manager is temporarily disabled. Main-display use is the default; multi-display canvases and interaction at arbitrary zoom are experimental. Documentation says live windows received most testing on macOS 27; CI targets macOS 26, so neither proves the entire advertised OS range. README, changelog.

Key Features and Architecture

### Two genuinely different rendering paths

The capture path represents windows with ScreenCaptureKit images (README says eight largest streams at 30 fps and other updates once per second). The live path applies transforms to actual WindowServer surfaces through code injected into Dock. App/Desk/CanvasController coordinate window discovery and canvases; Camera maps world coordinates to screen coordinates; RealWindowDriver and LiveWindowsConnection serialize snapshots into the payload protocol. It is not merely a screenshot grid.

The live driver replaces stale pending frames instead of accumulating animation history. A lease owns the windows it transforms; bounded I/O, acknowledgments, finite-transform and length checks, window-owner identity checks, and restoration on disconnect/lease expiry are meaningful defensive work. Up to eight leases can belong to the initial client process for multiple canvases. Recovery state is in Dock memory: a Dock crash destroys it, so timeout restoration is not a universal rollback guarantee. The documentation explicitly distinguishes compilation, synthetic socket tests and full visual/device validation. Sources/Canvas/RealWindows/RealWindowDriver.swift, Sources/Canvas/RealWindows/LiveWindowsConnection.swift, LiveWindows/osax/sunbeam.h, LiveWindows/README.md.

### Permissions and privileged execution

Demo mode asks for Accessibility and Screen Recording. Accessibility allows focus, moving/closing windows and reading/acting on UI; it is substantial authority even without SIP changes. Live rendering can avoid ScreenCaptureKit when available, but fallback may request Screen Recording. Live setup requires disabling SIP filesystem protections and debugging restrictions, an arm64e boot argument and root-assisted installation of the scripting addition. These are machine-wide security trade-offs, not a narrowly scoped app permission.

The signed helper checks a code-signing requirement containing Sunlight's bundle identifier and its own team; the XPC service only dispatches load and bootarg, serializes execution and exits when idle. Ad-hoc builds instead use an administrator prompt and a SHA-256-pinned sudoers rule for the helper's load operation. This is stronger than arbitrary shell-command RPC, but still creates persistent privileged integration. The source packaging path is unsandboxed. LiveWindows/helper.m, Resources/LaunchDaemons/com.spacefarm.sunlight.live-windows.plist, Sources/Canvas/RealWindows/AdditionReloader.swift, scripts/package.sh.

The Dock socket is user-owned and mode 0600. That excludes other OS users under ordinary filesystem permissions; it does not authenticate Sunlight's code identity. PID-based lease ownership prevents a competing process from taking simultaneous leases, not an unauthorized same-user process from being the first client. Move/order/level/Spaces dispatch is also present. Treat this as same-user desktop IPC, not a hardened multi-tenant or hostile-local-process isolation layer. There is no HTTP server, hosted account system or organizational RBAC in the reviewed architecture. LiveWindows/osax/payload.m, LiveWindows/osax/sunbeam.h.

### Takeover is not fully reversible

The README says every setting touched returns on quit. Code and the 0.2 changelog qualify that: takeover can move windows from other Desktops onto one Desktop per display and remove emptied Desktops. Consent text explicitly says merged Desktops are not recreated. Full-screen Spaces are treated separately. Preference restoration, Stage Manager restoration, watchdog/crash guard and safe-mode support are welcome, but do not restore the original Spaces topology. This matters before enabling takeover, even if no files are deleted. Sources/Canvas/Takeover/TakeoverMode.swift, Sources/Canvas/Spaces.swift, Sources/Canvas/Stability/Stability.swift, CHANGELOG.md.

Optional AI: Consent, Data and Costs

Tell Sunlight is real, shipped source, off by default in Experimental settings. It requires a user-supplied Anthropic key stored as a login-Keychain generic password, accessible when unlocked; settings can remove it. On submission, the request and current window list (including app names, titles and positions) go to Anthropic. Reads inside applications can send document/page/UI text and subsequent tool results. Settings discloses this. Therefore the README's absolute “only update checks” network statement is false when this feature is enabled. No model endpoint was contacted in this review. Sources/Canvas/Settings.swift, Sources/Canvas/Agent/AgentKey.swift, Sources/Canvas/Agent/ClaudeClient.swift, Sources/Canvas/Agent/AgentRun.swift.

The client hard-codes claude-sonnet-5-5 and the Anthropic Messages endpoint, requests up to 16,000 output tokens per response, and uses ephemeral prompt caching. A separately toggled server-side fallback option is off by default. Model availability, provider pricing, retention and fallback behavior were not independently verified. There is no demonstrated offline/local-model path or included inference allowance. The app may be free, but enabled AI incurs the user's API usage charges.

Code caps requests at 60 tool calls and checks a 300-second duration limit before executing tools; these are not a dollar budget or a strict end-to-end deadline, since HTTP replies and other work can extend wall time. Older reads are compacted in the in-memory conversation. Stop cancels further work, not effects already completed; no transactional undo or durable resumable-agent journal is established.

The guardrails block named settings/password/terminal apps, refuse typing into recognized secure fields, and require approval for pressing controls with certain English send/delete/pay/publish words or non-search Return. References must come from a snapshot in the current request. Those are useful code-level checks, not just a prompt. However they remain heuristic: renamed/unlisted apps, unlabeled/localized controls, auto-saving fields and operations whose consequences are not reflected in button names are not comprehensively covered. Blocked app contents and blocked app titles are different boundaries: initial canvas metadata is still sent. App/page text is declared untrusted in the model prompt, but there is no isolation sandbox preventing prompt-influenced actions in allowed apps. Supervise it on non-sensitive material; do not equate the UI's approval promise with complete authorization enforcement. Sources/Canvas/Agent/Guardrails.swift, Sources/Canvas/Agent/AppTools.swift, Sources/Canvas/Agent/AppReader.swift.

Persistence, Retention, Export and Recovery

Canvas.json and Layouts.json in the app's Application Support directory contain arrangement information, names/titles and, for named layouts, document URLs used for reopening files. JSON writes are atomic; malformed saved-list entries can be recovered individually, and the original unreadable file is set aside before replacement. This is a good recovery pattern. Saved layouts are not backups of document contents, unsaved edits or application sessions. Plain JSON is manually portable, but no general export/import compatibility guarantee was established. Keep a backup before editing or migration. Sources/Canvas/Layouts.swift.

Logs deliberately contain app/window information, rotate around 2 MB with one previous file, and are created with requested mode 0644 subject to umask and directory permissions; “local” does not mean encrypted or owner-only. Crash collection keeps up to 20 reports each for Sunlight and Dock. Diagnose summarizes rather than attaching the full title-bearing log/report text. Review diagnostic output before sharing. User-data removal covers preferences, support files, caches and logs, but the inspected removal function does not delete AgentKey; remove the API key explicitly in settings rather than assuming uninstall revokes it. Provider-side retention is separate and not controlled by deleting local files. Sources/Canvas/Stability/Log.swift, Sources/Canvas/Stability/CrashReports.swift, Sources/Canvas/Setup/SetupDiagnose.swift, Sources/Canvas/Setup/Uninstall.swift.

Uninstall is a guided reversal of Dock addition, boot argument/password rule, helper/login registration and SIP changes, with a Recovery step. Trashing the app alone is not equivalent. The implementation preserves unrelated boot arguments when constructing removal commands; merged Desktops remain a documented exception.

Build, Update, License and Maturity

The recommended make run builds a signed app and launches it; it is not a harmless test command. Packaging searches the keychain for signing identities, builds the helper, embeds Sparkle and signs nested components; release tooling can notarize and publish. None of those scripts was executed here. SwiftPM locks Sparkle to an exact revision but the manifest permits compatible updates; CI actions use major-version tags rather than immutable SHAs. Third-party binaries/frameworks and the separate release repository remain supply-chain inputs.

Sparkle configuration supplies HTTPS feed and EdDSA public key; upstream release tooling describes signing/notarization. Binary-to-source reproducibility, actual downloaded signature/notarization validity and update rollback were not verified. A missing manual-check feed returning 404 is displayed as “up to date,” which can obscure an absent/misconfigured release feed rather than prove freshness. Comparison and Practical Adoption

| Option | Better fit | Trade-off versus Sunlight | |---|---|---| | Rectangle | Conventional keyboard snapping | Less spatial expressiveness; a simpler alternative when a zoomable world is unnecessary | | AeroSpace | Keyboard-driven tiling/workspaces | Different mental model, not a live zoom canvas; investigate its own platform requirements | | yabai | Scriptable macOS window management | Relevant ancestor for Dock integration; privileged scripting-addition features carry similar SIP concerns | | Sunlight demo mode | Try the spatial interaction without Dock injection | Screen-capture permission and capture-renderer costs remain; not equivalent to real-window mode |

This is a desktop app, not something to self-host as a server. Start with demo mode and AI disabled on a non-critical Mac. Evaluate exact OS compatibility, recoverability after Dock/app failure, multi-display behavior and layout restore before relying on it. Keep SIP intact unless the live-window benefit justifies the explicitly understood platform-security cost. For managed or sensitive desktops, prefer simpler snapping/tiling until those boundaries and organizational policy are satisfied. The best reusable ideas here are lease-based restoration, stale-frame replacement and corrupt-layout preservation—not the assumption that a beautiful UI makes broad desktop authority safe.
