What matters most, in order.

A compiler, not a Cargo speed wrapper

Content-addressed source views and dependency-tracked queries reuse work across edits. Current native policy uses stencils and LLVM.

2

The headline measures v1

The 10–24× edit speedups are historical. Current-v2 benchmarks and compiler equivalence were not reproduced; keep pinned Cargo CI.

Build scripts inherit invocation inputs, normal tests run as the user, and daemon cache history outlives workspace cleanup. HTTP is owner-level authority.

Historical speedups do not measure this implementation

The README reports approximately 10× / 24× / 11× faster edits on macOS arm64 / Linux aarch64 / Linux x86-64. It and the benchmark document explicitly identify these as v1 results; no published v2 run supports transferring them to this SHA. The old ~20 ms live-edit headline needs the same qualification. methodology and raw-result links.

Positive evidence includes pinned project revisions, cold/no-op/body/signature edit cases, warm incremental Cargo baselines, repeated medians, raw JSON, machine/load details, fallback labels and memory/disk accounting. Limits include small samples (often three or five edits), different machines across platforms, busy Mac measurements and no confidence interval establishing a universal multiplier. Download time is excluded. Headline Cargo uses the default linker rather than the fastest mold/wild configuration; separate setup experiments should not be conflated with that baseline.

Historical memory costs are substantial: Linux x86-64 reports roughly 1.7 GB versus 528 MB for a ripgrep edit and 28.9 GB versus 8.5 GB for Bevy. Historical optimized-runtime geometric means are 1.10–1.18× slower than Cargo release. These are old measurements, not current resource guarantees.

The edit harness is not a compiler-equivalence proof. In the inspected harness, expected output comes from Blaze's cold program, and later edited outputs are compared against that. Cargo is primarily the speed baseline. Some fixtures only build or run help/version commands. Self-consistency can preserve an existing miscompile. harness/bench.py.

Security and privacy

Owner authority, not multi-tenant isolation. Unix sockets check ownership/peer identity and private permissions. The active API uses schema-versioned CBOR with size and queued-output bounds. Optional HTTP requires a nonempty BLAZE_API_TOKEN; its comparison is written to avoid secret-content-dependent timing. This is HTTP, not intrinsic TLS. Prefer local sockets or a separately secured transport, and do not expose a shared public compiler. One bearer credential reaches broad daemon operations rather than per-workspace RBAC. socket, server, startup.

Sandboxed does not mean secret-free. Build scripts receive the invocation's environment, with tracing/lending for cache keys; enumeration or child execution can expose all of it. The documented default filesystem view is broadly read-only, not necessarily project-only. Network denial and OUT_DIR write limits matter, but readable secrets can still enter outputs/logs. macOS also allows a per-user compiler cache. Workspace opt-outs and BLAZE_SANDBOX=off are execution grants. Plain tests and launched programs run as the user; test sandboxing is an opt-in experiment. sandbox contract, implementation.

Credentials/configuration are executable trust. Registry support reads Cargo-compatible tokens and can spawn configured credential-provider/token-from-stdout commands. They are local executables, not isolated provider APIs. Registry credential files have private-mode handling, not an encrypted-keystore guarantee. Review repository/config provenance before use. registry auth, provider processes.

Network is broader than building. Dependencies, toolchains, native inputs and releases are fetched. Update warning mode checks release metadata by default; automatic installation and offline modes are distinct. Digest-pinned fetch-url can retrieve bytes/Git trees and optionally write an output directory. A digest validates content, not permission to contact a host. Treat API callers as trusted owners and apply external egress controls where needed. No LLM provider, model or paid inference API is required by the compiler itself. Costs are CPU/RAM/disk plus any separately chosen hosted infrastructure; no hosted pricing/service guarantee was established. updates, fetch handler.

Remote-store machinery is not a secure shared service. SECURITY.md says no shared store is active. The source nonetheless contains remote client/server machinery that explicitly trusts its channel, lacks its own TLS/auth, refuses non-loopback TCP listeners, and verifies content without proving key-to-value mappings. No remote-store wiring was found in sampled normal daemon startup paths. Do not infer active cloud caching or tenant security from this module/roadmap. remote tier, security policy.

The policy calls Blaze a prototype without a security review. Its Windows warning also trails code: socket/windows.rs contains SID/DACL and peer-process checks where the policy says they are absent. This review does not validate Windows protection. Source inspection found meaningful controls, not proof against hostile code or sandbox escapes.

Persistence and recovery

Build directories, fetched source, compiled objects, VFS journals, images, build-script outputs, profiles and logs may contain proprietary material. State is local by default; no at-rest encryption or comprehensive secret-redaction guarantee was established. Keep stores owner-only: checksums detect damage, not a malicious writer substituting build code.

The detailed reference puts builds outside the checkout under the cache root, keyed by workspace path; the short guide's target/ wording is stale. Large output placement requires filesystem cloning according to the reference, failing on unsupported/cross-volume layouts instead of silently copying. Check filesystem fit. storage layout.

Recovery includes VFS torn-tail handling, block/content checks, explicit format mismatch rules, and daemon-image cold-start/refusal behavior. A graceful stop makes state durable. These were inspected, not crash-tested; retain source/lockfiles separately rather than treating cache state as backup. VFS, store.

GC protects leased/live directories, uses marked trash and rejects dangerous cleanup targets. Defaults include a 14-day workspace TTL, a 16 GiB workspace cap and grace periods. Daemon state/store/image/journal are excluded from GC, and store-value eviction is not implemented. Workspace cleaning therefore does not erase all retained source/build history or guarantee a total disk bound. serve.log rotates to two files totaling 16 MiB, not a global retention limit. GC contract, collector, fetch retention.

Outputs are native build artifacts and local diagnostic/profile formats, not an application-data export service. No complete portable backup/restore or secure-purge procedure was validated. Stop the daemon and inventory all retained roots before migration/decommissioning.
