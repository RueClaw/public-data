Key points

What matters most, in order.

1

Real shared-monitor architecture

One monitor can appear on several pages without duplicate checks. Incidents, maintenance, badges and scoped API tokens are implemented; MFA, SSO and private status pages remain roadmap items.

2

A live web server need not mean live checks

The entry point does not monitor early engine exit, and healthz always returns 204. Alerts have retries but no durable outbox; independently watch check freshness and delivery.

3

Trusted operators, bounded network reach

Browser users are full administrators and API grants span the installation. Monitor and webhook writes can reach internal networks; protect first setup, proxy access, database secrets and egress.

Uppies combines scheduled service checks, a web administration interface and branded public status pages in one server. A monitor belongs to the installation and can be placed on multiple pages, with page-specific ordering, categories and presentation. Public pages show uptime, response-time views, badges, published incident updates and maintenance history. This is not an AI agent, host-metrics collector, browser-testing platform or on-call escalation system. evidence 1evidence 2

The README's concise pitch is supported by the implementation. The roadmap also clearly separates future features: password-protected status pages, two-factor authentication, SSO, multi-location checks, configuration-file management and Uptime Kuma import are not present capabilities. Standalone binary releases, Atom feeds and email subscriptions remain planned. evidence 2

One monitor, several public pages

Monitor placements are separate from monitor ownership. A shared service can appear on several project pages without duplicated checking, and a placement can be excluded from that page's overall status. Custom domains, branding, per-page history windows and SVG/PNG badges are implemented. These are presentation boundaries, not separate tenants or authorization domains. evidence 6

Checks with explicit semantics

HTTP checks perform GET, accept 2xx after normal client redirects and optionally search a literal keyword in at most 1 MiB of body. DNS checks require at least one resolved address, rather than asserting arbitrary DNS records. Ping is IPv4 via an unprivileged datagram socket and depends on OS ping-group permissions. Push monitoring ignores a job until its first report, then allows a ten-second grace interval. TLS expiry warnings use 14/7/3/1-day thresholds. evidence 4evidence 7

Maintenance skips checks and alert transitions for covered monitors. Failure/recovery thresholds reduce flapping; confirmed transitions can produce draft incidents and follow published incident state. A new push job that never reports is not a reliable missing-job alarm until initialized. evidence 7evidence 8

API automation with meaningful limits

API v1 covers pages/layouts, monitors, alert channels, incidents and maintenance. Each route checks an exact grant against a live token on every request; expiry and revocation take effect immediately on the next request. JSON bodies are bounded to 64 KiB, unknown fields are rejected, pagination is bounded and API errors avoid printing potentially credential-bearing database messages. Tokens cannot substitute a browser session, and browser sessions do not authenticate the API. evidence 9

However, grants apply across the installation, not to a particular project. Any administrator can edit or revoke tokens. Repeating create/append requests can duplicate records: the documented API has no idempotency-key contract. evidence 9

Architecture

The entry point opens/migrates storage, constructs the check engine and web server, then starts both. The engine maintains one goroutine per active monitor, caps concurrent active checks at 32 and introduces startup jitter. Configuration reload cancels and reconstructs monitor loops; interrupted checks are not recorded as target failures. Results and rollups are stored, while notification deliveries run asynchronously. Embedded UI assets avoid a separate Node/frontend build. evidence 3evidence 7

The code is organized along useful boundaries: check performs one probe; health advances outage state; engine schedules and dispatches; store owns SQL and migrations; web handles browser/API/public surfaces. Explicit typed response projections and focused tests are stronger signals than the repository's popularity. evidence 4evidence 7evidence 9evidence 10

Important availability gap: the main select waits for process cancellation or HTTP server exit, but does not select on engineDone. If the engine exits early because loading monitors fails, the HTTP server can keep serving; /healthz always returns 204 without checking engine or database health. This is a static control-flow finding, not a reproduced failure. An outbound heartbeat is useful, but a heartbeat from the same still-running process is not proof that checks are advancing. evidence 3evidence 5evidence 7

Security, authority and privacy

  • First-admin setup is a deployment boundary. Setup is unauthenticated while no users exist. The raw executable defaults to all-interface :8080; the supplied Compose files bind the host port to loopback by default. Complete initial setup before exposing a reverse proxy. All signed-in browser accounts are administrators, with no per-project RBAC, MFA or SSO at this revision. evidence 1evidence 2evidence 3evidence 11
  • Good baseline controls, with proxy assumptions. Password hashing uses Argon2id (19 MiB, two passes, one thread); sessions are random, SHA-256-hashed in storage, 30-day, HttpOnly and SameSite=Lax. Secure cookies depend on TLS or X-Forwarded-Proto=https. Cross-origin protection, same-origin CSP and nosniff headers are present. The login limiter uses RemoteAddr, not forwarded client addresses: behind one reverse proxy, users can share the same failure bucket. Restrict direct backend access and normalize proxy headers. evidence 5evidence 11evidence 12
  • Monitor-writing permission grants network reach. HTTP/TCP targets and webhook destinations are syntactically validated but not restricted to public addresses; HTTP clients follow redirects and there is no application-level private-address/metadata denylist. That is useful for internal monitoring but unsafe as an untrusted tenant feature. A compromised admin or suitably scoped write token can cause server-side requests into the server's reachable network. Use dedicated network placement and explicit egress restrictions. No shell-command probe facility or os/exec use was found in the reviewed Go source; this is network authority, not demonstrated arbitrary command execution. evidence 4evidence 9evidence 13
  • Secrets are not uniformly protected at rest. Passwords, sessions and API tokens are hashed, but monitor targets, push tokens and notification destinations are stored as usable values in the database. API monitor reads omit targets, keywords, raw errors and push credentials; channel reads expose only ID/kind. Those protections also mean the read API is not a complete backup/export. Protect database files, volumes and backups as sensitive material. evidence 9evidence 14
  • Outbound alerts are deliberate data sharing. Generic webhooks include project, monitor, target and error; email includes the target; Slack/Discord send the summary, which can include error text. A keyword failure can include the configured keyword. Do not put secrets into monitored URLs, labels or keyword strings without considering these routes. SMTP upgrades with STARTTLS if offered, but does not require TLS for unauthenticated delivery. evidence 4evidence 13
  • Push URLs are credentials. GET and POST /push/{token} accept the path token; POST bypasses browser cross-origin protection intentionally. Reverse-proxy access logs and copied URLs can expose that capability. API credentials belong in Authorization headers instead. evidence 5evidence 9
  • Public means public. Hidden listings/noindex and custom domains are not access control. Public monitor detail checks page membership; Markdown rendering escapes raw HTML, rejects dangerous URLs and renders images as links. No external analytics requirement was found in the reviewed runtime paths, but this was not a dynamic traffic audit. evidence 2evidence 5evidence 6evidence 12

Persistence, recovery and export

SQLite uses WAL, foreign keys, a busy timeout and immediate write transactions. Before upgrading an existing SQLite schema, it writes a VACUUM INTO backup beside the database (unless that version's backup already exists), applies versioned steps and checks foreign keys before commit. A newer unsupported schema is rejected. This is a valuable upgrade safeguard, not scheduled/off-site backup or a demonstrated restore procedure. Other backend migrations follow a different path; do not assume SQLite's backup behavior applies to them. Turso SQLite explicitly requires a separate database from ordinary SQLite. evidence 15

Raw check results are pruned after 48 hours; rollups remain. Check coverage across long process gaps is capped at two monitor intervals, so the uptime number measures covered time, not all wall-clock availability. Optional visual backfill can color unmeasured days, but labels retain the no-measurement distinction and the numeric percentage is unchanged. Do not use a green historical bar as independent SLA evidence. evidence 6evidence 7

Alerts are best-effort: HTTP delivery retries up to three times on network errors, 429 or 5xx with short increasing waits, but no durable outbox/replay is implemented. SMTP has no corresponding retry loop. A crash after saving a transition can lose the alert; retries can duplicate external messages. Shutdown waits for deliveries, yet the alert deadline is one minute while supplied Compose grace is 15 seconds. There is no demonstrated HA scheduler/leader election: multiple instances sharing storage should not be assumed safe. evidence 3evidence 7evidence 13

Password reset is implemented as a database-access CLI operation that prints a new random password and invalidates sessions. Full recovery still requires a consistent database backup, external SMTP/database configuration and a pinned runnable version. No complete application export/import or cross-backend migration tool was found; API reads intentionally omit configuration secrets. Keep backend-specific backup/restore procedures and test them before upgrades. evidence 1evidence 9evidence 15

Supply chain, licensing and maturity

The project has an actual MIT license credited to ryana may que. THIRD_PARTY.md records Lucide/Feather ISC/MIT material and Simple Icons CC0; trademarks and transitive dependency licenses remain separate. No source code was extracted into this review. evidence 16

Go dependencies are version-pinned with go.sum. Base container images and the checkout Action are pinned by digest/SHA; the runtime container is non-root and the workflow disables persisted checkout credentials. These are good controls. Compose still defaults to a mutable latest application image. The optional Turso PostgreSQL image builds a checksum-pinned upstream tarball, patches foreign-key behavior and uses unversioned apt package resolution; it adds substantially more maintenance surface than the SQLite recommendation. Its internal-only Compose database network is an important boundary because the example uses passwordless PostgreSQL transport with TLS disabled. evidence 17

For a controlled pilot, prefer the documented SQLite Compose variant rather than the default compose.yaml's custom Turso PostgreSQL service. Pin an image digest or reviewed SHA-tag, keep the database volume durable, finish setup locally, then place it behind HTTPS with trusted Host/X-Forwarded-Proto handling. Before relying on it: run the test suite in an isolated environment, exercise each intended database/backend, test lost-network and lost-database behavior, restore a backup, verify alert delivery and process-kill recovery, and independently watch the freshness of actual check results.
