Cheyenne is aimed at open-source investigators following disasters, humanitarian crises and conflict. A browser globe combines orbital predictions with actual archive footprints, operator acquisition plans and optional live overlays. It distinguishes predicted imaging opportunities from confirmed tasking; commercial satellite visibility does not establish that an image will be taken. README

Its distinctive feature is composition: inspect the same place through optical/radar imagery, time-lapses, fire detections, recorded AIS and source-linked reports, then export imagery, annotations or a presentation card. The board does not independently corroborate Telegram reports or infer the cause of radar change. These are analytic aids, not evidence certification.



CelesTrak elements, ESA plans, scene catalogues and map layers are distinct inputs. Browser modules handle propagation, scene browsing and visualization; Python handles caching, selected proxy downloads and catalogue indexing. A three-hour TLE cache returns stale elements with an explicit stale flag when refresh fails instead of silently inventing fresh data. tracker, archive, TLE recovery

Ship detection with explicit uncertainty classes

The browser performs adaptive bright-target detection on Sentinel-1 radar over a land-masked area, then matches AIS and checks earlier passes for persistent objects. Classification distinguishes matched, dark candidate, near-shore, persistent and not-compared results. Crucially, the AIS archive tests recording sessions and at least two ships in a recording area within ±30 minutes; this avoids equating every empty feed with a dark vessel. However, the coverage test is area-level and checks the query centre, not reception at each detection. Sparse reception can still yield misleading confidence. Neither the README nor checked files supply a labelled validation benchmark. detector and classification, coverage heuristic

Burn scars and coherent change are implemented, but not validated here

Burn mapping applies fixed dNBR thresholds with reflectance and scene-classification filters; it is not a trained classifier. NISAR uses a custom HDF5 range reader and browser windowed complex coherence, optionally comparing an earlier reference pair. The code contains the stated stable-coherence (0.5) and loss (0.3) thresholds. These are meaningful algorithms, not proof of accuracy: crop cycles, weather, water, alignment and scene selection matter, and coherence loss cannot identify a strike or its actor. The README explicitly acknowledges unvalidated ship/burn detections and limited NISAR product coverage. Reported timings and the Kyiv example remain author claims, not reproduced results. burn rules, coherence implementation, HDF5 scope, limitations

Geolocated reports with a real privacy and spending boundary

Intel scrapes public Telegram previews, extracts written coordinates or sends post text and channel titles to Anthropic, and resolves place names through GeoNames with model-coordinate fallback. Approximate placement is not independent corroboration. Untrusted post text is placed directly in model input; structured output limits shape, not factual manipulation or prompt injection. The reviewed call is extraction-only, with no model tools or shell capability. resolution, model request

The repository has seven Python modules and a substantial browser module set rather than a framework-backed application. server.py routes local APIs, serves only the web directory, and coordinates Intel, AIS, NISAR and open-data managers. intel.py and ais.py own polling/feed threads and state; aisarchive.py stores positions; nisar.py uses h5lite.py to fetch only needed product chunks. The browser performs the heavy scientific and rendering work. Shared state/events and a small DOM helper connect modules. service routes, state, COG reader

The dependency-light design is attractive for inspection and setup. Its tradeoff is ownership of custom TIFF/HDF5 handling, projections, remote API compatibility and image-processing correctness. HDF5 support is intentionally partial and NISAR only supports UTM grids. Large typed-array analyses and concurrent downloads can consume substantial RAM and bandwidth. In particular, NISAR allows 36 million pixels; if an upstream ignores Range, Remote._get reads the entire response before slicing it. A nominally small window is therefore not a strict network or memory bound. NISAR transport, window cap

Security, permissions and privacy

  • Local-only is an actual boundary. The default bind is 127.0.0.1 and there are no user accounts. Do not expose --host 0.0.0.0 to untrusted users. same_site checks Fetch Metadata and Origin for Intel/AIS/NISAR APIs; POST requires JSON and a body below 16 KiB. These are useful browser protections, not authentication: non-browser clients can omit those headers. No explicit allowed-Host list is present, so this is not a complete DNS-rebinding defense. No exploit was attempted. handler
  • Not an unrestricted URL proxy. Planetary Computer downloads constrain collection and identifier formats and check blob host suffixes; NISAR requires HTTPS, its specific ASF hostname and an .h5 path. Initial destination restrictions are good, but redirects remain trusted upstream behavior rather than a comprehensive redirect/destination policy. asset signing, NISAR product gate
  • Keys remain server-side in the reviewed flows. Optional feed keys and the Earthdata token are environment inputs; NISAR status exposes a boolean. First-hop bearer authorization is separated from signed redirect requests. This does not establish absence of leaks across all dependencies or logs. Avoid copying the README's shell-profile key-storage example into shared environments.
  • Local UI does not mean offline or private. Upstream imagery, basemap, search and feed providers can observe requests, IP addresses and areas of interest. Telegram sees channel-page requests; Anthropic receives text/channel context when enabled. Browser annotations and local databases can themselves reveal an investigation; protect exports and backups. data sources and privacy, annotations
  • The daily Intel budget is a soft estimate, not a hard provider cap. The code uses hard-coded prices and checks recorded spend before a batch. Costs are accounted after responses; recursive splits can make more calls without rechecking budget. Failed/retried requests may further diverge from local accounting. The configured model string claude-haiku-5-5, SDK requirements, prices and claimed per-post cost were not independently verified against the provider. Use a provider-side limit and keep Intel disabled until explicitly approved. pricing constants, accounting and extraction

Recovery and operations

There are useful small-scale recovery patterns: atomic replacement of TLE and catalogue caches, AIS reconnect backoff, NISAR transient retries and signed-URL renewal, and resetting interrupted Intel busy rows to new at startup. SQLite uses WAL. These mechanisms improve resilience but are not a documented transactional job system or tested disaster-recovery plan. AIS reconnect, catalogue cache, Intel startup, NISAR retry

The Active Processes bar is browser in-memory state with cancel callbacks, not a durable server queue. Reloading does not resume an analysis. Aborting a fetch does not guarantee the server stops an already-running NISAR computation. Annotations require explicit GeoJSON export to survive browser-storage loss. Preserve data with a consistent SQLite backup or a stopped-server backup; regenerable .cache files are different from investigation records. jobs, annotation export

AIS recording areas deliberately keep feeds running without an open browser; Intel normally stops polling after three minutes without a watching client. Seven-day retention is not comprehensive erasure: AIS pruning deletes old positions and sessions but not the ships identity table or area definitions, and SQLite deletion does not itself guarantee physical byte removal. archive storage/pruning, pruning, Intel activity

This is a desktop-local service, not a multi-tenant hosted platform. The documented core needs Python 3.9+ and a WebGL browser; optional extras require Python 3.10+. run.sh only selects an existing virtual environment or system Python. Keep the default loopback bind, use a dedicated environment, review upstream terms, and leave paid analysis off until approved. Budget disk, memory and bandwidth for large scenes, and export annotation/data records before upgrades. ⚠️ Interesting — an unusually integrated investigation workbench, not a validated detection system. The implementation goes well beyond a map demo: real data adapters, range readers, analysis code and retention logic are present.
