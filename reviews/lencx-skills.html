Key points

What matters most, in order.

1

Activation is not authorization

coding-protocol separates read-only evidence work from execution. It explicitly rejects inferred permission to push, deploy, publish or overwrite user work; the host must enforce those boundaries.

2

Recovery needs a terminal invariant

keel distinguishes decisions, judgments and governance, including failure, uncertain commit and restart. It separates owners, writers and fact authority rather than assuming one actor owns everything.

3

Good prose is not a measured safety system

Two skills and eight references ship without tests or CI. Repository instructions remain a prompt-injection exposure, provider privacy depends on the host, and the installer is another supply-chain boundary.

Proportional verification

The verification reference requires a credible negative control and exact restoration, not merely a green check. Tests must reflect authoritative expected behavior, not freeze an incidental implementation.

Bounded architecture work

Keel keeps judgment separate from redesign, permits justified no-action and removal, and scales ceremony with impact. Records, cutover, rot audits and guard references load only when relevant.

Execution, injection and privacy

There is no independent permission engine, input-provenance validator, secret store, network client or telemetry implementation. Repository text and runtime output can still carry malicious instructions. Keep host approvals, isolation and redaction independent of the skill. A cloud model may receive code and logs; host/provider terms determine retention and cost.

Packaging and persistence

The packager checks paths, writes a temporary ZIP and force-replaces the output archive. It cleans its temporary directory on EXIT but supplies no archive signing, reproducibility controls or backup. Recursive inclusion can package local additions. The skills supply no durable job queue or restart engine.
