Key points

What matters most, in order.

1

Useful feedback, not a correctness oracle

Four plugins expose ten rules and exact-count legacy allowances. Scope-aware replacement detection is substantial, but no controlled defect-reduction study or precision/recall benchmark was found.

2

Network and timer guarantees are weaker than advertised

strict-msw accepts inline handlers that only record requests. A recognized vi.useFakeTimers call suppresses fixed-sleep reports for the whole file, without tracking restoration or separate tests.

3

Adopt conventions deliberately

Colocation accepts tests/ while naming rejects it under the all-error preset. Comment and return-type prohibitions are optional team opinions; preserve required license notices.

Testing policy with actionable errors

Rejects recognized behavior-replacing mocks, fixed sleeps, retry/timeout patterns and recorder polling. MSW startup checking is syntactic, not an egress firewall. Observation-only spies remain possible.

Count-based migration

Fewer violations than an allowance require reducing the baseline; equality passes. Counts do not identify individual violations. Retry errors are not covered by timeout allowances.

Version and style caveats

Public issue #9 reports MSW 3 option incompatibility; that external API claim was not independently reproduced. no-unsignaled-poll does not handle vi.waitUntil at this SHA. Explicit return types and prose comments can be valuable; enable those restrictions only intentionally.

Revision and evidence

Reviewed SHA: 92084b12872103b0f9245c0325ab571df00a574b. Static source, configuration and fixture inspection only. Public CI for this SHA reports success; no independent installation, tests or benchmarks were run.

Analysis design

AST visitors combine scope-aware framework detection with filename and call-shape heuristics. Cross-file ownership uses a resolver and Babel, confined logically to an enclosing package; this is not OS confinement. The 2,356-line replacement rule is a significant framework-maintenance commitment.

Execution and privacy

Plugins inherit linter-process authority and read source/manifest files. No model provider, account, credential store, telemetry transport or persistence service was found in inspected production paths. Diagnostics can persist in CI/editor/agent logs. Keep untrusted linting secret-free and bounded.

Supply chain and maturity

Version 0.1.0 has dedicated tests for all ten rules, invoking real Oxlint. Direct runtime dependencies are exact-pinned and a lockfile is present. CI uses pinned actions; release jobs separate packing and publishing and request provenance. Registry contents/attestations and branch protection were not audited. Project-local pilot, not server deployment

No service, model, dataset or credentials are required. Pin dependencies, select testing rules and measure false positives before enforcing. Keep style/types opt-in. Real-dependency tests require disposable services, synthetic data, egress controls and permission—not production credentials.

Recovery and costs

Rollback config/dependency changes in version control. No database or backup subsystem exists; external log retention belongs to your CI/editor/agent. Costs are compute and maintenance, plus any separately authorized integration services. No source code was installed or executed for this review.

Verdict

The call, and why.

⚠️ Interesting

Pilot selected testing rules, not the entire recommended preset. Actionable feedback and count-based allowances are useful; MSW, timer and directory-policy gaps mean passing lint is neither behavioral proof nor network isolation.
