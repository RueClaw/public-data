Key points

What matters most, in order.

1

Sessions become an implementation detail

The essay argues that human attention, not the model, limits multi-tasking; the authors say a person can follow only 3–5 sessions. A long-lived Router handles every human interaction and dispatch but never executes tasks. Isolated Workers each run one task.

2

Classic systems ideas, applied to agents

Fast/Slow-Path event filtering, Thread subscriptions with pass-through, “Inline & Spill” context, speculative execution, asynchronous start()/stop() tools, compute/state/environment separation and an external Watchdog. The authors present this as engineering practice, not new theory.

3

The ablation favors structure over prompting

Task time at p50/p95 was 12.4/15.7 min for Super-agent and 20.4/29.5 min for a single session that never delegated (0 of 5 runs). A single session with a delegation prompt reached 13.8/29.0 min. These are author-reported results from synthetic traffic with simulated coding.

4

It costs more tokens

Super-agent used 23.2M cache-read tokens per run, against 6.1M and 10.8M for the single-session designs. Removing pass-through raised it to 31.8M (about +37%) with no change in speed. Total tokens and cost are not reported.

5

The prototype covers part of the design, with broad local authority

The MIT prototype has a main Session, an Executor per Ticket and Thread subscriptions. No Watchdog or BYOM daemon was found, and its docs say workers run with danger-full-access as the operator’s OS user.

The bind: single-session agents

Today’s agents use a session as the unit of work, and sessions are isolated from one another. Running tasks in parallel means switching between sessions and remembering what each one contains. Adding MCP or CLIs so a local agent can read chat does not fix this: one synchronous session still blocks, mixes contexts, and stops when the device sleeps.

The essay’s example: the same agent continues a task across IM and GitHub while tasks stay isolated underneath.

Module

2 · Router + Workers: continuity and throughput

Routing every event to one session maximizes shared context but caps throughput and interleaves task details. A new session per event does the reverse. The two-level split aims to get both.

Compare designs
Router layer: thin, global, non-executing

A long-lived node for all human interaction and cross-task coordination, acting as the system’s global sequence point and memory. It does not execute tasks and can run without a Bash tool. The authors report that a lighter model is often enough.

Triggers that arrive during one inference turn queue up and are merged into the next call. Because the Router’s steps have long inputs and short outputs, prefill processes the batch in parallel, so amortized time per decision falls as backlog grows, up to a point.

Unlike an Agent Team lead that plans one task’s subtasks, the Router only dispatches tasks and tracks how they relate at a high level.

Worker layer: one task, isolated context, full tools

Each Worker owns one task, usually runs the most capable model, and never talks to people directly. It reports to the Router, which writes every reply. Workers that overlap on a shared pull request subscribe to the same Thread and can spot conflicts without messaging each other directly. A Worker may itself use subagents or an Agent Team.

3 · Triggers: the environment drives the agent

The main input is semi-structured events (chat, email, calendar, code-review comments, CI results) rather than typed prompts. Most of these events are noise.

Code drops noise cheaply; the model judges the remaining candidates; follow-ups on a subscribed Thread skip the Router.

Filtering and routing

Fast Path: deterministic checks on source, group and user/bot allowlists. Each source can be set to “respond only to explicit requests”, “treat as candidate events” or “ignore”. Slow Path: an LLM judges the remaining candidates against policies written as prompts, which people can change at any time.

The Router handles only cold starts and cross-task coordination. Subscriptions between Threads and Workers are many-to-many, and a Worker can unsubscribe or hand an event back to the Router.

Inline & Spill and Chain of Recall

The essay treats the context window as a cache. Inline puts information likely to be needed soon into the window. Spill keeps the rest outside, leaving a pointer or summary. Start with an ID and summary, add nearby content by locality, and truncate anything over the cap with a pointer to the rest.

Chain of Recall: Triggers, Threads and Worker Sessions get unique IDs. Related IDs are inlined, forming a reference graph that the model can follow hop by hop to recover the context of an old task.

Acting ahead (speculative execution)

The agent starts background work before it knows whether the result will be used. The internal example is a “silently reproduce and fix” policy: deliver only when the issue is confirmed and a simple fix exists, otherwise stay quiet. The essay gives no figures for hit rate or wasted compute.

4 · Full-duplex, multi-channel: talk while work runs

A classic ReAct loop blocks on a synchronous run(). Here, long calls become asynchronous start(), which returns “Started” immediately, and stop(). Results arrive later as new events.

Half-duplex: the user waits until the tool finishes, and new messages pile up unread.
Full-duplex: the conversation stays responsive and new input is handled after the current inference step.

According to the essay, DeepSeek Harness already implements this asynchronous mechanism, but it is not enabled by default.

Channel norms

IM: interrupt rarely, ask direct questions, give short conclusions. The essay cites a “verified” hard cap of 100 words per reply, without data.

GitHub, email, documents: structured, dense output, such as a pull request with background, the change and verification results.

Workers keep verbose reasoning and tool logs internal; only the Router speaks externally.

5 · Separating compute, state and environments

Local agents tie the agent loop, session state and the execution environment to one device. The essay separates them in two steps.

This parallels Anthropic’s “brain vs hands” decoupling. The essay’s stated difference is support for intermittently online personal machines (BYOM).

The essay argues that syncing real environments (uncommitted changes, private credentials, intranet dependencies, hardware) into a cloud sandbox is expensive and lossy, so it leaves them in place and reaches them on demand. Its own security section notes that this design assumes the cloud and the endpoints trust each other.

6 · Watchdog: an independent control loop

A running process does not mean the agent is healthy: a model can be stuck in an unproductive loop or drifting from its goal.

  • An independent Watchdog Session runs outside the main system and is driven by scheduled messages.
  • It handles infrastructure failures such as API errors and failed state recovery, and retries transient external failures until they resolve.
  • It uses the model to judge whether each Worker is making substantive progress or drifting from the goal.
  • Maintainers can ask it in natural language why something failed, and have it adjust prompts or trigger rules while the system runs.

A keyword search of the public prototype found no Watchdog implementation.

What the ablation shows, and what it does not

With the neutral prompt the model never delegated (0 of 5 runs): all work ran in the main session, new messages kept interrupting it, and p95 reached 29.5 min. With the delegation prompt it delegated in 4 of 5 runs, and the run where it did the work itself produced the long tail.

Without pass-through, the Router made about 30% more decisions and cache-read tokens rose from 23.2M to 31.8M (about +37%), with similar task times.

The two-level design used about 2–4× the cache-read tokens of the single-session designs. Total tokens, cost, quality and variance are not reported, and no harness or raw data is published.

Open problems the authors name

Scaling the two layers

When to shard the Router, when Workers should talk directly, and possibly training a model for Router work. Long-term memory over months is the main bottleneck beyond Chain of Recall.

Working without sessions

How to present tasks once sessions are hidden. More interaction may move into domain interfaces such as Issues and pull requests, and people still need to step in and take over during background work.

Context boundaries and A2A

Choosing which parts of an organization share an instance, and how isolated agents with different permission boundaries collaborate securely.

Security and privacy

Event-driven input is untrusted. A compromised cloud loop could take over every connected endpoint, and credentials must be usable without ever entering model context.

Reviewer’s limitations

  • Not reproducible: there is no public harness, workload or raw results; only five runs per design; and coding was simulated, so quality is untested.
  • Weak baseline: the neutral-prompt single session never delegated. Tuned orchestration or agent-team frameworks were not compared.
  • Cost understated: only cache-read tokens are reported, and Super-agent uses more of them.
  • Prototype gap: by its own README, the prototype is not identical to the essay’s design. Its deployment docs say workers run with danger-full-access as the operator’s OS user and recommend a dedicated OS account for isolation.
  • Provenance: the text is a machine translation, models and team size are undisclosed, and the figures were not inspected for this review.

Practical implications

For teams building always-on agents, these patterns are worth borrowing:

  • A thin coordinator that does not execute work and owns all replies
  • An isolated worker per task
  • Deterministic filtering before any model call
  • Thread-subscription routing for follow-ups
  • Asynchronous long-running tools
  • An external progress watchdog

Before relying on them, measure task quality, total token cost per task, p50/p95 latency and Router accuracy under batching on your own workload. Keep credentials out of model context, and run prototypes under a dedicated low-privilege account.

Verdict

The call, and why.

📚 Good reference

The essay gives a clear systems-engineering vocabulary for always-on, multi-task agents, and some of it appears in an MIT prototype. Its experiments are synthetic and indicative: five runs per design, simulated coding, and no public harness. The design also trades 2–4× more cache-read tokens for shorter, steadier completion times. Use it for the design patterns, not the benchmark. Static review only; nothing was run.
