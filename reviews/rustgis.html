⚠️ Interesting — evaluate on disposable datasets, not as a production GIS replacement yet. The implementation is substantial and its shared command engine is genuinely useful for reproducible automation. The unusually young public repository, approximate analysis choices and broad plugin/AI/native-runner trust surface call for controlled validation rather than accepting headline feature parity.

RustGIS combines familiar layers, tables, styling, layouts and map navigation with a command registry that can be driven by the GUI, CLI, automation and assistant. Native desktop and browser builds share much of the interface and engine. This is not merely a wrapper around an LLM: geometry, rendering, providers, analysis and project state are implemented in separate Rust crates.

The advertised 1,000-plus GeoLibre/Whitebox tools are external-suite integrations, not 1,000 independently reviewed built-in algorithms. Desktop use involves an optional native runner; browser integration has a separate adapter. Do not assume the two execution environments have identical capabilities or trust boundaries.

The layered workspace and engine expose the same command concepts to multiple interfaces. That is a strong foundation for repeatable map manipulation and integration tests, but a command being available does not establish that its numerical result is suitable for a particular scientific or surveying purpose. Workspace, engine, CLI.

The plugin runtime rejects imports other than three RustGIS host functions, creates fresh instances and applies fuel, memory and table limits. The instance memory ceiling is 512 MiB, and inbound messages are capped at 128 MiB. This is meaningfully stronger than importing arbitrary native code.

However, host calls run outside WebAssembly instruction metering. The inspected reply path serializes a host result before assigning it to the reply buffer and does not apply the same explicit MAX_MESSAGE check there. Thus guest memory/fuel limits should not be described as a complete host-memory/latency bound. Tools also run on the command/UI thread; the source itself describes a runaway tool consuming roughly 15 seconds of release-build time. These are static resource-exhaustion concerns, not demonstrated exploits. Runtime.

The stdio MCP server denies file/network access by default, reserves user automation and plugin management, bounds batches, and limits map-image dimensions. Broad access can be enabled explicitly. Existing web-tile layers may still generate network traffic, as the source documents: default-denied commands do not mean a fully offline session. This is a local stdio service, not a reviewed HTTP deployment with authentication/CORS. MCP policy.

Assistant provider configuration permits HTTPS and selected local HTTP endpoints. Model use sends prompts and accessed data to the selected provider. The optional “remember key” setting stores keys unencrypted in application preferences/browser storage, and the UI explicitly warns about that. Prefer session-only keys or carefully controlled environments; local-first does not mean that an enabled assistant keeps data local. Provider, key storage UI.

The workspace separates geometry/data, analysis/rendering, engine, plugins/assistant and GUI/application adapters. A layering check is present in CI. This is an appropriate way to keep the GIS domain independent from the presentation shell.

The analysis module explicitly describes work in Web Mercator with per-feature latitude scale corrections, giving approximately ground-distance buffers. That is not a substitute for validating geodesic behavior, high-latitude results, antimeridian cases and topology against established tools. The native GeoLibre runner is a trusted executable with user-level filesystem access, unlike sandboxed WebAssembly plugins. Analysis, GeoLibre boundary, browser adapter.
