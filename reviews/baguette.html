Key points

What matters most, in order.

1

Unified devices, unequal abilities

Simulators have the broadest control surface. Wired iPhones and Android emulators implement subsets; the Wi-Fi DeviceTwin preview is view-only.

2

Browser checks are not authentication

Loopback Host/Origin defenses matter, but no-Origin callers remain allowed. Plugin grants constrain identified API calls, not native processes running as the operator.

3

Measure on the actual hardware

Main includes unreleased WebRTC work, with no STUN/TURN and one encoder per viewer. The 60 fps headline is not a verified universal result; this review is static only.

Baguette lets developers and automation harnesses boot devices, send gestures, inspect accessibility, capture screens and recordings, and manipulate simulated camera, motion, location and network conditions. The browser adds a device list, focus view, multi-device farm, bezels and 3D presentation. Its useful abstraction is “ask this device for an ability,” not “pretend every device implements every simulator feature.” Unsupported operations name the device and fail.

The README's broad feature table primarily describes simulators. Cable iPhones need pairing with Xcode, Developer Mode, an unlocked device and mounted developer disk image; their input support is narrower. Android emulators use SDK tools and emulator control interfaces. The separate Wi-Fi DeviceTwin companion is a view-only preview, requiring the user to start an iOS broadcast; it is not the same thing as wired phone control. Evidence: [README.md, docs/features/real-devices/README.md, docs/features/device-twin/README.md]

- One interface, explicit capability failures: worth adopting as a design pattern. The route tree is /devices/:udid; older /simulators paths remain deprecated aliases, so integrations should expect migration rather than freeze the old spelling.
- Capture and presentation: screenshots, recordings, accessibility and interactive streaming are backed by real modules, not only demos. “60 fps” is a configuration/marketing ceiling, not a verified universal delivered rate. The WebRTC design records an end-to-end Chrome run at 38–40 fps and says congestion control was tested on a simulated link, not yet a real throttled one. This review did not reproduce those measurements.
- New remote-view transport: reviewed main includes unreleased WHEP/WebRTC work after v0.3.0. It supports H.264 High profile, with browser fallback where negotiation fails; host IPv4 candidates only, no STUN/TURN, and a UDP port per viewer. It is not a turnkey internet relay. Docs specify a 30-second connectivity-check expiry and a separate WebSocket control path.
- Simulated world controls: injected Objective-C libraries alter guest app behavior, including camera, CoreMotion and URLSession-related network conditioning. This is valuable testing instrumentation, not proof that all OS/device network traffic experiences a faithful network emulator. DYLD_INSERT_LIBRARIES changes are merged per library, rather than one feature erasing another's entry.

Evidence: docs/serve.md, docs/features/webrtc/README.md, docs/features/webrtc/design.md, Sources/Devices/Simulator/InjectedDylibs.swift, Injected/VirtualNetwork/Sources/VirtualNetworkHooks.m.

Loopback defenses are not login or tenant isolation

The default service is 127.0.0.1:8421. Its server checks Host, Origin and Sec-Fetch-Site, including loopback DNS-rebinding rejection. Explicit allowed hosts are trusted for both Host and cross-origin browser access, ignoring ports; credentialed CORS reflects allowed origins. This is meaningful browser protection, and BrowserTrustRouterTests covers both accepted and denied routes.

But requests without Origin are deliberately allowed, and there is no general user login, per-device owner ACL or tenant session boundary in this control path. Any local program able to reach it shares the operator's authority; non-browser clients on a broadly bound interface do too. A wildcard allowed-host entry expands which web pages may control devices. Never treat CORS, a UDID, a viewer ID or a private network address as authentication. Add separately managed access control and encrypted transport if remote operation is necessary; avoid sharing one server between mutually untrusted users. The project's own security policy excludes deliberately broad exposure on untrusted networks. [Sources/Server/Server.swift (trust checks and middleware), Tests/BaguetteTests/Server/Router/BrowserTrustRouterTests.swift, SECURITY.md]

Plugins are trusted local programs

There are good safeguards: scan/install does not execute plugin commands; browser installation is restricted to already-trusted bakeries; adding trust stays a terminal operation; installs demand the recorded commit instead of silently substituting HEAD. Per-invocation grants carry declared capabilities, are revoked on completion, and invalid presented tokens fail closed. The child environment forwards PATH and explicit Baguette context rather than the full parent environment. Commands get a ten-second timeout followed by termination/escalation.

These grants govern requests that identify themselves as plugins, not the process. PluginAccess treats an absent/empty token as anonymous, and plugin docs candidly explain that a child can call the ordinary local API, run other executables or read user files. No OS sandbox is established by the dispatcher. Tokens are not bound to one device in PluginGrants. A trusted plugin is therefore broad host trust, not a least-privilege app store. Git checkout also retains the host environment except for disabling terminal prompts, so source fetching remains subject to normal Git configuration and credential behavior. Plugin stdout accumulation is not visibly byte-capped in the dispatcher, despite the time limit. [Sources/Plugins/Plugin/PluginDispatch.swift, Sources/Plugins/Plugin/PluginAccess.swift, Sources/Plugins/Plugin/PluginGrants.swift, Sources/Plugins/Bakery/Internal/GitCheckout.swift, docs/features/plugins/README.md]

Sensitive device contents and outbound flows

Screens, accessibility labels, app logs, pasteboards, notifications, app preferences and uploaded media can contain credentials or personal data. A connected automation harness gets consequential device actions, not just pictures; there is no per-tap human approval layer. Use synthetic accounts and spare test devices, and gate destructive actions in the calling harness.

DeviceTwin requires a user-started broadcast and iOS recording indication, which is real capture consent. Its “pair” flow is entering an address: the inspected hello checks UDID consistency, not cryptographic device identity. Plain HTTP/WS remote use does not protect screen or control traffic. WebRTC encrypts media with DTLS-SRTP but does not by itself authenticate the ordinary HTTP signaling/control surface. [Sources/Server/ServerDeviceTwinRoutes.swift, Companion/DeviceTwin/Wire/Sources/TwinTransport.swift, docs/features/device-twin/README.md]

No model provider, inference API key or token-metered AI service is required for the core tool. Expected external flows include package/release retrieval, Git bakery fetches, optional asset sources, and whatever the tested apps or trusted plugins do. This is not a blanket no-egress guarantee. Costs are primarily Apple hardware, storage, device/SDK maintenance, concurrent encoding and network bandwidth; the WebRTC docs describe one encoder per viewer. Any external agent or remote-access service adds its own data policy and possible costs.

Upload handling has guards, not service quotas

Upload routes strip supplied path components, validate extensions and resolve devices; camera staging validates its per-device slot. Ordinary uploads use unique temporary directories with deferred cleanup. The body cap is nevertheless 1 GiB collected in memory per request, with no tenant quota established in that handler. Concurrent uploads/viewers are an operational resource risk on a shared service. The static inspection did not establish archive-decoder or malformed-media safety for all downstream parsers. [Sources/Server/ServerFileRoutes.swift, Sources/Device/Abilities/Camera/Internal/CameraSourceStaging.swift]

- Plugin provenance: the public docs describe a Baguette home containing trusted-bakery and installed-plugin JSON registries, cached checkouts and installed plugin directories. Registry writes are atomic and corrupted JSON is surfaced rather than silently interpreted as empty. A process-wide lock protects in-process read/modify/write, but the code explicitly says separate processes remain unserialized. Atomic file replacement is not a multi-file transaction or a backup.
- Captures and browser state: image/video exports and redirected logs are ordinary user-controlled files; browser localStorage retains capture/view preferences. App installs, Photos imports, preferences and other device mutations remain in the target device independently of the viewer.
- Temporary does not mean erased: camera sources outlive the upload until replacement or camera teardown clears the slot. Normal upload cleanup is best-effort. A crash, a never-started camera or filesystem errors can leave residue; no complete crash-time purge or secure-erasure guarantee was established.
- No comprehensive restore contract found: plugin remove/update and feature-specific stop/delete operations exist, but they do not constitute a global rollback of device state or an encrypted, versioned backup/export system. Before a pilot, keep known-good binaries/resource bundles, trusted-plugin pins and relevant test-device snapshots/backups. Avoid concurrent registry writers; test stop/reconnect/relaunch and restore on disposable devices after upgrades. Revoking a grant does not undo a program's filesystem or device side effects.

The documented baseline is Apple Silicon, macOS 15+, Xcode 26 and Swift 6.4 for the current source workflow; Package.swift has a 6.1 tools-version declaration, which is not proof that every older compiler builds this revision. Android needs its SDK tools too. This is not a Linux server merely because it exposes HTTP. The Homebrew formula installs the executable beside its resource bundle and uses an archive checksum; its smoke test only checks --help.

SwiftPM declares ArgumentParser, Mockable, Hummingbird, HummingbirdWebSocket and NIO SSL, with Package.resolved recording dependencies. Builds compile/stage guest helpers; committed resource binaries are not independently proven equivalent to source by this review. Release automation builds arm64, produces checksums and publishes archives, but the inspected workflow does not demonstrate Developer ID notarization or signed provenance attestations. CI actions use mutable version tags and setup-swift@latest. Checksums from the same release are useful integrity metadata, not independent publisher authenticity. No dependency advisory scan was run. Only the latest release receives security fixes per SECURITY.md.

The root Apache-2.0 license permits reuse subject to its notices, modification and patent terms. HingeControl carries an MIT idb/Meta notice that must be preserved. Do not assume this grants rights to Apple's private frameworks, DeviceKit artwork or every bundled USDZ model: several model definitions have null downloadURL and sha256 fields, while the Duo definition points to an installed Xcode resource. The package comment promising downloaded SHA-256-verified large assets is not proof of provenance for all shipped assets. Verify the origin and redistribution rights of each model before repackaging; no assets were extracted for this review. Verdict

The call, and why.

⚠️ Interesting

Strong unified device abilities, capture and plugin provenance. Pilot locally on synthetic test devices; anonymous control, unsandboxed plugins, private Apple APIs and unreleased transport work rule out treating it as a secure multi-tenant device cloud.
