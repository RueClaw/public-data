Key points

What matters most, in order.

1

Real touch integration, narrow hardware scope

Pixel 7 Pro is the main target. Fold, Pixel 6 and Pixel 4 are separate bring-up stages, not equivalent supported phones. Waydroid remains a goal.

2

Phone fundamentals still block adoption

No SIM validation of registration, SMS, data or calls. Reported s2idle draw is 312 mA versus 32–50 mA in stock deep sleep; suspend is not on by default.

3

Guarded flashing is still destructive

The installer constrains writes and checks device identity, but erases userdata. Widget approvals are not a sandbox; root SSH and unauthenticated-by-default USB mirroring deserve explicit trust decisions.

The cheetah modem boots firmware and answers IPC, but the matrix explicitly says no SIM test has happened. A ModemManager-shaped API and Calls/Chatty integration do not prove calls, SMS, data or emergency calling. Four cameras have image paths, but telephoto focus is unresolved and quality is basic. A genuine mobile session

The shell package provides status bar, quick settings, home pages/widgets, drawer, recent-app switcher, permission sheet, keyboard controls and fingerprint UI. phone.lua maximizes ordinary windows, handles power/volume/screenshot gestures and arranges keyboard/fingerprint surfaces above the session lock. The session auto-logs in then requests a lock when configured: not boot-time encryption, and lock startup/failure behavior needs adversarial testing.

Sensor integration adapts AoC sensors to the iio-sensor-proxy D-Bus API and transforms both display and touchscreen during rotation. That avoids the obvious input-coordinate mismatch. Full-screen placement does not make every desktop application touch-friendly.

Power remains a practical blocker

The matrix reports 31/31 Wi-Fi-connected s2idle cycles, but screen-off suspend is not on by default. Reported screen-off consumption is 434 mA awake, 312 mA in s2idle, versus 32–50 mA in stock deep sleep. Deep sleep is not started. These are project measurements, not independently controlled benchmarks or a universal battery-life estimate. Charging has a temperature guard; USB Type-C/role switching remains unfinished. Screen-off is not phone-grade standby.

Widget approvals are not OS isolation

OWL exposes command, HTTP, file and Linux-adapted device sources. OwlPhoneHost.qml checks approvals/network settings and executes commands through timeout and bash -c in the user's session. Network classification uses command capability analysis, not a separate network namespace. Approval sheets and risk heuristics therefore should not be sold as strong isolation for hostile code. Approved widgets exercise user authority; AI-created or arbitrary QML widgets require code-review-level trust.

Limits and conformance fixtures are good engineering, but output truncation is not a full process/memory sandbox. Widget web requests and optional location-based weather disclose data to selected services. The README describes an AI-agent chooser with no agent preinstalled; provider credentials, terms and costs remain separate choices.

This is an integration layer around moving upstreams, not one self-contained app. Descriptors feed build/flash tooling; rootfs construction installs regular and patched packages; firstboot creates the owner and enables services; shell packages seed per-user profiles. Hardware bridges expose standard desktop interfaces where possible.

The design is coherent but maintenance-heavy: patched Mesa/Hyprland/libcamera, Omarchy patch reapplication, external kernel, vendor firmware and separate omacam versions must remain compatible. pacman.conf gives mobile packages precedence and requires package signatures (database signatures optional; local-file signatures optional). omacam's PKGBUILD pins an archive checksum and locked Cargo fetch/offline build. Good hygiene does not prove whole-OS reproducibility or security.

Security and permissions

  • Boot/data protection: unlocked bootloader; inspected initramfs directly mounts an ext4 root, with no encrypted-root unlock flow found in that path. A PIN/session lock is not Android-equivalent at-rest protection or verified boot. Full hardening was not audited.
  • Credentials: installer uses SHA-512 crypt, restrictive firstboot-file permissions and normal-exit cleanup of temporary config/image copies. Wi-Fi secrets temporarily reside in provisioning data. This is not secure-erasure proof after crashes. Any nonempty PIN/password is accepted; choose a strong one.
  • SSH/firewall: firstboot installs the supplied public key for root and owner; its SSH drop-in disables password authentication. It allows SSH on USB but also TCP/UDP 53317 without interface restriction, and permits outbound traffic. USB-only SSH does not mean every inbound service is USB-only. Verify actual listeners/rules.
  • Mirroring: wayvnc integration is on-demand, USB-bound, session-scoped and has no password by default; optional password/RSA-AES is available. An active mirror grants screen/input access to the connected host. Do not assume authenticated encryption by default; runtime binding/firewall behavior was not tested.
  • Permissions: portal consent improves portal-aware apps, not isolation of every native app or direct hardware access. Sensor docs permit any local user to claim gyro data. Vendor chroots, firmware and fingerprint bridge add privileged attack surface despite the mainline-kernel label.
  • Network/privacy: GNSS assistance options, widget endpoints, NFC-opened links and ordinary native applications create network boundaries to assess. No traffic instrumentation or exhaustive daemon/parser/polkit/dependency audit was performed.

This is an unlocked-phone firmware/root-image workflow, not a casual desktop add-on. The documented host needs Arch/Omarchy, Docker, android-tools and e2fsprogs, plus the owner's factory image. Nothing was installed for this review.

install-phone parses descriptors as restricted data instead of sourcing shell, checks one fastboot device, codename, unlocked status, matching bootloader-slot versions, checksums and some kernel/module consistency. Bundle mode checks a signed checksum manifest against a pinned fingerprint unless explicitly allowed unsigned. A narrow flash function accepts descriptor-approved slot-B boot images and userdata, gated by typed codename. These are meaningful safeguards, not authentication of an untrusted installer itself; repository mode and signed-bundle verification differ.

Installation erases userdata, including Android data. Slot A boot images survive, but Android needs a factory reset on return. The reinstall runbook documents recovery and one clean reinstall on 2026-10-13, including subsequently fixed missing firmware/services. This is not transactional installation or nondestructive uninstall. Old userdata survives only in backups. The generic installer refuses non-android-v4 boot methods: do not apply cheetah instructions indiscriminately to Pixel 4 probes.

The installer's narrow write scope is not a blanket no-sensitive-writes guarantee. The matrix says boot-success marking writes slot flags in devinfo; fingerprint startup writes Trusty secure storage/RPMB. Fingerprint is appropriately opt-in and the runbook calls that step irreversible. These lifecycle exceptions qualify the README's broad partition-safety language.
