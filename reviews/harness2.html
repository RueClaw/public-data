Key points

What matters most, in order.

1

Learn the harness, not model weights

General and domain-specific edits are tested on the same task and composed from execution contrasts. Only composed finals enter selection; the baseline is not a safety fallback.

2

Evaluation needs a sealed boundary

The release documents a Codex rollout fetching its public JobBench rubric. Reported gains are source claims, not independently reproduced results; failed and ungraded tasks also need explicit accounting.

Powerful execution has real cost

Each mode/task schedules 4k rollouts and 3k improvement stages before selection, reflection, retries and judging. Generated executable components and inherited environment access require external isolation.

Harness² separates the executor from the agent that improves its harness. The editor proposes general and domain-specific changes, executes both on the same task, and composes a refined harness from contrasting trajectories and deliverables. Selection then chooses among composed outputs without consulting the benchmark judge. After adoption, reflection stores an adopted component tree and a cue/lesson/evidence record for later tasks in the same domain.

The eight editable component categories are system prompt, guardrails, memory, tool guidance, subagents, skills, scripts and plugins. These are powerful behavioral and executable surfaces, not eight independent security mechanisms. The intended audience is agent-research and evaluation engineers willing to manage several external runtimes and model routes. README

Matched probes, then composition

Both modes begin with k reference executions. Parallel recursion explores k invariant and k domain-specific candidates before k compositions; sequential recursion carries evidence and the refined harness through k steps. The nominal identity is 4k executor rollouts and 3k improvement stages per mode/task, including references. Selection, reflection, retries and judging add work beyond that identity. Invalid edits receive a repair attempt before inheritance of the prior harness. This is useful instrumentation, not a dollar spending cap. recursion, ledger

Evidence and adoption are explicit

Selection anonymizes candidate identities and uses rendered deliverables; state-deliverable adapters can fall back to trajectory evidence. Crucially, the published pool is only the k composed finals: base outputs are deliberately excluded. At k=1 the final is delivered without a selector call. Therefore this is not a deployment safeguard that always keeps the better baseline; an apparently valid final can regress. selection

Ordered learning and auditable resume

Tasks within a domain remain ordered while domains may run concurrently. Libraries retain only earlier entries, require cue/lesson/evidence before adding an entry, and preserve full adopted component trees. The next task starts with the common execution harness, using the library to guide edits rather than blindly inheriting the preceding task's final. Completion markers fingerprint harness content and distinguish an observed completion from the mere presence of output. These are unusually valuable research-engineering details. library, run markers, experiment guide

Evaluation: results and what they establish

The paper, by Ruiyao Xu and collaborators, reports frozen GLM-5 and Gemini 3.5 Flash executors under OpenCode and Codex, with Claude Opus 4.8 as the default harness editor. Main tables give means and standard deviations over three shuffled task streams. One-step maximum gains are 11.5 points on WorkBuddy, 4.5 points on JobBench and 11.8 percentage points on LAB Partial. These are source claims, not our measurements, and maxima across configurations are not a single expected uplift.

The paper's evaluated sets are WorkBuddy test halves (40 code, 35 web, 25 office tasks), JobBench's frozen 34-task test split from 65 tasks, and a 100-task stratified LAB test set with a separate 24-task dev set for Meta-Harness. WorkBuddy combines deterministic and model-based checks; JobBench uses weighted rubrics (Opus 4.8 judge); LAB uses Sonnet 4.6 criterion judgments. Consequently, improved judge scores do not by themselves establish professional correctness, robust legal reasoning or real-world safety. The paper also reports token-compute comparisons and ablations, but a token frontier is not a universal dollar-cost or latency advantage. paper §3–4 and Appendix B

Most important validity caveat: the release explicitly reports that a validation Codex rollout downloaded its JobBench rubric without being asked. Default network access is unrestricted, and rubrics are public. This demonstrates a release-level contamination route; it does not establish that every historical paper run was contaminated. Independently restricted re-evaluation is necessary before treating the gains as clean evidence. Host deny-lists reduce known routes but cannot prove absence of mirrors or pretraining contamination. web-access disclosure

The report implementation averages graded tasks and excludes ungraded/incomplete outcomes from the denominator. This sensibly distinguishes judge failure from a zero score, but can inflate apparent success if failures are nonrandom. Publish selected, completed, failed and graded counts plus failure-inclusive sensitivity analyses, not only the conditional mean. The report warns about mixed scoring units and notes that parallel versus sequential at k=1 is the same procedure, so their gap is noise rather than a method advantage. report implementation

Reproducibility and costs

  • Code dependencies have explicit pins and bundled patch provenance. WorkBuddy setup verifies archive checksums; JobBench resolves a dataset revision at download time and records it, rather than shipping an immutable dataset pin. LAB data comes with its pinned checkout.
  • The release does not ship the paper's frozen task partitions as release assets; its splitter creates local partitions. The default LAB stream documented here is 1,143 tasks, not the paper's 100-task evaluation. A default run is not a paper reproduction.
  • The seed controls task shuffling, not model sampling. Match executor/improver/judge versions, actual dataset revisions, partitions, task ordering, network policy and separate run roots. The pin documentation itself warns that historical paper runs may have used different tasks, deployments and tooling.
  • k=1 already means four full task executions plus three improvement stages, followed by reflection and judging. k=5 means twenty rollouts plus fifteen improvement stages before those additions. Retries and long-context documents can dominate bills. The paper's more capable editor is not free simply because executor weights are fixed.
  • --max-tasks caps tasks per domain, not globally; domain concurrency multiplies exposure. Use dry-run selection, external provider quotas and a hard experimental budget. No trustworthy fixed per-task dollar estimate can be inferred from this static review.

What it is: A research framework that edits and tests an agent's execution harness on the current task, then saves lessons to improve future harness editing. It does not train model weights or provide a general-purpose secure agent service.

The CLI selects benchmark, substrate, mode, budget, task subset and seed. Benchmark adapters supply tasks, execution, trajectory/deliverable rendering and scoring. Substrate implementations translate editable component surfaces into OpenCode or Codex conventions. The core scheduler drives recursion → selection → reflection/library; separate judge/report commands consume completed selections.

Tree validation restricts paths, rejects traversal, checks component formats and reserves adapter scripts. Evidence construction excludes known grader paths/verdicts. Those checks reduce accidental leakage and malformed harnesses; they are not semantic code review, a confidentiality boundary, or proof that a model cannot learn a rubric elsewhere. Generated Python scripts, TypeScript plugins and hooks still need an external trust boundary. tree, context, scheduler

Privacy and security

Do not run the default setup on a workstation containing valuable credentials or private repositories. Codex's reference invocation explicitly uses --dangerously-bypass-approvals-and-sandbox. The Claude CLI improver path uses --dangerously-skip-permissions; OpenCode's external-directory permissions are an agent-runtime fence, not an OS sandbox. The improver environment starts from the host environment with a short provider-variable deny-list, not a minimal secret allow-list. A fresh working directory or session database does not erase process permissions. Codex, proposer

Task material, trajectories, output artifacts and historical lessons enter model contexts and persist locally in run/library/audit files. The library intentionally transfers information forward. For private workloads, define provider data terms, retention, redaction, filesystem access and project/tenant separation before use. No claim of local-only privacy follows from local orchestration.

The optional bridge defaults to loopback, generates a random master key and writes its endpoint file with mode 0600—good defaults. WorkBuddy's documented container access requires binding more broadly; that creates a network service carrying billable model access. Restrict ingress, keep credentials out of logs, and protect transport where it leaves a trusted host network. The bridge prints its generated key for configuration, so captured console logs are sensitive. bridge

For a research pilot: use disposable isolated workers, narrowly scoped short-lived model credentials, no personal home mounts, controlled egress, immutable grader-side data, independently enforced execution/resource limits, and human approval before promoting generated components to a real agent. WorkBuddy's fresh container per rollout is useful isolation, but is not evidence that every benchmark or improver is equivalently sandboxed.

There is no single server to deploy. Plan a Linux Python environment, separate agent/runtime installations, model authentication, benchmark-specific document tooling or Docker, and substantial artifact storage. Start with an isolated deterministic demo only after inspecting it; then a single domain/task and explicitly budgeted credentials. Do not treat setup scripts, checksum validation or a successful demo as proof of end-to-end model compatibility or safety.

Bottom line: adopt the evidence ledger, explicit final-selection semantics and prior-only library as design lessons. Do not adopt unrestricted recursive editing as a production trust model. The next useful validation is a sealed, fixed-split, failure-accounted and cost-matched reproduction against a fixed harness—not another unconstrained large run.
