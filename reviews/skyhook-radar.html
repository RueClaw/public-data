Key points

What matters most, in order.

1

Context for humans and agents

Topology, issues and changes feed UI and MCP. Separate read-only catalogs are meaningful; the full endpoint still exposes mutations.

2

Read RBAC has a namespace tradeoff

Ordinary namespaced cache reads are broader than exact per-kind Kubernetes permissions. Shared deployment requires trust-boundary scoping and careful impersonation/Secret grants.

3

AI and Cloud expand the boundary

Agent context can reach model providers; full-local adapters auto-approve tools. Optional Cloud tunnels the router, while history and transcripts create sensitive stores.

Skyhook’s Radar runs against local kubeconfig, as a desktop app, or in Kubernetes through Helm. Go watchers populate a shared model served through a React UI, SSE and MCP. Features cover resources, topology, issues, logs, Helm/GitOps, traffic, metrics and change history. Richer views need existing integrations: “no agents” describes the basic client, not all possible data sources. readme

Radar also drives installed AI CLIs and optionally connects to Radar Cloud via an outbound tunnel. Neither is required for local browsing. The client is reviewed here, not the remote Cloud service’s tenancy, retention or security. cloud

Shared contextual model

Relationships, issues and recent changes reduce repeated raw-object exploration. MCP builds distinct read-only and full catalogs rather than relying on a prompt not to mutate. Investigation/apply transports are separate; the apply catalog removes deletion and Helm-management tools. mcp

History with explicit gaps

SQLite uses WAL/cleanup and distinguishes corruption from locking/permission failures; corruption is quarantined and unavailable SQLite can degrade to explicitly marked memory. PostgreSQL startup outages leave history unavailable and reconnect rather than silently pretending memory is durable. Observation-start timestamps bound claims about periods actually watched. These are good patterns, not tested disaster-recovery guarantees. manager sqlite postgres

Not a read-only dashboard

Full MCP and UI expose mutation workflows under the effective Kubernetes identity. The read-only endpoint excludes writes; the MCP read-only flag does not disable UI writes. Opt-in MCP exec can change containers/external systems and returns unredacted output. Destructive-tool annotations are not a universal server-enforced human approval boundary for arbitrary clients. readme mcp exec

Architecture

Kubeconfig/ServiceAccount → watchers and shared cache → contextual permission/read layer → REST/SSE/MCP → React or agent.

Optional Cloud hub → authenticated outbound WebSocket/yamux transport → the same HTTP router.

Startup composes services in internal/app; internal/server integrates HTTP, internal/k8s collects state, pkg/auth discovers permissions, and internal/mcp exposes tools. Domain modules handle integrations/storage. Shared Go/UI packages offer reuse seams, but the large routing module and many authorization-sensitive integrations increase maintenance complexity. The efficient shared cache is also a privileged aggregation boundary. server permissions tunnel

Security, Privileges and Privacy

Local default versus shared exposure

CLI defaults to loopback. Docker/Helm shared listeners need an explicit network/auth decision: authentication defaults to none, so reachable clients act with Radar’s Kubernetes identity. Host validation, CORS and origin/fetch-metadata checks address browser threats; headerless non-browser requests are intentionally supported. CORS is not authentication. Do not expose an unauthenticated ingress based on a read-only assumption. listener origin authdoc

Proxy mode accepts forwarded identity headers; the proxy must strip supplied identities and be the only backend path. Normal auth deployment grants users/groups impersonation and SubjectAccessReview creation. Reserved-identity filtering is useful, but a compromised Radar process remains a high-value cluster principal. middleware rbac

Per-user RBAC is not exact read parity

Namespace discovery checks cluster-wide pod listing, then pod/deployment listing per namespace. Ordinary namespaced cached reads use that visibility: a pod reader can see ConfigMaps even where direct Kubernetes authorization would deny them. Secrets, selected sensitive kinds and cluster-scoped resources have tighter gates; writes use caller identity. This is documented behavior, not a newly demonstrated bypass. Separate namespace-scoped instances are a better fit for strict tenant boundaries. permissions authdoc

Raw PromQL/aggregate metrics use broad pod visibility for authorization but Radar’s credentials to query Prometheus; that backend still needs tenant isolation. Documentation also acknowledges limited matching-information disclosure through narrowed relationship results involving hidden cached objects. authdoc

Render privileges rather than trusting one checkbox

Default Helm values disable general Secret reads, Helm writes, pod exec, port forwarding and self-upgrade; pod logs and broad inventory remain. Traffic integration has its own certificate-secret grant. Auth or Cloud automatically enables cache Secret reads even when rbac.secrets is false. Enabling Helm writes without auth adds create/update/patch/delete across all API groups/resources. values rbac

Cloud is off by default. When enabled it tunnels the router, including SSE, exec and MCP, and advertises cluster/installation metadata. Tunnel requests carry a private in-process marker; Cloud auth refuses spoofed forwarded identities on the ordinary TCP listener. That is concrete hardening, but Cloud is still a remote authority/data recipient. Avoid insecure TLS bypass. User-token mode has separate chart checks requiring verified transport and different RBAC assumptions. Reconnection uses bounded exponential backoff. cloud tunnel middleware rbac

Agent context is sensitive

MCP withholds Secret value fields and AI context uses key/shape heuristics. Regex cannot guarantee removal of arbitrary credentials, business data or unusual encodings. Read-only tools prevent mutation through that catalog, not disclosure to the model provider or prompt injection from logs/resources. Opt-in exec returns raw output. readme redact exec

Claude’s safeguarded adapter disables built-in tools and constrains MCP. Codex requests read-only sandboxing and constrained configuration. Cursor/OpenCode full-local paths retain other configured tools and auto-approve requests: Radar’s read-only catalog does not bound their authority. Approve the particular adapter, provider and tool setup, not merely the Investigate button. claude codex cursor opencode

Local-first does not mean unconditional no-egress

Usage reporting is consent-controlled and off unless opted in; payloads contain counts/coarse cluster facts. Release checking has vendor/GitHub endpoints. Registries, metrics, OIDC, Cloud and agents introduce further destinations. No egress capture or airgap test was performed. usage payload version

Authenticated image inspection is documented to gate images by readable Pods, constrain credential use/connections and reject metadata/link-local destinations. Private addresses remain allowed for enterprise registries; local unauthenticated credential discovery is broader. Redirect/credential-provider behavior was not exhaustively traced; SSRF resistance was not proven. authdoc

Persistence and Recovery

Memory timeline is bounded and restart-volatile. The chart defaults persistent-backend retention to 168 hours; SQLite needs writable persistent storage with the hardened container filesystem. Configure retention/capacity/backups together. This is observed history, not a cluster backup or complete audit system; downtime and database failures leave evidence gaps. values manager sqlite

Investigation transcripts have separate SQLite persistence with private file creation, transactional event/summary boundaries and degraded-state reporting for disk/queue failures. These are sensitive records requiring access controls and deletion policy. No restore, crash injection, migration or multi-replica consistency test was run. aistore

1. Pilot locally with restricted kubeconfig; effective authority includes credential-plugin behavior.

2. Start agents on the read-only MCP endpoint; separately restrict UI/Kubernetes writes and exec. Prefer safeguarded adapters over full-local auto-approval.

3. For shared use, configure TLS/OIDC or an isolated trusted proxy. Scope cache/service-account namespaces and inspect rendered Secret, impersonation and Helm grants.

4. Keep Cloud/telemetry off unless approved; review registry/metrics/provider egress separately and never bypass TLS verification in production.

5. Choose durable history deliberately, protect transcripts, test restore and validate with representative user identities before rollout.

6. Pin releases and independently verify distribution integrity. No installer/deployment was executed here.
