The README and feature guide describe floating bar islands, animated workspaces/window titles, an auto-hiding dock, launcher, quick settings, calendar, clipboard history, media controls, notification daemon, OSD, wallpaper and lock screen. These have corresponding Rust modules; this is substantive implementation, not a mock-up README. Visual quality and real-device behavior were not independently verified.

Its audience is ShojiWM users and developers exploring a native Rust animated desktop shell. Linux Wayland, layer-shell/session-lock support and the compositor's workspace/toplevel integration matter. There is no demonstrated X11, Windows or macOS support. Hyprland/Sway compatibility is not established by using Wayland: ShojiWM theme IPC, logout command and documented startup/keybinding integration are specific. Do not substitute it into another desktop on that assumption.

Key Features and Architecture

main.rs separates msg and preview modes from normal Shell startup. Normal startup installs IPC, theme sharing, notification popups, OSD and lock hooks, then creates bar/dock/wallpaper/panels per output. Components are organized by desktop surface rather than backend/frontend services; there is no web server or hosted account required by this repository's documented model.

  • Coordinated motion and colors: shared settings/theme signals drive Material color schemes and spring animations. wm.rs sends JSON theme.set roles to ShojiWM, reconnecting with a 500 ms to 30 s backoff and resending the latest scheme. This is a useful integration pattern, not a portable theme API.
  • Practical controls: qs_pages.rs includes Wi-Fi joining/password prompts and attempts to reconnect the previous network after failure. Bluetooth, audio and power controls are actual operations, not read-only status widgets. NetworkManager/polkit/system service policy ultimately determines permissions.
  • Integrated session UI: power_dialog.rs confirms logout/restart/power-off. Logout invokes shoji_wm --quit. Application launching and desktop actions in the dock use AntiWebUI app adapters; trusted desktop entries/helper PATH are execution inputs.
  • Observability: counted animation clocks, msg status and a CPU-report script offer useful diagnostics. They are not published benchmark results.

Security, Privacy and Failure Boundaries

IPC: local, but relies on the runtime directory

ipc.rs binds a Unix socket under XDG_RUNTIME_DIR, falling back to a predictable temporary-directory name if unset. There is no explicit peer-credential authorization or socket permission hardening in this file. A correctly private runtime directory is consequently important; the temporary fallback should not be treated as equivalent isolation.

A single listener thread performs an unbounded blocking read_line before dispatching. A client that connects and never sends a newline can monopolize the command listener; a huge line can grow memory. The two-second timeout covers the UI reply, not socket reads. This is a static local availability finding, not a tested exploit or remote network vulnerability. Commands include quit and theme changes but no unlock command. Arbitrary shell commands are not accepted by the IPC parser.

Locker: correct protocol intent, important assurance gaps

lock.rs uses ext-session-lock through AntiWebUI, closes panels, shares password state across outputs, authenticates off the UI thread and hooks logind lock/sleep events. The documented recovery says ShojiWM remains locked if the shell dies and another locker such as swaylock can take over from a TTY. This is a compositor/dependency claim, not an independently verified recovery guarantee.

pam.rs calls pam_authenticate for the login service, not account/session management. Its conversation supplies the same password to all hidden prompts, so arbitrary MFA/challenge flows are not established. The username comes from USER in user.rs, not a UID-derived account lookup. Password buffers use String/CString and ordinary overwrite loops; that is not proof of compiler-resistant zeroization, and clearing UI strings does not guarantee all copies disappear. There is no visible sleep-inhibitor/locked-ack handshake in the shell's sleep callback; whether the dependency guarantees suspend ordering remains unverified. These are review questions before relying on it as a security boundary, not a demonstrated bypass.

The fixed preview password is restricted to the separate preview path; it is not evidence of a production backdoor. Crucially, development docs explicitly warn that preview clicks can change real network/Bluetooth/audio services and clipboard contents. Offscreen rendering is not a safe sandbox. No previews were run.

Clipboard, notifications and credentials

clipboard.rs lists cliphist entries, keeps previews in memory and decodes image contents to runtime-directory files. Despite thumbnail-oriented wording, decode writes the clipboard image data to disk for display. There is no shell-level secret exclusion/encryption policy. The app expects an external wl-paste --watch cliphist store recorder; removing the shell does not erase that history or stop a separately configured recorder.

Copy/delete use fixed sh scripts with the entry supplied as quoted positional argument $1, not interpolated command source—a meaningful distinction from shell injection. Deleting an image removes its local cached file, but external history changes do not imply automatic cache cleanup. XDG_RUNTIME_DIR fallback again weakens assumptions about private, session-lifetime storage.

notify.rs tries to own the notification service and logs failure if another daemon owns it. It shows up to three popups and exposes notification history through the service adapter; persistence/retention limits inside AntiWebUI were not verified. Notification image hints accept local absolute/file paths and image bytes, putting sender-controlled content through image decoding. No HTML/JavaScript execution sink was established in the inspected UI. Do not run it alongside an existing daemon expecting both to receive the same notifications.

Wi-Fi passwords pass from UI signals to the network adapter; their final storage and authorization belong to NetworkManager/dependencies and were not audited. No direct telemetry uploader or remote API client was identified in the inspected shell code. That is not a guarantee of zero network traffic: helpers, launched applications, media artwork loading and dependencies have their own behavior.

Performance: evidence versus claims

The README claims no frames when nothing moves and “0% CPU when idle.” ui.rs does condition ticker continuation on live/running state, and exposes an active-clock count. This supports a deliberate event-driven design, not a measured universal zero-CPU claim: clocks, service events, animations, media and reconnection can still wake work.

There are no reviewed reproducible measurements for CPU, RSS, GPU, startup, multi-monitor scaling or long-running clipboard/history size. The diagnostic script samples process/thread counters, perf and D-Bus profile traffic and writes local reports. Its optional sudo mode refreshes credentials and also uses sudo chown on perf output, so “only perf runs under sudo” in the docs is imprecise. Reports can expose local process/bus details; review before sharing. The script was not executed.

Before any adoption, preserve existing compositor config, notification/clipboard startup entries, locker and working binary. Merge startup/keybindings rather than replacing a config. Keep a known-good separate session and TTY recovery route; validate lock/refusal/suspend/crash takeover before enabling automatic locking. No installation or configuration changes were made here.

settings.rs reads XDG_STATE_HOME/shoji-bar-4/settings.json (HOME fallback, then /tmp), defaults malformed/missing values, debounces changes by 400 ms and writes a neighboring partial file before rename. This avoids partially replaced JSON, but errors are ignored, there is no fsync guarantee, no schema version/migration/backup and unknown keys are lost on a subsequent save. Manual edits are not shown being watched/reloaded live. Invalid files may silently become defaults and later be overwritten. Multiple display instances share this state location.

user.rs copies avatars and removes older avatar-* files; reset removes the configured avatar path without checking it is inside the managed directory. Hand-edited avatar settings should therefore not point at a valued original file. Preserve the state directory separately from source/build updates.

Rollback means restoring the prior executable/revision and compatible saved state/config, not merely pulling an old commit. Uninstall has no dedicated script: remove only this shell's startup/keybindings, restore the prior notification/lock components, and then remove its source/build artifacts if desired. State, reports, runtime clipboard images and the external cliphist database have separate lifetimes; erase only deliberately. Do not terminate a locked shell assuming that will safely unlock the session.
