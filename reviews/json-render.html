Key points

What matters most, in order.

Catalog prompts are not enforcement

Generic multi-component propsOf validation accepts unknown prop records rather than discriminating by component type. Structural validation is separate and not a complete graph or security check.

2

Actions and URLs remain your responsibility

State watchers and registered handlers expose real capabilities. Require server-owned authorization and confirmation, validate resolved URLs, and keep model state separate from privileged business state.

React can hide failed elements; Chat SDK streaming can leave a partial message visible when final validation fails. Budget parsing, rendering and provider spend, and design explicit recovery.

Catalogs are a vocabulary, not guaranteed model output

The README claims output matches the schema “every time.” Actual catalog validation calls a generated Zod schema, but its propsOf implementation deliberately returns z.record(z.string(), z.unknown()) when there are multiple component prop schemas. It does not build a discriminated union matching each element type to its props. A catalog with one props schema behaves differently. Known component names can be enforced by the generated enum, but only if validation is actually called; a prompt is not enforcement.

The React schema describes root/elements and optional visible/repeat/slots, while runtime specs also use state, on and watch. Its ordinary Zod object generation can strip fields outside that declared shape. Treat validation output as a tested integration contract, not an interchangeable full-runtime spec. Validate each selected component's resolved props explicitly, with separate rules for expression syntax and trusted state-derived values.

validateSpec checks roots, child references, visibility forms, repeat contexts and misplaced fields. It does not take a catalog and therefore cannot reject unknown component types or enforce per-component prop schemas. Its ancestor guard avoids looping during one structural traversal but does not report cycles as invalid. A self-referencing child graph needs explicit application rejection before recursive rendering. These are static deductions, not executed exploit demonstrations.

Streaming and repair are useful but tolerant

SpecStream buffers newline-delimited JSON patches, mutates a spec and emits shallow snapshots. Malformed lines can be ignored; the parser checks for op/path rather than validating a complete patch schema. Replace intentionally sets missing targets for streaming tolerance; this is not strict RFC 6902 validation. The compiler retains its buffer and applied-patch history without an application budget. Bound bytes, line length, patch count, tree depth, repeat size and elapsed time.

Auto-fix can move misplaced fields and prune dangling references; structured fix details mark lossy pruning. Retrying while preserving content is different from silently accepting a pruned result. React hooks provide abort/error handling; missing components/children can disappear with console warnings, and per-element error boundaries render nothing after failures and reset on a changed reset key. None of this guarantees a complete or semantically correct result.

State and actions are real application capabilities

React rendering resolves state/item/template/conditional expressions and calls registered computed functions. Bindings write state; repeated children inherit item scope; watchers skip initial mount and dispatch when watched values change. Registered functions/directives remain trusted executable code, not sandboxed model expressions.

The action provider implements state mutations and other built-ins, then dispatches registered handlers. Confirmation is driven by the supplied binding; it is not server authorization. The registry helper forwards params to action functions without automatically parsing them against catalog action schemas. Watchers and chained callbacks also mean “the user clicked a button” is not a safe universal assumption.

Keep principal identity, tenant IDs, access policy and secrets out of writable model state. On the server, revalidate action params, authorize every resource, protect against CSRF/replay as applicable, rate-limit and use idempotency keys for side effects. Require server-owned confirmation policy for costly/destructive operations; an absent model-supplied confirm flag must not bypass it. Visibility and disabled controls are presentation, not access control.

Architecture and Trust Boundaries

  1. Trusted developer catalog/registry → generation prompt. Catalog descriptions help the model select a vocabulary. User messages, retrieved content and tool output can still inject instructions; the model must not decide its own permissions.
  2. Untrusted JSON → validation → resolution → rendering. Separate shape, graph, expression, component-prop and policy checks. Revalidate resolved URLs and action parameters; a syntactically valid state reference can resolve to an unsafe value. Render only a minimal allowlisted registry.
  3. Rendered component → browser/network/host side effect. Ordinary React text escaping is useful, but URLs and custom components are different sinks. shadcn components pass image sources and link hrefs onward; email and image likewise accept URLs. The shared layer is not a universal URL sanitizer. Allowlist schemes/origins, block private-network destinations for server-side fetchers, constrain redirects and isolate remote asset retrieval. Browser images can leak requests; server-side rendering dependencies may fetch resources. Actual SSRF exploitability was not tested.
  4. MCP app HTML → host iframe. MCP server registration validates through catalog.validate, but inherits that validator's limits. Its advertised CSP allows all HTTPS resource and connection domains, not an application-specific allowlist. buildAppHtml escapes title but deliberately inserts developer-supplied head/CSS/JS. Those are trusted bundle inputs, never places to insert model text. Host isolation and user consent do not replace backend authorization.
  5. Prototype/path and resource handling. Core mutable JSON-pointer helpers reject __proto__ segments and use own-property/dense-array handling. This is welcome hardening, not a blanket guarantee for every setter: immutableSetByPath is a separate implementation. Reject dangerous path segments at ingress and review each state adapter. No working prototype-pollution exploit is claimed here.

Platform Adapters and Recovery

Shared vocabulary does not mean identical component sets or validation behavior. PDF, email, image, terminal, video and 3D adapters have different resource and output semantics; choose a target-specific catalog. Routing integrations and code generation expand the trusted surface and deserve a separate deployment review.

The new Chat renderer is a notable contrast to generic validation: it resolves elements and checks each component's props, plus structure and optional platform limits, before final card output. streamCard posts partial cards and throttles edits (500 ms default), then validates the final card. If final validation or posting fails, an already-visible partial message can remain. The caller must handle retries, platform 429s, cleanup/error edits and duplicate-post avoidance; the helper does not provide a durable delivery transaction.

Provider Data and Cost Flows

The chat API example sends converted conversation messages into an AI SDK agent. Its agent uses a configurable Gateway model and public-data tools, including a web-search provider, with a five-step stop condition. Prompts, history and tool results therefore leave the application under the selected provider's terms. No inference is required just to render an existing spec.

The example rate limiter uses Upstash Redis when configured but allows requests when Redis is absent. The shown route has no user-authentication check and trusts a forwarded IP header; safe interpretation depends on a trusted reverse proxy. A duration limit and five tool steps are not per-user monetary budgets. Add authenticated quotas, input/output limits, concurrency caps, provider spend limits, request cancellation and retention rules. Keep Gateway and Redis credentials server-side.

The optional experimental evaluator explicitly posts evaluation requests to Vercel AI Gateway using a supplied API key/model. Do not describe the whole repository as offline because normal rendering can be offline. Candidate evaluation is a separate opt-in data/cost path. Provider privacy, actual token costs and hosted availability were not tested.
