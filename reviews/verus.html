Specifications, proofs and executable code are distinct

Function modes are spec, proof and exec. Specification functions express mathematical properties; proof functions establish logical facts; exec functions are compiled. Both spec and proof are ghost code. Mathematical int/nat are not machine integers, and ghost values cannot simply leak into executable computations. Arithmetic safety obligations in exec code must not be confused with mathematical expressions that have unspecified values outside their useful domain. Modes, ghost/exec

Variable modes are a separate distinction: exec, ghost and tracked. Tracked resources are erased like other ghost state but retain ownership discipline, supporting permission/token reasoning rather than freely duplicable mathematical facts. Ghost/Tracked wrappers contain PhantomData in the actual builtin definitions, not runtime copies of the represented proof data. Variable modes, builtin

Contracts need deliberate coverage

The binary search in examples/vectors.rs requires a sorted vector and the existence of the searched-for value. Its successful proof would not specify an absent-key API. Its loop carries quantified invariants and a decreases measure. The reverse example uses a ghost snapshot, multiple quantified invariants and an explicit trigger. These are useful, concrete demonstrations of the work needed to connect an efficient implementation to a mathematical specification. Examples

Recursive spec/proof functions need termination reasoning for consistency. Executable termination is subtler: the guide calls its default decreases checking a lightweight lint conditional on callees terminating, not a complete termination guarantee; exec nontermination is allowed. Do not advertise verification as universal liveness, deadlock freedom or termination. Termination

Supported Rust and adoption cost

The feature matrix (itself dated 2026-05-13) lists ordinary functions, structs/enums, shared/mutable references and many traits as supported. It lists async/await, function-pointer types, Pin, hardware intrinsics, printing/I/O, custom Drop and transmute as unsupported; floating point, pointer operations, iterators, dyn traits and multi-crate integration have partial support. This is a documented snapshot, not an independent exhaustive compatibility test. Existing applications often need a verified core plus unverified integration boundaries. Feature matrix

Budget for writing models/contracts, identifying loop invariants, proving helper lemmas, managing quantifier triggers and reveal/fuel choices, and adapting proofs after dependency or solver changes. Timeout/unknown is not a counterexample, and more solver budget is not a substitute for a missing invariant. The repository's examples, guide, negative tests and libraries are meaningful maturity signals; they do not establish a predictable proof-to-code ratio or maintenance cost. No proof-effort benchmark was run.

vstd covers collections, arithmetic, raw memory, interior mutability, atomics and concurrency helpers; examples extend to linked structures, state machines and a cuckoo hash table. That is substantially more useful than a minimal syntax demo. Review the exact abstractions used rather than extrapolating to full Rust ecosystem coverage. vstd, examples, tests

The driver uses rustc expansion/type information and lowers HIR through rust_verify into VIR. The vir crate handles well-formedness, mode checks, simplification, recursion and verification-condition translation; SST removes expression/statement nesting before AIR. The air crate manages SMT processes, resource limits and result interpretation. Compilation is a distinct path with ghost erasure and ordinary Rust code generation. The decomposition is a good maintainability feature, but each translation is a potential semantic correctness boundary. Architecture, driver, verifier, modes

The inspected solver result code distinguishes unsat, sat, unknown and cancellation; it is not merely searching the log for the word “verified.” Nevertheless, this review found a solver-response-based pipeline, not evidence of an independently checked end-to-end proof certificate for the generated executable. Solver correctness and faithful encoding remain trust assumptions. cvc5 is described as experimental, and is not an automatic independent cross-check of every Z3 result. Trust boundaries

  • admit and assume: the frontend lowers admit to an assumption of false; assume inserts the supplied proposition as an assumption. An admit is a proof hole, not evidence. A contradictory assumption can justify arbitrary conclusions. Lowering
  • external_body / axioms: a proof function with an unverified body can introduce an axiom; an exec function with external_body has an assumed contract rather than a verified implementation. assume_specification and external function specifications likewise move obligations into the trusted boundary. Trust guide, assumed specs
  • external is different: ignoring a function does not itself make that function callable from verified code with arbitrary guarantees. A trusted wrapper often supplies the bridge. Ignored trait implementations can still affect rustc's reasoning, including Send/Sync. Trust guide
  • Trait and library assumptions: unchecked external trait specifications can constrain all implementations, including future unverified ones. vstd documents an obeys_* pattern to make such conditions explicit. “Standard library” does not mean “every implementation proved”: vstd combines proved lemmas, axioms and external interfaces. Seq has both lemmas replacing older axioms and a remaining axiom declaration; raw pointers use an abstract provenance model and tracked permissions. Traits, Seq, pointers
  • Unsafe and FFI: absence of the unsafe keyword is not a sufficient audit for Verus. Its memory-safety guide explains APIs whose safety depends on verified preconditions rather than defensive checks for arbitrary unverified Rust callers. Foreign code, OS interfaces and unverified dependencies need an explicitly reviewed specification/implementation bridge; this review establishes no blanket FFI guarantee. Memory safety, unverified calls
  • Erasure and build parity: the code/configuration actually compiled must match the verified exec behavior. The guide explicitly warns that conditional executable code using verus_only can break guarantees. Include features, target architecture, dependencies, compiler and solver versions in the verification record.
  • Remaining TCB: macro expansion, rustc integration, VIR/AIR transformations, models/axioms, solver, ghost erasure, rustc/LLVM, linking and runtime/environment assumptions. This is not a fully verified compiler stack. Application claims also require adequate specifications for I/O, security policy, failure handling, side channels and concurrency progress; those are not implicit outputs of a successful proof.

Known soundness reports: a real operational consideration

Public issue data retrieved on 2026-11-20 includes open #3566, reporting that a use import inside a tokenized state-machine transition can rebind pre or a field type and permit proving false. The report includes purported verifier output; this review did not run it or establish applicability to this exact SHA. It is a reason to review the feature's issue/fix status before relying on it, not a reproduced finding. Issue #3566

The same snapshot shows closed reports #3565 (transition-let side effects omitted from a relation), #3564 (forging generated instances from within the macro body), #3502 (dyn supertrait positivity) and #3498 (recursive call type arguments in decreases checking). These document the kinds of subtle bugs a verifier must exclude. Closed status alone is not proof that a chosen binary contains the fix; verify its commit ancestry and regressions. No claim is made that all these closed issues affect the reviewed revision. #3565, #3564, #3502, #3498

Privacy and supply chain

This is primarily local developer tooling, not a hosted application needing an auth/CORS/database deployment review. The inspected solver interface uses local process pipes; cloud submission is not necessary for the basic verification pipeline. That is not a comprehensive no-telemetry audit. The separately linked browser playground entails sending source to another service; do not assume local-processing privacy there.

Build/install executes compilers, Cargo build scripts/procedural macros and downloaded tooling. Treat both the verifier supply chain and code being verified as executable development inputs; verification is not a sandbox. The Z3 helper downloads a versioned ZIP over HTTPS and unpacks/copies it without a visible checksum verification step. Installation also describes removing macOS quarantine and a rustup shell installer. None was executed in this review. Use isolated builds, explicit artifact provenance and pinned dependencies; examine scripts before adopting them. Z3 helper, installation

The workspace manifest itself flags older transitive dependencies in some auxiliary tools. That is a maintenance signal, not evidence of an exploitable vulnerability in the verifier: no advisory matching or reachability assessment was performed. Logs of VIR/AIR/SMT and diagnostics can contain source/specification details; treat CI logs and proof traces as code-sensitive artifacts. CPU/memory exhaustion and long solver runs also matter when accepting untrusted projects.

Evaluation gate

Choose a bounded component with a meaningful contract; enumerate all trusted functions/axioms and unchecked callers; prohibit admits and unreviewed assumptions; verify specification completeness with independent review and negative tests. Record the exact executable build configuration and proof-tool versions. Re-run proof/regression tests on upgrades and explicitly check soundness fixes affecting used features. Keep ordinary testing, fuzzing and integration/security review: they address gaps in specifications, tool implementations and external systems.
