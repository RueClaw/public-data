Key points

What matters most, in order.

1

The host writes the action space

The model answers boolean, choice or score questions; code owns transitions. Unknown choice labels are rejected, but allowed actions still require host-side authorization.

2

Replay takes saved states

Recorded steps do not call the model or rerun transitions. Forking resumes execution; definition changes are noted, not an integrity or reproducibility guarantee.

3

Promising evidence, unresolved limits

Open PRs address one-option picks, 64-question limits and missed context-overflow errors. Reported 94.6–95.0% legal-judge agreement comes from previously seen private cases, not a held-out public benchmark.

Typed questions and budgeted views

Code builds finite menus with stable keys, duplicate checks and priority-based truncation. Requests are batched by estimated token size; recognized overflow shrinks custom views by 0.7 for up to three attempts. Step limits are optional, not a total spend cap.

Provider compatibility

Inspected code matches the gaps reported in open PRs #40–42: single choices still reach providers, question count is not capped at 64, and some local-server overflow spellings are missed. Reports were not reproduced here.

Evaluation caveat

The rubric minimum of P(meets) and 1−P(misses) is an upper bound on their conjunction, not a calibrated joint probability. Require unseen human-labeled cases and false-pass analysis.

Domain → state → typed questions → bounded view → pi-ai classifier → validated answers → trusted transition → trace. CLI artifacts and a separate viewer make each run inspectable.

Execution and privacy

Hosted providers receive selected state and images. Full-state traces and request logs may retain sensitive documents; no general redaction/encryption layer was observed. Native document converters run with process privileges. The viewer binds loopback without application authentication; domain modules are trusted code.
