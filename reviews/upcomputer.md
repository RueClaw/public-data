## Verdict

⚠️ **Interesting — a substantial agent workbench, but pilot with deliberately reduced authority.** The durable orchestration graph, task reconciliation and provider-neutral handoffs are compelling. Full-access agent defaults, control-enabled desktop defaults, persistent browser credentials and opt-out telemetry mean this is not a safe-by-default sandbox or a zero-egress private assistant. Prefer a dedicated account or disposable machine and explicitly supervised threads before connecting important repositories or sessions.

## What It Is

The canonical project calls itself **Up.computer** and explicitly identifies as a fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code). It retains upstream package names, protocol identifiers and substantial runtime/release infrastructure. Its distinguishing workflow is conversation → task → saved worker → durable result, alongside the ordinary interactive coding-agent interface. It can commit, push, publish repositories and create pull requests: those are real external write capabilities, not merely suggested commands.

The README names Codex, Claude Code, Cursor, Grok Build, OpenCode, Antigravity, Pi and registry/custom ACP agents. Codex and Claude are enabled by default; the others require configuration. The implementation also contains additional upstream adapters; presence of a package is not proof that every released build supports every provider identically. React Native mobile code and the Connect relay remain in-tree, but the README says mobile is not published and the UpComputer relay is not deployed. Generic remote-access documentation describes more than that declared release state. [Evidence: [README.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/README.md), [docs/operations/upcomputer-connect-setup.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/operations/upcomputer-connect-setup.md)]

## Key Features and Architecture

### Durable app state, not just terminal multiplexing

The V2 model separates AppThread, Run, ExecutionNode, ProviderThread and ProviderSession. ContextTransfer records lineage while ContextHandoff materializes portable history. Stored normalized events have monotonically increasing sequence numbers; clients read a snapshot at N and stream later events. The event-store API records pruning boundaries, so consumers must resynchronize rather than assume an infinite replay log. This is a useful separation between provider-native runtime state and application-owned state. [[docs/orchestration-v2/core-graph-and-data-model.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/orchestration-v2/core-graph-and-data-model.md), [apps/server/src/persistence/OrchestrationEventStore.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/persistence/OrchestrationEventStore.ts)]

### Workers have real ownership and recovery logic

TaskAgentService uses persisted run ownership, finalization claims, run/thread reconciliation and explicit stopped/failed/interrupted outcomes. Startup preserves a still-active V2 run rather than indiscriminately restarting every worker; incomplete finalization can resume, while missing threads and start timeouts become actionable failures. This is stronger than “repeat a prompt until done.” It still does not establish exactly-once external side effects: an agent may have pushed, sent, or changed a website before losing its response. Inspect actual outcomes before retrying. [[packages/tasks-server/src/agents/TaskAgentService.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/tasks-server/src/agents/TaskAgentService.ts)]

### Portable context is bounded, not lossless runtime migration

Provider switching selects intact messages, original/recent requests and useful activity under a budget, retaining references to omitted history. It does not transfer reasoning, tool-call state or attachments. The documented initial history cap is 16,000 tokens, with conservative byte-based accounting and provider-capacity fallbacks. Keep essential constraints explicit when switching providers. [[docs/user/portable-handoffs.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/portable-handoffs.md)]

## Permissions, Computer Control and Isolation

**New threads default to Full access.** This is explicit both in documentation and DEFAULT_RUNTIME_MODE. Supervised, Auto-accept edits and provider-specific Auto modes exist, and managed policy can cap modes, but enforcement differs by provider. A thread/worktree is an organizational boundary, not an OS tenant or secret boundary. Do not assume a project selection prevents tools from reading the rest of the account, invoking network clients, or affecting other repositories. [[packages/contracts/src/providerPolicy.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/contracts/src/providerPolicy.ts), [docs/user/permission-modes.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/permission-modes.md)]

**Native computer-use defaults are unusually permissive:** enabled=true, mode=control, requireActionApproval=false, allowedApps=[]; coordinate fallback is false. The policy rejects unknown tools, disabled control, disallowed apps, Plan-mode actions and sensitive-app names. An app allowlist also prevents whole-screen captures lacking an app target. These are useful restrictions, but the sensitive-app test is based on the supplied app name/bundle identifier, not comprehensive identification of password/payment content in ordinary browser windows. Empty allowedApps means unrestricted app selection, not deny-all. [[packages/computer-use-contracts/src/settings.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-contracts/src/settings.ts), [packages/computer-use-server/src/computerUse/ComputerUsePolicy.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/computerUse/ComputerUsePolicy.ts), [packages/computer-use-server/src/computerUse/SensitiveApps.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/computerUse/SensitiveApps.ts)]

**Approval settings fail closed on the inspected MCP path, rather than opening a confirmation UI.** ComputerUseMcpTools resolves the calling thread on every call; a missing thread mode or Supervised thread is denied. If action approval is required, actions are refused because this adapter cannot solicit approval. Plan allows observation only. This is an important distinction: the existence of an “Action approvals” setting does not imply a working per-action consent dialog for agents. The sidecar starts on demand and is stopped with the service. OS accessibility/screen-capture permissions and actual cross-platform behavior were not exercised. [[packages/computer-use-server/src/mcp/ComputerUseMcpTools.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/mcp/ComputerUseMcpTools.ts), [packages/computer-use-server/src/computerUse/ComputerUseService.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/computerUse/ComputerUseService.ts), [packages/computer-use-server/src/computerUse/ManagedComputerUseSidecar.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/computerUse/ManagedComputerUseSidecar.ts)]

Managed browser automation uses a persistent default Chrome/Edge profile shared by the preview host and settings. Cookies and logged-in sites are therefore authority available to automation; it is not an ephemeral per-task isolation container. Browser reset removes that profile. There is no evidence in this sampled browser-lifecycle module of a universal outbound/private-network sandbox. Use a separate low-privilege browser identity and treat screenshots/page content as sensitive provider input. [[packages/computer-use-server/src/browser/BrowserAutomationService.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/computer-use-server/src/browser/BrowserAutomationService.ts)]

## Authentication, Network and Credential Boundaries

The backend is not merely an unauthenticated localhost RPC service. EnvironmentAuthPolicy distinguishes desktop-managed-local, loopback-browser and remote-reachable modes; bootstrap uses desktop handoff or one-time tokens, followed by cookie, bearer or DPoP sessions. Session code handles expiry/revocation; RpcAuthorization maps operations to scopes, including filesystem, terminal, provider-management, settings and maintenance. Cookie-authenticated requests have origin checks. Protect reverse-proxy forwarded-host handling and use TLS or a private encrypted transport for remote access; token auth alone does not encrypt LAN HTTP. [[apps/server/src/auth/EnvironmentAuthPolicy.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/auth/EnvironmentAuthPolicy.ts), [apps/server/src/auth/EnvironmentAuth.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/auth/EnvironmentAuth.ts), [apps/server/src/auth/SessionStore.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/auth/SessionStore.ts), [apps/server/src/auth/RpcAuthorization.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/auth/RpcAuthorization.ts)]

These are meaningful access controls, not proof of hostile multi-user isolation. Terminal/full-access agents still execute as the environment user. Pairing a device or granting broad guest scopes should be treated as delegating machine authority. The direct-pairing/SSH/Tailscale paths are distinct from the hosted Connect offering; do not assume the latter is operational merely because upstream docs describe sign-in and machine limits. No live auth, proxy, relay or tenant-isolation test was conducted.

Provider login may use existing CLI credentials or built-in flows (including ChatGPT/Cursor/Antigravity); selected prompts, repository contents, images and tool outputs go to the chosen provider as needed. Credential fields are redacted in settings views and moved into ServerSecretStore. **That store is raw local binary files protected by 0700-directory/0600-file permissions, not encrypted-at-rest storage.** It does not isolate secrets from arbitrary processes under the same account. The optional 1Password resolver keeps references in settings and resolves on use; supplied values still reach their intended consuming tools/providers. Agent secret requests avoid chat display, but command-consumable secrets can be materialized in private files for about 24 hours. [[apps/server/src/settingsSecrets.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/settingsSecrets.ts), [apps/server/src/serverSettings.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/serverSettings.ts), [apps/server/src/auth/ServerSecretStore.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/auth/ServerSecretStore.ts), [apps/server/src/secrets/SecretRequests.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/secrets/SecretRequests.ts), [docs/user/secrets.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/secrets.md)]

## Privacy and Costs

“Every chat stays on your computer” is best read as local application-history storage, **not no data leaves the device**. Model execution necessarily uses the configured provider; optional remote access and diagnostics introduce other recipients. AnalyticsService defaults T3CODE_TELEMETRY_ENABLED to true and sends to PostHog. The telemetry document describes hashed account/install identifiers, provider/model/mode, token totals, usage events and error categories; it explicitly excludes prompt/response bodies and raw provider events. Hashing is pseudonymization, not absence of tracking. Relay traces may go to Axiom, and configured OTLP receivers add another export surface. Opt out before launch if that is required. Static inspection did not independently prove every telemetry field excludes sensitive content. [[apps/server/src/telemetry/AnalyticsService.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/telemetry/AnalyticsService.ts), [docs/user/telemetry.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/telemetry.md)]

The app's MIT source does not make inference free. Existing subscriptions, API keys, rate limits and provider terms still apply; workers/schedules and ancillary title/commit/PR generation consume resources. Usage reports are API-equivalent estimates rather than invoices. Documentation explicitly excludes some Codex/Claude ancillary text generation and lacks some incomplete Grok records; provider-specific history/account APIs determine coverage. Do not treat that dashboard as a complete hard spending cap. Self-hosting the optional relay also adds infrastructure/account operating costs. [[docs/user/usage.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/usage.md)]

## Persistence, Retention, Export and Recovery

SQLite uses WAL with synchronous=NORMAL and checkpoint_fullfsync: a deliberate throughput tradeoff. App-process crashes differ from OS crashes or power loss; post-checkpoint committed work may roll back after the latter. Database migration snapshots V1 using SQLite's backup API and publishes a completed V2 copy without replacing an existing V2 database. This is good migration hygiene, not a full-machine backup. [[apps/server/src/persistence/Sqlite.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/persistence/Sqlite.ts), [apps/server/src/persistence/initializeV2Database.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/persistence/initializeV2Database.ts)]

V1→V2 preserves conversation text and selected metadata but does not recreate old live sessions, approval history, checkpoints/diffs or all tool activity. Settings, attachments and workspace files remain shared between versions. The docs explicitly say there is **no whole-thread export command** and recommend a stopped-server userdata recovery copy. That copy alone is not a backup of external Git worktrees, provider-native histories, keychain items or password-manager accounts. Keep those dependencies in a tested restore plan. [[docs/user/thread-migration.md](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/docs/user/thread-migration.md)]

Worktree, browser-artifact and log age retention defaults are null; merge/delete cleanup defaults are false. This favors preservation, but screenshots, logs, cookies and old histories can accumulate. Cleanup has active-session/ownership and uncommitted-change protections; configure retention deliberately. Deleting a conversation is not evidence of erasure from provider logs, retained backups or independent browser state. [[packages/contracts/src/settings.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/packages/contracts/src/settings.ts), [apps/server/src/storageCleanup.ts](https://github.com/krl-gr/upcomputer/blob/89354bf98008cbfbe4a85e5bcc56770cd604696a/apps/server/src/storageCleanup.ts)]

## Practical Pilot / Self-Hosting Notes

Start local-only on an expendable developer account; explicitly set new threads to Supervised, disable native computer use unless necessary, and use an app allowlist/observe mode for initial evaluation. Do not weaken action approvals simply to silence the MCP adapter's refusal. Keep provider and browser accounts least-privileged, opt out of unwanted telemetry, and keep LAN/Connect/SSH exposure off until actually needed. An external OS/container/VM boundary is required when untrusted code must be contained; an agent permission label or worktree is not that boundary.

Before unattended workers: verify provider-specific approvals with harmless fixtures, review Git write authority, establish real billing limits, test interrupted-run reconciliation, and practice a full restore including external workspaces. Before upgrading: snapshot state with the server stopped and retain the prior known-good release, while recognizing shared settings/files complicate rollback.
