Key points

What matters most, in order.

1

A translation platform, not an ordinary app

ARM64 code, M2 device models and Metal graphics converge in a bare-metal UEFI runtime. NVIDIA support and macOS startup remain upstream claims, not independently reproduced guarantees.

2

Apple-like behavior is not Apple hardware trust

Stela implements its own SEP; it cannot execute Apple’s encrypted sepOS. Secure Boot is disabled, Wi-Fi keys are stored in plaintext, and exported machine state contains keys without export encryption.

3

Real recovery engineering; very early acceptance

Setup rechecks disk identity and supports interrupted updates, state backups and repair. There is no rollback, uninstall retains installed macOS/SEP state, and ordinary CI covers CLI tests rather than full hardware boot.

ARM translation with retained work

The README claims more than 3,000 AArch64 instruction encodings and x86-64-v2 compatibility. The compiler and engine are substantive implementations rather than just command wrappers; this review did not enumerate encoding coverage or establish instruction-level equivalence. Translation packs are keyed to translator identity, bounded, and recoverable on corruption; the installer provisions a spare so firmware need not grow files at boot. Translation-store management keeps one translator pack and a 64 MiB pipeline store, and prunes stale packs during repair/update. Checksums and identity binding provide corruption/staleness checks, not a reason to trust writable boot media against a malicious local actor.

Metal on supported NVIDIA hardware

The project advertises GTX 16/RTX 20 and newer, Metal3 and Apple7, with AIR shader IR translated toward NIR. Source includes a Metal service, resource/queue/lifecycle handling, a guest IOKit user client and Objective-C Metal bundle, plus Mesa/LLVM integration. GPU discovery carefully distinguishes an enumerated adapter from an initialized accelerator. Finding AMD/Intel vendor enums is not proof those GPUs work. No GPU, Metal conformance, application compatibility, or speed claim was independently tested.

Installer repair is more developed than the short README suggests

Creation rejects internal disks for the USB-erasure path, requires confirmation for destructive formatting, checks input placement, and rechecks selected-media identity before erase. Updates prepare new content first, activate recorded state, then prune old content; interrupted operations can be repeated. These are useful safeguards, not transactional protection against every power failure or wrong operator choice. The update implementation explicitly says there is no rollback.

Bare-metal trust, not a sandbox

Setup needs administrator/root disk authority and intentionally erases the selected USB. Installation also requires an empty target GPT partition and destructive restore choices. Boot requires Secure Boot off per upstream requirements. The boot program then manages physical memory, PCI/MMIO, interrupts, DMA, networking and storage. There is no SaaS login/RBAC/CORS boundary to evaluate; possession of the boot medium, local administrative access, guest driver interfaces, and firmware/device isolation are the relevant boundaries. Do not treat this layer as an isolation boundary for hostile guests.

The SEP is Stela's software, not Apple's hardware security

SEP firmware states that Apple's encrypted sepOS cannot run here: Stela implements its own SEP under an explicit TSS-free trust policy. Container measurements/signature evidence are not asserted to be Apple-verified boot. Key derivation likewise distinguishes its UID/GID substrate from Apple's secret hardware KDF. A familiar macOS login or encryption UI therefore must not be read as equivalent Secure Enclave, physical extraction resistance, or verified-boot assurance. This is an architectural distinction, not a claimed exploit.

Credentials and exports need physical protection

Wi-Fi setup masks interactive input but writes the passphrase in plaintext to EFI/stela/wifi.key on the ESP; the plan discloses this. The setup record keeps the SSID/country, not the password. Prefer a disposable isolated network or wired install rather than putting a valuable network password on a portable USB.

State backup exports NVRAM and the SEP area, including machine keys, with identity metadata and SHA-256. It creates a new file with mode 0600 on Unix; Windows inherits directory ACLs. It does not encrypt that export. Restore checks the original machine identity; this is not a general migration facility. Protect backup media separately and do not attach state backups to public issue reports.

Egress is real and not uniformly HTTPS

Install preparation obtains macOS images/catalogues, public archive keys, signing responses, and sometimes hardware firmware. Historical image metadata uses ipsw.me; public AEA keys use an HTTPS host/path allowlist and redirect restrictions. Boot-time ranged downloads use source length/entity-tag identity and manifest checks; HTTPS depends on admitted clock and entropy capabilities. Firmware recipes name linux-firmware and wireless-regdb sources.

However, setup TSS transport explicitly POSTs to http://{host}{path}, with the TSS host set to gs.apple.com. This exposes request metadata/identifiers to the network and lacks TLS server authentication on that leg. Recognizing a STATUS-prefixed response is not transport authentication; downstream ticket validation must be considered separately. This review did not prove ticket forgery or bypass.

No model provider, API-token billing, paid AI call, or model download is part of the inspected purpose. Costs are compatible hardware, storage, substantial downloads/build time and power; Apple software/service terms remain separate. No application telemetry sink was identified in sampled paths, but this is not a whole-program no-egress certification. macOS and applications have their own networking and account behavior, untested here.

Persistence and recovery

  • Installer USB: bootloader/configuration, setup record, restore bundles/media, firmware, translation/pipeline caches, and boot log. Some install flows stream images; larger media can hold the full image. The release history shows this policy evolving rapidly—do not assume every install is offline.
  • Installed system: macOS data plus NVRAM/SEP machine state on a recorded state partition or designated partition tail. Preserve both system data and machine keys; a state-only backup is not a full disk/user-data backup.
  • Boot logs persist on the USB and, when space permits, the machine-state area; log code spans firmware and native-driver phases. Logs can contain hardware identifiers, paths, addresses and download metadata. Inspect/redact before sharing; no comprehensive retention/privacy policy was established.
  • Uninstall removes recorded Stela USB artifacts and Wi-Fi key but keeps installed macOS, NVRAM and SEP state. Deleting the bootloader is not erasing the installation or its secrets; deletion is not secure sanitization.
  • Update handling distinguishes replacing Stela from replacing installer media; installed macOS has its own Software Update boot path. That code path is not proof arbitrary future macOS updates will work. Keep independent offline backups and a separate known-good boot environment.

Upstream minimums are x86-64-v2, UEFI with Secure Boot disabled, 8 GB RAM, supported NVIDIA GPU, USB at least 8 GB, and an empty GPT partition at least 60 GB. These are stated requirements, not a qualified-machine matrix. The Linux release targets glibc 2.35+, Windows is x86-64, and macOS CLI archives are universal. A Mac installer binary does not make this an Apple-silicon Mac virtualization product.

Source builds require Rust 1.99.1 per toolchain file, Clang/LLVM 21+ per README, and fetch/build substantial Linux, Mesa, LLVM and related sources. Git submodules are commit-pinned by the repository; Cargo.lock and firmware recipes improve reproducibility. A plain GitHub source ZIP omits submodule contents; the release workflow separately assembles corresponding source.

Release CI checks version/tag alignment, constructs guest app → EFI → CLI artifacts, checks embedded EFI bytes, packages license texts, and publishes SHA256SUMS. Those checks are positive evidence of packaging discipline, not a boot test or an independent signature. Actions use version tags rather than immutable action SHAs; macOS signing shown is ad hoc. No independent release-signing/attestation guarantee was established. Do not run build or installer commands merely to inspect this project on a daily-use machine.

Licensing

The LICENSE supplies GPL v2 text; NOTICE and workspace manifest explicitly choose GPL-2.0-or-later for own code. NOTICE distinguishes the Linux-containing stela.efi (GPL-2.0-only) from the CLI linking Apache-licensed crates (GPL-3.0-or-later); the EFI is aggregated inside, not linked into, the CLI. Other guest/maintenance components and third-party files retain their stated terms. Binary redistribution requires corresponding source, pinned dependencies/patches, scripts and notices—not just a link to a moving main branch. No code was extracted for this review.

macOS, Apple firmware/services and third-party firmware do not become GPL merely because Stela is. Evaluate Apple's applicable software-license and hardware restrictions before use; the README's legal disclaimer is not permission or legal clearance.

Evidence and limitations

Public GitHub metadata observed on 2026-11-11: repository created 2026-10-12; 389 stars, 11 forks, two open issues; last push 2026-11-11T20:06:48Z. Both v0.1.0 and v0.2.0 were published on November 11, with v0.2.0 at 15:51:23Z. The reviewed main commit is later than that release; README prose still says “as of v0.1.0.” Do not conflate main with the downloadable binary.

CI formats the workspace and runs CLI-only Clippy/library tests on Linux, Windows and macOS. It does not run the full translator/SoC/GPU/boot acceptance suite. The inspected revision's public CI was pending during observation, not a passing result. xtask check defines broader cross-target checks, and the tree contains substantial synthetic tests for installer recovery, TLS, device models and translation. Their presence is not proof they pass or cover real machines.

The v0.2.0 release notes include reverts of native transition optimizations after early watchdog resets and a hold on firmware MMIO admission pending proof. Issue #10 reports a boot page fault on Ryzen 5 1600/RTX 3060 Ti. This is a user report, not a reproduced diagnosis, but consistent with upstream's explicit hardware warning.

Verdict

The call, and why.

📚 Study

Substantial translator, hardware-model and GPU work, but not a dependable Mac replacement. Low boot-success warnings, bare-metal authority, plaintext Wi-Fi credentials and a software SEP keep this in disposable-lab territory. Static review only; no boot or performance claims reproduced.
