What matters most, in order.

A real shared design model

Humans and agents edit HTML frames through common actions; WebSocket rooms carry changes and presence. Inspect and screenshot tools support a concrete visual feedback loop.

2

Private canvas does not mean private media

Image and asset routes intentionally authenticate by possession of an unguessable ID. Production credentials stay plaintext unless encryption keys are configured; enabled PostHog replay can include prompts and comments.

Deployment defaults need work

The supplied Docker runtime disables Chromium sandboxing, and Compose persists the database but not default disk assets. Debounced write-through persistence and bounded version history are not a crash-proof backup.

Verdict

⚠️ Interesting: a credible agent-native design workbench, not a confidential-design drop-in. The shared human/agent mutation model, live rendering and inspect/screenshot feedback loop are unusually concrete. Pilot with non-sensitive designs first: unauthenticated asset/image URLs, optional plaintext credential storage, conditional session replay, asynchronous durability and a weak default Docker rendering boundary need explicit operational decisions.

What It Is

Doop stores canvases containing pages and HTML frames, rather than converting a proprietary vector-document format into application code. The browser editor changes layout, typography, shapes and elements; MCP clients create and patch HTML, inspect computed geometry and take screenshots. WebSocket rooms carry presence, cursors, changes and task progress. Prototypes connect frames with declarative interactions; comments can queue agent work.

Its built-in agent is separate from an externally connected MCP client. External clients bring their own inference/account environment. Built-in runs use connected model accounts or an explicitly enabled server allowance. Design references, decisions, guidelines, reusable components and tokens persist alongside the work. The first-canvas welcome animation is scripted; it is not evidence of model output quality.

The README explicitly excludes Figma, Canva and PSD import/export from the open-source edition. Do not equate the public checkout with complete hosted-service parity. Sources: README.md, server/mcp.ts, server/resident.ts.

Key Features

One mutable design model for humans and agents

REST, MCP and resident workers converge on shared actions, rather than maintaining separate design documents. MCP exposes HTML editing, page management, component/token operations, prototype wiring, imports, inspect and screenshot tools. Browser rooms show progress live. This is useful for iterative UI composition; it does not prove fidelity to an arbitrary production app. Evidence: server/actions.ts, server/mcp.ts, shared/types.ts.

Visual verification and design memory

Agents can render their frame and inspect computed layout for overflow, clipping and overlap. Those are candidate problems, not an automated aesthetic oracle. Guidelines, pinned references and recorded decisions provide persistent design context. Imported website content, comments and memory remain untrusted model inputs: tool schemas and budgets constrain actions, but do not solve prompt injection. Evidence: server/screenshot.ts, server/guide.ts, server/workBudget.ts.

Actual collaboration, with a centralized authority

Canvas access distinguishes view/comment/edit and durable membership. Owners, invited members and workspace members edit; share-link permissions are weaker and separately checked. Signed-out visitors can view link-shared canvases, with team conversations omitted. Ownerless legacy canvases intentionally permit editing. The server—not a peer-to-peer CRDT—is authoritative. Evidence: server/access.ts, server/index.ts.

Architecture and durability

The Express process owns in-memory maps and WebSocket rooms. Metadata hydrates from the database; frame HTML loads per canvas. Shared actions update memory, schedule persistence and broadcast. A journal queues external effects until an operation commits and can undo changes on failure; its own documentation explicitly disclaims isolation across awaited work. This is an application transaction mechanism, not proof of serializable database transactions. Multiple independent application replicas would need coordination not established by this review. Evidence: server/store.ts, server/frameHtml.ts, server/journal.ts.

Persistence deserves particular care. Ordinary mutations mirror asynchronously; general write failures are logged. Frames debounce for 400 ms, track dirty generations, remain loaded while unsaved, and retry failed writes during idle sweeping. A flush path and queued version writes exist; canvas duplication explicitly awaits a database transaction. These are real mitigations, but a UI-visible update is not automatically a durable commit, and process death can lose pending state. Do not describe this as a crash-proof collaborative database. Evidence: server/db/persist.ts.

Frame and guideline versions cap at 50 each. The hydrated log window is 100 entries per canvas for relevant histories; this is not a comprehensive retention/deletion policy. Export includes HTML-oriented workflows and PNG/JPG/vector PDF, not an independently verified full-instance backup/restore interchange. Account deletion removes private owned canvases but deliberately preserves shared/workspace canvases. No restore drill was performed. Back up the database, object bytes and encryption key material as one recoverable system. Evidence: server/db/persist.ts, server/accountDeletion.ts, server/storage.ts, README.md.

Security and privacy boundaries

Authentication is not the same as asset confidentiality

MCP tools require OAuth or a revocable account-scoped bearer key; agent keys are stored as SHA-256 hashes of high-entropy secrets. They resolve to the human's access, not a separate per-canvas least-privilege identity. Anonymous MCP discovery is limited to static resource discovery/ping. Bans are checked beyond token validity. REST/room/tool permissions share canvas-role helpers, and admin access is deliberately separated from ordinary MCP authorization. These are positive controls, not a complete endpoint audit. Evidence: server/agentKeys.ts, server/mcp.ts, server/auth.ts, server/access.ts.

Frame images and uploaded assets are deliberately public by unguessable ID. The /i/:id image handler checks frame existence, not canvas membership, and renders the current design. The /a/:id asset handler similarly omits membership checks, permits cross-origin loads and advertises one-year immutable caching. Thus a private canvas does not make a leaked asset/image URL private; turning off its share link is not equivalent to revoking those URLs or cached copies. This is observable route design, not a claimed live exploit. Evidence: server/index.ts (public images/assets routes).

Credential encryption must be configured

Model/integration credentials can be AES-256-GCM sealed with per-write random IVs and a versioned key ID. Rotation/backfill is implemented. Production without SECRETS_ENCRYPTION_KEYS stores these credentials as plaintext and only warns at boot. Development uses a fixed test key. Better Auth social OAuth tokens have a separate encryption setting backed by the auth secret. Server compromise still exposes usable credentials; this is at-rest protection, not end-to-end encryption. The supplied Compose environment does not forward the secret-encryption setting, so merely defining it outside the container is insufficient unless deployment wiring is changed. Evidence: server/secretBox.ts, server/secretBackfill.ts, server/env.ts, server/auth.ts, docker-compose.yml.

Replay is conditional, but potentially content-rich

Without a build-time PostHog key, client analytics is disabled. When enabled, the code initializes session recording with cross-origin iframe recording, maskAllInputs false, and password/email masking; its comments explicitly include prompt/comment visibility. A same-origin relay is designed to avoid ordinary analytics-host blocking. Internal-domain and impersonation exclusions exist. Self-hosting alone therefore does not establish zero analytics egress; inspect the built bundle configuration and obtain appropriate consent. This review does not establish whether the hosted service currently enables recording. Evidence: src/lib/posthog.ts, src/lib/frameReplay.ts, Dockerfile.

HTML sandboxing and server-side rendering are different boundaries

Editor/prototype frames use sandbox=allow-scripts without allow-same-origin, preventing normal same-origin access to the parent. That is not a blanket network-denial policy or proof that arbitrary HTML is harmless. Server rendering and website import execute web content in Chromium. Public-URL helpers reject private/literal/resolved network ranges, pin DNS for Node fetches, validate browser resources, impose byte budgets and block unsupported transports. Custom model endpoints require public HTTPS and reject redirects unless an operator explicitly enables private hosts. Declaring a remote renderer isolated changes enforcement and must reflect real network separation. Evidence: src/components/FrameView.tsx, src/components/PrototypePlayer.tsx, server/publicUrl.ts, server/customProviderFetch.ts.

The Dockerfile enables CHROME_NO_SANDBOX and specifies no non-root USER. A container with Chromium's own sandbox disabled should not be treated as a strong hostile-document execution boundary. Use a deliberately isolated renderer/network and resource policy before accepting untrusted public workloads. No browser escape or SSRF exploit was tested. Evidence: Dockerfile, server/screenshot.ts.

Optional native integrations widen trust

The desktop app wraps a chosen server and grants its origin native IPC capabilities. Its local Claude worker asks consent, runs an installed CLI in a temporary directory, disables built-in tools/settings/hooks/slash commands, and permits only the run's Doop MCP tools. This is materially narrower than an unrestricted shell agent, but depends on CLI behavior and trusts server-supplied work plus the native bridge. A separate Gemini worker also spawns a CLI with core tools/extensions/hooks disabled. Desktop updates use the Tauri updater and configured signing key; release builds check/download in the background. The Chrome capture extension requests activeTab, scripting and clipboardWrite—not unrestricted persistent all-site access in its manifest. None was installed or exercised. Evidence: desktop/src-tauri/src/server.rs, desktop/src-tauri/src/claude.rs, desktop/src-tauri/src/updates.rs, server/geminiCloudWorker.ts, chrome-extension/manifest.json.

Providers, data flows and costs

Built-in model adapters cover Anthropic, OpenAI, Gemini and Chat Completions-compatible providers, with custom endpoints behind explicit controls. Prompts, relevant design context, tool results and screenshots/images may leave the instance for the selected provider. Optional rendering, object storage, email, image search/generation, GitHub, Slack and Linear integrations add their own destinations and retention policies. External MCP clients also decide what they send to their models. A local canvas database is not local inference.

The server free-task allowance defaults to zero; connected user accounts or explicitly funded server keys enable real agent runs. Agent turns, image generation/description, remote rendering and storage can incur separate costs. Tool rate limits and work budgets are useful controls, not a universal money-denominated spending cap. Provider rates and hosted subscription prices were not independently verified.

The ChatGPT connection reuses Codex OAuth registration, with loopback, device and pasted-callback variants. The source itself warns that third-party-server subscription use is not sanctioned and may cause rate limits/suspension. Treat that as the maintainer's compatibility/terms warning, not an independent legal determination; prefer documented API-key arrangements for predictable operations. Evidence: server/modelAccounts.ts, server/agentModel.ts, server/env.ts, server/imageGen.ts, server/mcp.ts.

Self-Hosting Notes

  1. Start with non-sensitive sample designs on a restricted instance; configure production auth origin/secret, TLS, signup policy and real SMTP/SSO as appropriate. Development origin trust is deliberately permissive.
  2. Configure and verify credential encryption inside the actual process/container. Preserve old rotation keys until data and backups remain recoverable.
  3. Persist both database and assets. The supplied Compose file persists PostgreSQL, but gives the app no volume for its default disk assets: container recreation can discard uploaded files while database references survive. Add durable object storage or an appropriate app-data volume; do not mistake the database volume for a complete backup.
  4. Isolate Chromium and egress; decide whether public-by-ID media is acceptable. For confidential material, redesign/access-gate delivery rather than relying on obscure IDs.
  5. Keep PostHog disabled unless deliberately approved; audit every provider/integration destination. Use external provider-side spending controls.
  6. Pin reviewed builds and lockfile, back up before boot migrations, and test restoration before upgrades. No deployment was attempted here.

Sources: docker-compose.yml, Dockerfile, server/storage.ts, server/db/index.ts, server/auth.ts.
