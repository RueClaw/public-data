The important distinction is between serving the interface locally and processing/storing music locally. One host contract, two deployment contexts

The standalone host installs only when an embedded host is absent. Capability flags explicitly disable directEngine, share and mozart in standalone; unsupported engine mappings return 501. Pattern-arm and scene-launch support varies by view. This is a good boundary: UI presence is not evidence of backend availability or equal capabilities everywhere. Contract, standalone implementation

Recording and export distinguish acceptance from durability

The recording controller freezes the original project/lane context, caps uploads at 25 MB, requires a consistent durable clip identity and re-reads canonical project state before confirming placement. Uncertain uploads are not automatically repeated. Export tracks job identity, rejects mismatched project/job receipts, respects retry hints and distinguishes ready, pending, failed and uncertain results. These are implemented safeguards, not measured guarantees. Recording persistence, export controller

MIDI portability, but not complete project independence

The sampled app exposes MIDI import/export, cloud project snapshots, revert/history and cloud audio bounce. MIDI tests cover timing, polyphony, sustain, percussion and malformed data. MIDI cannot preserve the entire hosted instrument/effect/audio project, and a rendered mix is not an editable project backup. App save/menu implementation, MIDI tests

Architecture

Browser view → host API → loopback Python bridge → Freestyle REST/MCP and cloud project engine. Realtime audio/control additionally uses WebRTC; state changes arrive through ticket-backed WebSockets. The Python adapter maps legacy-shaped tool calls onto public v1 operations, while explicitly AI-only actions such as compose/refine/mix-check use MCP. This is not a bundled local model runner. Security, Privacy and Costs

  • Local trust boundary: the sampled server binds 127.0.0.1, checks Host, rejects foreign mutation Origins/cross-site requests, constrains static paths and excludes dotfiles. The API proxy validates paths and applies additional fetch-site checks. These controls are meaningful; they are not user authentication or protection against hostile same-user processes. Do not expose this bridge as a public multi-user service. Bridge
  • OAuth and permissions: PKCE/state handling and refresh-token rotation are implemented. Credentials are kept server-side in an app-local JSON store with directory 0700/file 0600, flock locking and atomic replacement. This is permission-protected plaintext, not a keychain. Requested scopes include project/DAW writes, AI use, media upload, library writes and offline access—not read-only access. A supported environment bearer is another sensitive input. Bridge
  • Origin configuration: FREESTYLE_BASE permits arbitrary HTTPS origins, with HTTP allowed only for loopback. That is operator configuration, not a verified Freestyle-only allowlist; a changed origin is a credential/data trust decision. Do not copy unreviewed environment settings. Bridge
  • Devices and cloud data: recording uses getUserMedia; Web MIDI is requested through browser APIs. Uploaded recordings, project edits and remote audio sessions cross into Freestyle, while browser storage includes device identifiers and UI preferences. OAuth tokens stay out of normal browser API responses, but short-lived WebSocket tickets necessarily reach the client. Browser permission is not a cloud-data consent policy. Recorder, MIDI input, host, WebSocket
  • Diagnostics: the bridge sanitizes common credential/error forms and suppresses callback query strings in request logs. Its client diagnostic ring accepts bounded client-supplied entries, so do not assume every diagnostic export is free of project names, user text or signed URLs. Review diagnostics before sharing. Bridge
  • Costs and service terms: the launch message calls for a Pro account; AI actions and cloud exports depend on service entitlement. The repository license is not a free-service promise. No current price, quota, retention/deletion guarantee, training-use policy or subprocessor list was verified; confirm these with the provider before uploading sensitive recordings. No provider/model calls were made. Bridge, AI routing

Persistence, Export and Recovery

The app's Save action saves a snapshot in Freestyle, not a full local project archive. Browser preferences and a local auth file are not project backups. Recording placement reads back canonical state, and pending export observation can resume by job ID within the controller. However, the inspected export controller stores its receipt in memory; this alone does not prove recovery after browser restart. Preserve independent audio/MIDI exports and verify the provider's project backup/export facilities before relying on it for irreplaceable sessions. Save implementation, recording, exports

A network failure can leave a write uncertain rather than safely retryable. The code's inspect-before-repeat approach is a strength, but recovery still depends on a reachable provider and trustworthy canonical state. Snapshot retention, complete project portability, outage recovery and cross-view undo behavior were not tested.
