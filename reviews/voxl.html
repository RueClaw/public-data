Key points

What matters most, in order.

1

Built for existing desktops, not speech

X11/Xvfb, macOS and Windows capture feed H.264 over a browser WebSocket. Screenshots, recording and sequence-aware visual waiting are useful for agents; native Wayland and GPU encoding are absent at this revision.

2

Read-only is not a privacy boundary

Authentication and server-side input restrictions are implemented. But read-only viewers retain observation and enabled downloads; the default home-directory share can expose hidden files through direct downloads or ZIPs.

3

Benchmark headlines need qualification

The README uses best runs, native decode timing and loss-free shaped links. The reviewed commit updates Selkies setup and reports substantially closer results. Test real browsers, legibility, packet loss and matched resources.

1. Damage-driven video rather than constant screenshot polling. Platform capture feeds conversion and x264; the shared Hub distributes frames, cursor and audio. Client acknowledgements drive queue tracking and adaptive bitrate. Paint-over frames sharpen still content. A stalled client is resynchronized after roughly four seconds; before that, a slow viewer can gate the shared capture flow. This is not independently isolated per-viewer video quality. video.rs, hub.rs, encoder.rs.
2. Useful agent APIs without an agent dependency. Screenshot responses carry a sequence number; /wait supports change/idle, region, timeout and since-sequence semantics, avoiding blind sleeps and missed-change races. This detects visual changes, not semantic application readiness. Recordings reuse encoded frames rather than re-encoding, but muxing, buffering and transfer still consume resources; the README's “no extra CPU” wording is stronger than the implementation warrants. Resize ends a recording and multi-stripe recording is refused. wait.rs, record.rs.
3. Browser work is separated sensibly. The worker owns transport and video decode, with OffscreenCanvas or a presentation handoff; the main thread owns layout, input, clipboard, audio and microphone controls. It checks secure-context/WebCodecs availability and reconnects a closed socket after one second. This is transport recovery, not durable session replay. main.ts, worker.ts.
4. A compact embeddable process, not a static dependency-free binary. main.rs delegates to library run(); compile-time platform modules share interfaces. build.rs generates x264 FFI and invokes esbuild, then embeds client assets. Native codec/display dependencies remain operational and supply-chain inputs. lib.rs, build.rs.

Authentication and network boundary

Authentication middleware protects the desktop, WebSocket, file and agent endpoints; a small explicit asset list and /healthz are public. Credentials may come from a CLI flag, VOXL_PASSWORD, a Selkies-compatible environment variable, or a generated 128-bit random password. Basic, Bearer and URL-token authentication all grant the same authority; the optional Basic username does not constrain Bearer/token access. There is no per-user RBAC, MFA, expiring viewer token or per-session permission system in the reviewed paths. No application login rate limiter was found. login.rs, lib.rs.

Generated passwords are intentionally printed in startup logs. Token links remain in the page URL and are propagated to worker/WebSocket/file URLs, so browser history, copied links and proxy access logs must be treated as credential stores. Use protected secret injection rather than command-line secrets, restrict logs, and prefer an authenticated front proxy for multi-user access. Changing a configured password requires restarting/reconfiguring the process; a generated one changes on restart.

Linux defaults to all interfaces on port 6901; macOS/Windows default to loopback. The server itself is plain HTTP. Host validation and browser Origin checks are real middleware, run before login, but are not network authentication: non-browser callers can omit Origin, IP hosts are permitted, and wildcard exceptions weaken browser protections. Remote browser WebCodecs also requires HTTPS. Terminate TLS at a trusted proxy and restrict direct backend reachability; disabling built-in auth is safe only when that proxy cannot be bypassed. access.rs, SECURITY.md.

Desktop authority is execution authority

An authenticated writable viewer can type into a terminal or privileged application already present in the desktop. There is no command allowlist, action approval or application sandbox. All viewers share the same desktop and privilege level. macOS needs Screen Recording and Accessibility permissions; Windows runs in the user's interactive session and has lock-screen/UAC restrictions. Do not elevate it to bypass those boundaries. Linux capture relies on authority to access the X display.

Read-only mode is enforced on the server: a command allowlist rejects input/clipboard writes/resize and all binary client messages; upload is disabled separately. Read-only does not mean confidential: screen, screenshot/recording, outbound clipboard and enabled downloads remain available. Turn off clipboard, audio and file transfers independently when those data channels are unwanted. Browser microphone is off by default server-side and requires a browser permission flow when enabled. server.rs, lib.rs, mic.ts.

Files are a broad grant, not a vault

Uploads and downloads default on, with the user's home as files-root (falling back to filesystem root if neither home environment variable exists). The list UI hides dotfiles, but direct downloads resolve a requested relative path and directory ZIP traversal does not filter hidden files. Hiding dotfiles is not secret protection: a home-root share can expose configuration and credentials to an authorized downloader. Use a dedicated minimal exchange directory instead of a real user's home.

Path components reject absolute paths and parent traversal; canonicalized existing targets must remain under the configured root. Folder ZIPs omit symlinks, upload subdirectories are checked stepwise, uploads require a custom header and use create-new temporary files followed by rename. These are meaningful safeguards, but path validation and later filesystem operations are not a race-proof filesystem sandbox. Concurrent local mutation and crash/race behavior were not dynamically tested. Avoid attacker-writable shared roots and use OS isolation. files.rs.

Data and cost flows

The reviewed runtime has no model provider, account service, telemetry uploader or obligatory third-party media relay. Screen/audio/clipboard/files go between the host and authenticated viewer through whatever reverse proxy or tunnel the operator chooses; a TLS-terminating intermediary can observe them. Browser-origin media permissions are separate from server authentication. Apps on the controlled desktop can make their own network calls; voxl does not restrict their egress.

Costs are CPU encoding, bandwidth, hosting and optional tunnel/proxy services—not model tokens. The 30,000-kbps default video ceiling is about 13.5 GB/hour per viewer if continuously saturated, excluding overhead/audio; actual damage-driven/adaptive traffic can be much lower. Multiple viewers still multiply delivered traffic. The optional Daytona benchmark script uses an external account/API key and may incur cloud charges; it is not a runtime requirement and was not run. lib.rs, bench README.

Persistence and recovery

- Uploaded files persist in the selected root; there is no expiry/cleanup scheduler or resumable upload protocol. The default per-upload size limit is unlimited. Error paths attempt to remove temporary .part files, but crashes can leave them behind; no startup scavenger was identified. Unique-name selection plus rename is not a transactional multi-client conflict protocol.
- Recordings are RAM-backed, with a default 300-second maximum. Started/unclaimed recordings are discarded after the maximum duration plus a 60-second grace period. No global recording-count/byte budget was found. A time limit alone is not a safe aggregate memory bound. Saved downloads/recordings then have viewer-owned retention, not server-enforced deletion.
- Session state is ephemeral. There is no database, durable task journal, audit identity or restore system. WebSocket reconnect resets decoding; disconnect releases input state and stops that client's microphone stream. It does not undo desktop actions or recover an interrupted upload/recording after process loss.
- Operational recovery is external. Release builds abort on panic; the library also installs an aborting panic hook in unwind builds. A supervisor, isolated desktop lifecycle, resource quotas and backup/restore policy belong to the deployment. /healthz is a simple “ok” response, not proof that capture/input/audio are healthy. files.rs, record.rs, server.rs, lib.rs.

Claims and maturity

The README reports approximately 60 FPS and 12–99 ms median latency on a 16-vCPU GPU-less VM. It discloses that voxl's column uses its best run, that native clients measure draw-to-decode rather than complete browser/input-to-photon latency, that Sunshine is outside its GPU-oriented sweet spot, and that shaped links do not drop packets. These results are useful author evidence, not a universal product ranking or a reproduction by this review.

Importantly, the reviewed HEAD itself updates the Selkies benchmark setup. Its merged commit message reports much closer voxl/Selkies results, including faster Selkies LAN scroll in that separate run, and calls for standardized quality/legibility tests. Hardware and setup differ, so do not combine those numbers with the README table; they do show why its headline should not decide a purchase or migration. Compare text/chroma fidelity, real browser latency, loss, concurrent viewers and matched resource limits. README, benchmark methodology, reviewed commit discussion.

Deployment checklist

Start with a disposable Xvfb VM/container and dedicated low-privilege account, not a logged-in personal workstation. Explicitly bind loopback or a protected interface; use TLS and authenticated proxy access with an exact host/origin allowlist. Keep built-in authentication unless the backend is unreachable except through the authenticating proxy. Disable files/clipboard/audio/microphone unless needed; otherwise use a minimal exchange root and nonzero upload limits. Read-only is useful for observers but does not remove download or capture authority.

Add connection/request/concurrency limits and memory/disk quotas outside the process, bound recordings, protect access/startup logs, and test reconnect, shutdown, upload interruption, restore and loss-heavy networking with synthetic data. Validate permissions and input on each OS before use. For computer-use agents, put policy and approval gates in the agent harness and isolate the actual desktop: the streaming layer is not that boundary.
