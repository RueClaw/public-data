Key points

What matters most, in order.

1

A real local-first engine

Transactional local edits and a per-service outbox preserve offline work and expose refused changes. Some Drive and Photos operations still require immediate network access.

2

Strong controls, broad trust

Separated HTTP clients, narrow renderer CSP and short-lived file grants are meaningful. The native process retains the Apple password in the keyring, and the local library is not encrypted.

3

Export is not full backup

Export includes local data and cached bytes, not every cloud original. Separate Photos/Drive backup retains deleted content and earlier versions, requiring its own storage and retention policy.

Durable writes rather than optimistic UI alone

Notes, Reminders, Contacts, Calendar and Photos flags combine local changes and queue insertion transactionally. A worker drains per service, preserves ordering on transient failure, and retains refused edits for Retry/Discard. The inspected drain_as path checks account ownership before taking each change, and serializes sending with the service's sync pass. Protocol/conflict errors become refusals after five attempts; network/reauthentication failures remain retryable. This is a good practical design for intermittent connections. queue.rs, outbox.rs.

Do not generalize this to every operation: Drive rename/move/delete and some Photos metadata are direct network writes; mounted-file writes have their own disk journal. Offline browsing is not proof that every edit works offline. Notes' CRDT and merge logic are interesting, but “nothing is lost” and universal idempotence are guarantees requiring much broader fault testing than this review performed. architecture writing section.

Account separation is meaningful, but not tenant security

The library records a SHA-256-derived account tag. Switching accounts sets whole libraries aside, including caches and unsent changes; sync passes and queue drains validate ownership. That reduces accidental cross-account synchronization. It is a single-user native application, not a hosted multi-tenant service with RBAC. All authorized application windows and the native process remain powerful, and a hash of an account identifier is not encryption. main.rs, claim_library, queue ownership.

Network policy and local authority

Four client builders separate Apple services, public calendar subscriptions, explicitly added CalDAV accounts and GitHub release updates. Apple requests require permitted domain suffixes and TLS; loopback is a test/feature exception, not the normal shipping allowance. Regional Apple domains are enabled for regional accounts. Public subscription resolution filters private/reserved addresses; account clients deliberately permit user-selected private servers. Environment proxies are supported, so these controls should not be described as an OS firewall or an independently verified guarantee about every proxy-resolved destination. auth client builders, release client.

The bundled desktop page's CSP blocks general network connections and grants only narrow Tauri plugin permissions. Custom application commands still carry substantial library/account authority. For filesystem access, grants.rs canonicalizes paths, expires grants after ten minutes and consumes save grants once; directory read grants include descendants. This protects against a renderer inventing arbitrary file paths, but is not a sandbox against compromised native code or another process running as the user. CSP, capability, file grants.

Video playback uses a loopback HTTP server with a fresh UUID secret, exact Host validation and rejection of non-app Origins, without CORS grants. Those are useful browser/DNS-rebinding defenses, not protection from a same-user attacker able to inspect the application's memory or files. video gate.

SRP avoids transmitting the raw Apple password as the login proof; it does not mean Skykeep never receives or retains that password. The documented design keeps password plus session in the OS keyring for automatic reauthentication. Cookies are AES-256-GCM sealed with a separate keyring key. The local library, opened files and image caches are not encrypted by Skykeep; full-disk encryption and a trustworthy logged-in session matter. The security document explicitly acknowledges same-user keyring access. credential/session policy, sealed cookies.

Content normally goes device ↔ Apple. A user-added calendar server receives its own calendar data/credentials; subscription hosts receive fetches; update-capable packages contact GitHub. Browser-opened links and Android system-provider integration create additional user-selected trust boundaries. No model provider or AI inference is needed, and no Skykeep telemetry backend was identified in the inspected architecture. Do not translate that into “no network requests” or a universal anonymity claim.

Advanced Data Protection still requires enabling Apple's web-data access and approving a temporary session from a trusted device. The local readable copy remains after the approval expires; queued protected-service edits wait for renewed approval. This is a conscious expansion of endpoint access, not a bypass of ADP or access to iCloud Keychain/Health. ADP policy.

Costs are ordinary iCloud storage, bandwidth, local disk and optional CalDAV hosting—not token fees. Backing up a large photo library can consume substantial bandwidth and disk; no spend cap or storage quota should be inferred.

Persistence, Retention, Export and Recovery

  • Local continuity: SQLite/WAL and durable queued writes survive restart. Corruption recovery sets the damaged database aside and attempts salvage, including outbox records, rather than overwriting the evidence. Salvage is best effort, not guaranteed recovery of every unsent edit. library recovery.
  • Sign-out is a policy choice: users can keep the library; otherwise the code removes library files, sidecars/corrupt copies and caches. Deferred keyring cleanup handles an unavailable keyring. Other account archives, user-created exports, downloaded files and backups need their own retention decisions. File deletion does not prove forensic erasure from SSDs, snapshots or external backup media. sign-out, security retention policy.
  • Export is local, not a complete cloud backup: Markdown, iCalendar, vCard and CSV plus cached media are written through a partial-directory/rename scheme. Unopened photos and undownloaded Drive content are listed instead of fetched. A successful export can therefore omit original bytes. export implementation.
  • Backup is a separate feature: Photos originals and Drive files are copied to a chosen destination; changed Drive files keep earlier versions and cloud deletion is not mirrored as backup deletion. That is valuable protection from accidental cloud removal, but intentionally retains deleted personal data and grows storage. It is not a one-click restore of the entire iCloud account or all six applications. Recently Deleted items are not copied. backup implementation.

Before adoption, test interruption/retry, simultaneous-device note edits, account switching with pending writes, deleting/recovering a disposable record, disk-full behavior and restoring a sampled export/backup. Keep at least one independent offline copy; synchronization alone is not backup.

Verification limits

The reviewed implementation supports the core architecture and several concrete security controls. It does not establish end-to-end protocol compatibility, complete command-grant coverage, race-free account switching, full restore fidelity, performance, binary provenance or freedom from vulnerabilities. Verdict

The call, and why.

⚠️ Interesting

Thoughtful outbox, account isolation and native boundaries make this worth a cautious pilot. Broad Apple-account authority, readable local retention and unofficial protocols rule out treating it as a proven primary-library client. Static review only; no account or device tests.
