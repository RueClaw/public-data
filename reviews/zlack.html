Key points

What matters most, in order.

A client, not a collaboration backend

Slack still owns accounts, authorization, messages and retention. Zlack adds native windows, badges, downloads and up to two warm workspaces.

2

Remote IPC needs one more boundary

New workspace URLs are validated, but an existing window can receive an unchecked URL through switch_workspace. This is a static code-path concern requiring an authorized IPC caller, not a demonstrated message-based exploit.

3

Real tests; important behavior unverified

All 33 JavaScript tests passed in a network-isolated synthetic sandbox. Google login and Linux sign-in handoff issues have open proposals; those fixes are not in the reviewed revision.

Zlack loads app.slack.com into a system WebView and injects a substantial JavaScript compatibility layer. Slack still supplies the UI, accounts, messages, files, permissions and backend. There is no independent message database, server API, tenant provisioning, retention service or offline archive. The project is not affiliated with or endorsed by Slack/Salesforce.

The audience is a desktop user seeking native notifications and workspace switching without packaging an entire Chromium runtime. That packaging choice is verified; lower real-world RAM/CPU use is not. Up to two workspace windows stay warm. Evicted workspaces are not continuously live, so do not assume every workspace continues receiving real-time alerts.

Native notification routing

The preload replaces Notification and notification-permission behavior, disables service-worker registration, and intercepts fetch/XHR/sendBeacon telemetry to associate notifications with team/channel IDs. The native layer shows titles/bodies through the OS notification service and routes activation to the originating window, with a Slack URL fallback. Ten-minute JavaScript and Rust activation retention is not a promise to purge OS notification history or Slack messages. Slack-internal telemetry formats are compatibility liabilities despite thoughtful reconciliation tests. Bridge, native registry, activation.

Workspace and unread integration

A mutex-protected Rust registry tracks window/team mappings, LRU order, metadata and aggregate badges. MAX_LOADED_WORKSPACES is two. Preload observes Slack state, caches workspace names/domains locally, and remembers request headers/body for counts polling in page memory. Authentication remains Slack's responsibility. Registry, request replay.

Authenticated downloads

File/image requests run inside the logged-in page with credentials included, then send base64 bytes through IPC to Rust. Native saves use the OS Downloads directory, sanitized stems/extensions and 64 MiB image / 256 MiB general-file limits. Base64 and full-buffer copies can be expensive. Native save commands do not themselves require a user gesture or Save dialog: a compromised allowed page could issue repeated writes. General-file extensions may be executable, but this code does not automatically execute the saved file. Downloads, fetch bridge.

Authentication and tenant boundaries

Slack web sessions/cookies handle login and service authorization; Zlack has no separate password system or server-side authorization. Workspace windows are UI separation, not strong tenant compartments: they use shared application state, no explicit per-workspace WebView data directory, and commands accept team identifiers supplied by the page. workspace_status exposes aggregate workspace metadata. update_notification_context mutates a global ID-keyed registry without checking the caller's originating window. These are local cross-workspace trust concerns, not evidence of bypassing Slack's server-side access controls.

Public issue #13 reports Google login blocked in embedded WebViews. PR #14 proposes browser/deep-link login, but was open at review time and is not in this SHA. PR #7 separately addresses Linux slack: sign-in handoff recovery. These are upstream reports/proposals, not independently tested fixes or proof every login fails. Validate the actual identity-provider flow before adoption; do not infer huddle/screen-sharing support from a working chat page.

Native IPC: useful restrictions, incomplete defense

Static capabilities permit only the slack-ipc command set on HTTPS app.slack.com/slack.com in main/workspace-* windows. Additional workspace-host capabilities are created for a particular window after Slack-domain URL parsing. No general shell permission is exposed. New-window URLs must be credential-free HTTPS under slack.com. External opening accepts credential-free HTTP(S), rejecting file/custom protocols, but does not exclude private-network hosts or unusual ports; this opens the user's browser, not a native HTTP proxy. Capability, permissions, URL validation.

Important static finding: switch_workspace accepts an optional URL. Creating a new window validates it, but ensure_workspace_window skips creation/validation when that team already has a live window. switch_to_workspace then supplies the URL to an evaluated script, attempts the Slack router and otherwise assigns window.location.href. A non-Slack URL can therefore reach that fallback for an existing window. No native on_navigation allowlist is installed in the reviewed main.rs. A compromised IPC-authorized page could navigate another existing workspace window; javascript: evaluation risk should also be explicitly regression-tested and blocked rather than assumed safe. This is a code-path finding, not a demonstrated live exploit, and requires control of an authorized page/IPC caller—not merely posting a normal Slack message. Fix by parsing URLs at the command boundary on every call and applying native navigation policy. Creation/lookup, navigation sink, command.

Application csp is null; that does not prove Slack's remote response CSP is absent. Injected page interception is a compatibility mechanism, not a security boundary. Executable-adjacent CSS is read and delivered to the page; use trusted CSS only. A sibling fixed WebView2 runtime is executable code and shifts runtime-update responsibility to the operator. Config, platform handling.

Message/file privacy and retention

There is no independent privacy layer or end-to-end encryption implementation. Slack and any identity provider remain network trust dependencies. Zlack observes page requests/responses for unread/workspace/notification behavior; the OS receives notification titles and message bodies. Session data, localStorage workspace metadata, clipboard image copies and attachments are separate persistence surfaces. No application-wide secure erase, configurable retention, profile encryption or account-removal cleanup mechanism was found in the inspected implementation. Signing out must not be assumed to remove Downloads or notification history.

Filename sanitization prevents ordinary path components from choosing arbitrary destinations, but unique_path checks existence separately from std::fs::write and falls back to the original filename after 9,999 collisions. Overwrite avoidance is best-effort, not atomic: concurrent saves or name exhaustion can overwrite. Prefer atomic create_new-style allocation and failure instead of fallback. This edge case and filesystem symlink races were not dynamically exercised. Filename selection.

npm and Cargo lockfiles are present. npm has only the Tauri CLI as a direct dev dependency; the native/runtime supply chain is much larger. CI compiles on Ubuntu, Windows and macOS and runs clippy without warnings-as-errors; it does not run cargo test or JavaScript suites. Pin immutable revisions/digests and add test gates. No vulnerability scan, SBOM, binary signature verification or reproducibility comparison was performed. CI, release.

Adoption considerations

Slack's supported systems/browsers distinguish huddle browser support; a spoofed Chrome user agent does not turn WebKit into Chrome. Zulip and Mattermost are category alternatives, not audited deployments in this review.

Practical gate: fix the existing-window URL boundary; scope native mutable state by originating window where appropriate; add tests to CI; validate real SSO and notification/download behavior on each platform. Until then, study or cautiously pilot rather than standardize on it.

There is no server to self-host. Desktop packages exist for Windows, macOS and Linux; source builds require Node, Rust and platform Tauri/WebView prerequisites. The configured macOS minimum is not a guarantee Slack's current web client supports that OS/WebKit. Keep the system WebView patched; a fixed Windows runtime needs its own updates.

Startup does a DNS reachability check and can show a local retry page polling Slack every five seconds. That is connection recovery, not offline messaging. Window close normally hides the app; the tray offers quit/restore. Maximized state is explicitly persisted in a small window-state file. Keep a known-good installer and normal supported Slack access as fallback; no in-app rollback or message backup/restore subsystem was found. Fallback, lifecycle.

The updater checks GitHub Releases on startup and asks before download/install/restart. An embedded public key and release signing configuration are positive, but updater signing does not prove platform code signing/notarization, reproducible builds or successful end-to-end updates. Documentation warns that losing the signing key breaks existing clients' trust in replacement-key updates. Updater, operations.

Verdict

The call, and why.

⚠️ Interesting

Useful native notifications and a small system-WebView shell, but unresolved authentication compatibility and an existing-window URL validation gap prevent a default deployment recommendation. 33 synthetic JavaScript tests passed; no live Slack or native application validation was performed.
