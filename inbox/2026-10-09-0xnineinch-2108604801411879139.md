## Article text

Your Opus 5.5 bill grows every time an agent reads the same material, makes the same decision, or retries without knowing what failed.
“Is this relevant?” “Should I continue?” “Does this draft need another pass?”
Across hundreds of tasks, those small decisions become a workload of their own. Useful research and writing have to wait behind them.
My approach is to give Jev the focused judgments, give Opus the work worth developing, and let ordinary code handle repeats, limits, and state.
The target is 20x more accepted work for the same API budget. Reaching it depends on where the original workflow spends its money. This guide shows how to find that opportunity, build the process, and count the complete cost.
 
Part 1: Find the Work You Keep Paying For
Start with a recurring process: monitoring sources, reviewing an inbox, triaging issues, or preparing content.
Follow one task from arrival to completion. Record every model call and what it contributes.
The questions worth investigating are concrete:
Did the source change since the last run?
Did the model read an entire document to make a small routing decision?
Were five questions about the same text sent as five requests?
Did another attempt receive new evidence or just “try again”?
Did someone still have to repair the result?
A workflow that checks an unchanged inbox every ten minutes can repeatedly pay to rediscover that nothing needs doing. A content loop can rewrite a weak draft three times without identifying its weak claim.
The first saving comes from identifying work that never needed another model call.

Part 3: Four Changes That Reduce Waste
1. Avoid unnecessary Opus launches
Code recognizes an already processed version. Jev evaluates genuinely new material. Only suitable work advances to drafting or analysis.
The filter must retain valuable tasks as well as reject irrelevant ones. A cheaper process that misses the important work needs adjustment.
2. Give Opus a smaller, useful packet
Pass the approved brief, relevant source excerpts, source IDs, and current requirements. Keep unrelated documents out of that task.
Long documents need preprocessing. Jev currently accepts text, so recordings require a transcript and visual material requires a text representation before evaluation. genui{"citation":{"ref":"turn188view1"}}
3. Batch independent questions
Check evidence support and usefulness against the same draft in one Jev request. Each question can evaluate the supplied state independently.
A question that depends on a previous answer belongs in a later step.
4. Make every retry earn its place
Return the failed criterion, relevant evidence, and previous draft to Opus. Allow one revision, then send unresolved work to review.
A second attempt should have a reason to produce a better result.
 
Part 4: Start With One Research-to-Content Workflow
The first job is small: take a source packet and prepare one English AI post for review.
The packet contains an audience brief and source excerpts with stable IDs. Opus produces a 150–250-word draft, including source IDs beside factual claims for the reviewer.
The process is:
Source Packet → Repeat Check → Jev Selection → Opus Draft → Jev Checks → Review
Suppose the topic is an agent that can classify incoming support issues. The packet includes an official explanation and a demonstration transcript.
Jev decides whether the material supports a useful post for AI builders. Opus develops the practical angle: what the classification enables, what input it needs, and what remains unresolved.
The output check asks whether the claims match the supplied evidence and whether the reader receives a concrete example or action. Failed work returns with those criteria attached.
The review package contains the draft, its sources, and the check results. That makes the next decision easier to inspect.

I want each call to receive the information required for its own job.
Opus gets the brief, selected evidence, output requirements, and source IDs. A revision also gets the previous draft and failed checks.

The starting implementation uses a routing confidence threshold of 0.8 and a 0.85 threshold for its yes/no draft checks. Those settings need calibration against the evaluation set. Choice confidence and the probability assigned to a selected option are different fields.

Part 8: When a 20x Budget Target Makes Sense
Take a decision-heavy workflow with these assumptions:
600 judgments per day for 30 days.
4,000 total input tokens per judgment, including instructions.
50 output tokens per judgment when using Opus.
Standard uncached API pricing.
That is 18,000 judgments, 72 million input tokens, and 900,000 Opus output tokens.
Opus 5.5's listed standard rates are $4 per million input tokens and $20 per million output tokens. Jev 1.13 charges $0.042 per million input tokens, with free output. genui{"citation":{"refs":["turn189view0","turn188view1"]}}
 
Now add the Opus work that remains: drafting, analysis, and revisions. Keep that expense identical in both versions to isolate the decision-layer change.
 
The largest opportunity is a workflow that spends heavily deciding what deserves a small amount of useful work. When generation dominates, the same routing change has less impact.
To interpret those ratios as more accepted work per dollar, the outputs and acceptance rate must remain comparable. Infrastructure and human review add further costs.
Opus cache reads are listed at $0.20 per million tokens. A baseline that already reuses cached input can cost substantially less than the uncached example. Use its actual cache usage in your comparison. genui{"citation":{"ref":"turn189view0"}}

Part 10: Apply It to Email and GitHub
Email
Code recognizes new message versions. Jev routes messages into reply, task, ignore, or review. Opus drafts responses for selected messages using the relevant conversation and instructions.
Keep sending as a separate permission. Classifying a message as urgent does not authorize the reply.
GitHub
Code checks issue IDs, revisions, and existing jobs. Jev evaluates whether a report fits the project's scope and contains enough detail. Opus receives the selected issue, relevant project context, and acceptance checks.
Tests produce concrete evidence for the review step. Jev can help evaluate whether that evidence addresses a requirement, while code handles test exit statuses and required files.
The biggest gains are likely in repeated queues containing plenty of irrelevant or unchanged work. A single complex task with little routing overhead may receive little benefit from another model call.
Choose a workload with decisions you can define and outcomes you can inspect.

Part 11: Build One Useful Loop First
Start with one brief, a small evaluation set, and a complete review package.
Inspect selection in shadow mode. Run accepted tasks through Opus. Check the output, bound the revisions, and record the expense of getting something usable.
Expand after the numbers show where the process improves. More sources, more checks, or a schedule should each serve a specific need.
Give Opus prepared work. Give every retry a reason. Keep a record of what finished.
That is the foundation for pursuing the 20x target: spend the budget on work that survives review, and remove the repeated decisions consuming it along the way.
