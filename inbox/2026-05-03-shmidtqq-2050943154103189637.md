## Article text

You're building a feature you sketched out with Claude this morning. The conversation went well, the plan was solid, the architecture made sense, you both agreed on the data flow. You closed the laptop, grabbed lunch, came back, and asked Claude to start implementing.
It's now writing something that directly contradicts the morning's plan.
You paste the earlier decision back. Claude apologizes, agrees, rewrites. Forty lines later it contradicts itself again. By 4 PM you've spent more time re-aligning Claude with the plan than executing on it. By 6 PM you're debugging a 400-line implementation it wrote in fifteen minutes, half of which wasn't needed in the first place.
This is what working with Claude Code feels like by default.
The model is brilliant. The harness around it, the part that decides what to remember, when to think, when to reach for a tool, when to stop and ask, is barebones. You're effectively pair-programming with a senior engineer who has the memory of a goldfish, no checklist, and a permanent itch to start coding before anyone agrees on the design.
The fix isn't a better model. It's three small open-source projects that wrap Claude Code and supply the missing parts.
 
1. The amnesia problem → claude-mem
The first thing you notice after a week of daily use is that Claude doesn't remember anything between sessions. Yesterday's architectural decision? Gone. The bug you fixed Tuesday with a specific workaround? Gone. Every morning starts with re-explaining your project.
 
claude-mem (by Alex Newman: github.com/thedotmack/claude-mem) 
fixes that with five lifecycle hooks that quietly capture every session, compress what mattered with AI, and inject the relevant slice back into your next session. SQLite under the hood, a local web viewer at localhost:37777, full search through past observations.
 
After about a week you stop noticing it, which is exactly what you want from a memory layer. You just pick up where you left off.
 
2. The "code first, think later" problem → Superpowers
Claude's default mode is to start writing code. Ask it to add a feature and it's editing a file within seconds. Great for trivial tasks. Disaster for anything that needs design.
 
Superpowers (by obra: github.com/obra/superpowers) flips that reflex. 
It adds structured-thinking modes - brainstorming, TDD discipline, root-cause debugging - that force a plan before implementation. The agent doesn't get permission to write code until it has named the problem, listed the options, and picked one.
 
The cost: ten minutes of "but I wanted to ship now." The payoff: the difference between 400 lines that need rewriting and 100 lines that just work. After a few days you stop wanting to skip the planning step.
 
3. The "every project from scratch" problem → Everything Claude Code
By the third project you realize you've been re-creating the same setup every time: the same review agents, the same test workflows, the same /plan shortcut, the same package-manager detection. Each project ends up with a slightly different half-finished CLAUDE.md.
 
Everything Claude Code (https://github.com/affaan-m/everything-claude-code) is one developer's ten-month accumulation of those configs polished into a single plugin. 
Inside:
A few dozen specialized agents - planner (decomposes tasks and delegates to others), code-reviewer, security-reviewer, tdd-guide, build-error-resolver, plus language-specific reviewers for TypeScript, Python, Go, Rust, and more.
Slash commands that replace paragraphs of prompt engineering: /plan, /tdd, /security-scan, /quality-gate, /simplify.
Skills that load on demand instead of squatting in your context window.
 
Don't enable everything. Pick your stack and the agents you actually need, each agent description costs context tokens.
 
The thing nobody warns you about → AgentShield
There's a fourth piece, bundled inside ECC, and it's the one that justifies the whole stack on its own.
In early 2026, a viral AI project called Moltbook leaked 1.5 million API tokens in plaintext through a single misconfigured database setting. The founder had vibe-coded the whole platform. The fix took two SQL statements; the damage took weeks to contain.
That class of problem - configuration files quietly becoming execution paths, is exactly what bites you with Claude Code. Real CVEs (CVE-2025-59536, CVSS 8.7) showed that opening the wrong cloned repo could leak your Anthropic API key before the trust dialog even rendered. A hardcoded key in a CLAUDE.md you forgot about is a one-line breach.
AgentShield scans your entire Claude Code setup for exactly this:
 
The --opus flag is the interesting one. It runs three Claude Opus 4.7 agents in sequence, an attacker hunting exploit chains in your config, a defender evaluating your protections, and an auditor reconciling both into a prioritized risk report. It checks CLAUDE.md, settings.json, MCP server configs, hooks, agent definitions, and skills. 1,282 tests, 102 rules.
Run it once on every Claude Code project. Run it in CI on every PR that touches an agent config. The cost is thirty seconds; the upside is not being the next Moltbook footnote.
 
The five-minute setup
 
Then add a few house rules to your CLAUDE.md. Three lines is enough:
Run the relevant tests before marking a task complete.
Never delete files without confirmation.
Explain your reasoning before writing code.
Every agent in the stack reads CLAUDE.md, so those rules cascade.
 
What changes after a week
Hour three of a project stops going off the rails. The morning's plan is still there. The agent thinks before it writes. The same /plan, /tdd, /security-scan commands work in every repo. You stop re-explaining your conventions every day.
This isn't "Claude replaces your team." It's Claude becoming usable for real work, the gap between the demo and the second week.
