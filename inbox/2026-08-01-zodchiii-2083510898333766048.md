## Article text

AI agents can build a knowledge graph from your docs in an evening. Most people run it twice and get four copies of the same company.
The fix is 6 rules: a locked schema, deterministic IDs, validation before write, provenance on every edge, and a golden subgraph to diff against.
Get these right and your graph improves on every run.

Why agents break graphs
Graph engineering used to be a month of a data engineer's time. An agent does a rough version in a night, which is exactly why so many broken graphs exist now.
The failure is always the same shape:
read document → guess the entities → invent a relationship type → write to database
No schema check, dedupe, record of where anything came from. Run it again next week and it invents slightly different names for the same things.
Two weeks in:
Duplicates. Acme, Acme Inc, Acme Incorporated and ACME are four separate nodes.
Drift. works_at, employed_by and member_of all describe one relationship.
No trace. 40,000 edges, none of them saying which document produced them.
The graph is not wrong in an obvious way. It is wrong in a way that only shows up when you query it and the answer comes back quietly incomplete.
 
1. Lock the schema before the agent touches anything
An agent given a blank graph invents structure, and it invents different structure every run.
Write the schema first, as a file the agent reads before it does anything:
 
The agent picks from that list and does not extend it. Anything outside the file is a proposal, not a write.
This one rule kills most of the mess. The agent's job stops being "design a graph" and becomes "fill in this graph", which models are far better at.
2. Deterministic IDs, never generated ones
If the agent invents an ID for every entity it sees, every run creates new nodes.
Derive the ID from a canonical key instead, so the same input always produces the same ID:

 
The second run now upserts the existing node instead of adding a fifth Acme.
Do the normalization in code, not in the prompt. Code does it the same way 100% of the time, a model does not.
The other half is restarts. A run that dies halfway shouldn't write the same batch twice.

3. Extract, validate, then write
Most broken pipelines have one arrow: extract to write. Add a step in the middle.
Extractor proposes nodes and edges as structured output. It never touches the database.
Validator checks that proposal against the schema. Wrong node type, illegal connection, missing property, conflicting edge, all rejected.
Writer commits what passed. Everything else lands in a review queue.
This is the generator-evaluator pattern, and it works because the model doing the checking is not the model that just convinced itself the answer was right.
The catch is separate context. Run both in one thread and the validator inherits the extractor's assumptions, which defeats the point.
keeps agent conversations isolated by default, so the evaluator sees the proposal and nothing else.@teamly
 
4. Every edge carries its source
An edge with no provenance is a claim you can never check.
Every relationship should carry four extra properties: document ID, text span, extraction timestamp, confidence score.
Without them, a bad run is permanent. You either rebuild the whole graph or live with it.
With them, a bad run is a delete query. You can audit any answer back to the sentence that produced it, re-extract only low-confidence edges when a better model ships, and find the one malformed document that poisoned 200 edges.
Provenance only helps if the run itself is traceable too.
Teamly's task board shows which documents processed and which failed as a tree, so a bad batch is one click away instead of a grep through logs.
 
5. Approve schema changes, not every edge
Reviewing 40,000 edges by hand defeats the point. Reviewing zero of them is how you get a silently broken graph.
Put the gate where being wrong costs the most:
new relationship type → stop and ask bulk delete or merge → confirm first low confidence → review queue validated edge → write it, no interruption
A handful of decisions a week instead of thousands of rows.
The hard part is stopping without the pipeline looking frozen.
Teamly ships approval cards for this: the agent pauses, surfaces the decision with options, and resumes once you answer.
6. Diff every run against a golden subgraph
 
Build a small subgraph by hand. 50 nodes, 100 edges, from documents you know cold. That is your test set.
Every run gets scored on precision (are the edges right), recall (did it find everything), and duplicates (how many new copies appeared).
An eval you run manually is an eval you stop running by month two.
@teamly scheduled routines run the diff weekly and report the three numbers whether you remembered to ask or not

The bottom lin
The hard part of graph engineering was never extraction. Models have been good enough at that for a year.
The hard part is that a graph is a permanent record, and an agent writing into it without guardrails compounds every mistake it makes.
→ Lock the schema so structure stops drifting between runs
→ Derive IDs so the second run updates instead of duplicating
→ Validate before write so bad edges never land
→ Keep provenance so any run can be undone
Set these up once and your agent stops being a risk to your data and starts being the thing that keeps it clean.
