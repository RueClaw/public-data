## Article text

Docker popularised containers as a way to package, isolate and run microservices, and Kubernetes became the de facto standard for orchestrating them at scale. 
Why isn't Kubernetes also the best place to run AI agents? What changes when the workload is an agent?
Consider a coding agent: it waits for approval, runs a script, calls a model and pushes a change. Each step asks something different of the infrastructure. Four properties explain why Agent Substrate adds another layer on Kubernetes.
1. High idle time
An agent can wait for human input, an LLM response or a remote tool result. Its local environment has little work to do, but a dedicated Pod still retains memory and reserved capacity.
Across thousands of sessions, that becomes expensive.
 
Agent Substrate separates the session's lifetime from its worker Pod. When the application decides it is safe to suspend, Substrate snapshots the environment and frees the worker. The session can later resume on another worker.
Many agents take turns using a smaller pool. This is temporal multiplexing, much like CPU time-sharing at the level of agent environments.
2. Nondeterministic behaviour
In a microservice, developers supply the code and define the available execution paths. Give an agent a shell tool and it can write a Python script, then run it immediately.
That code can modify files, spawn processes or attack neighbouring workloads. The isolation boundary must hold regardless of the model's decisions.
 
Substrate gives each active agent its own gVisor or microVM sandbox. Agents reuse workers while retaining separate execution boundaries.
3. Dynamic network access
A script can stay inside its sandbox and still send proprietary code to an external endpoint.
Our coding agent needs the repository and an approved model API. It has no reason to upload files to an arbitrary internet destination.
 
Substrate routes outbound traffic through an egress gateway and DNS relay. Policy controls destinations, and the gateway can inject credentials outside the sandbox.
An approved destination can still receive sensitive data. Payload inspection needs additional policy, and the receiving API must authorise the operation.
4. Delegated authority
Two users ask the same agent to push a change. One can write to the repository; the other can only read it. The API needs to distinguish them.
The agent session needs its own identity, independent of its worker, plus the authority of the user it represents.
 
Substrate provides short-lived agent identities. The application authenticates users and integrates their delegated permissions with backend identity systems. Native on-behalf-of flows remain under design.
Where this goes next
Kubernetes manages worker Pods. Agent Substrate manages the sandboxed environments that take turns using them. The application still owns user authentication and delegation.
