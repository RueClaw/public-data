## Article text

TL;DR: I brought Omarchy to my old iPad 6, running Arch Linux ARM with a touch-friendly desktop on just 2 GB of RAM. Touchscreen, Wi-Fi, Bluetooth, internal storage and basic power management are working. I also built an installer that takes the device from DFU to a running desktop in a single boot, with recent installs taking under four minutes when the Linux partition is already in place. GPU acceleration is still missing, and there's plenty left to do. The code and tooling are being made available for others to build on.
A little while ago, I picked up my old 2018 iPad 6 again.
It was running iPadOS 17, and using it had become painfully slow. The hardware wasn't exactly impressive anymore — an A10 Fusion, 2 GB of RAM — but I couldn't help wondering how much of that was actually the hardware, and how much was the operating system.
I'd been following Omarchy closely, waiting for M4 Pro support, and I wanted to try putting it on the iPad.
That sounded like a fun weekend project.
It was not a weekend project.
First, figure out how to boot Linux at all
Unlike a regular computer, you can't just plug in a USB stick, select a boot device and install Linux on an iPad.
Apple's boot chain is locked down. Fortunately, older devices like the iPad 6 are vulnerable to checkm8, a BootROM exploit that allows running unsigned code.
But having an exploit doesn't mean having a working Linux system.
I started digging through existing projects: palera1n, PongoOS, m1n1, Hoolock Linux, Project Sandcastle, and various other attempts at running alternative operating systems on Apple hardware.
Each solved a different part of the puzzle.
Eventually, I managed to put together a boot chain:
**checkm8 → PongoOS → m1n1 → Linux**
I built a custom kernel inside a Linux container on my Mac, assembled the boot image, fought with DFU mode for longer than I'd like to admit, and finally got Linux running on the iPad.
That was the first milestone.
Unfortunately, booting Linux and having a usable tablet are two very different things.
Then came the hardware
The initial Linux environment was extremely minimal. A shell, some debugging interfaces, basic display support.
A lot of the underlying A10 platform support already existed thanks to Hoolock and other developers. That gave me a starting point I would never have had otherwise.
But the iPad 6 itself still needed a lot of work.
Take the touchscreen, for example.
There was an existing implementation for the related iPad 7, which uses the same A10 SoC, but it wasn't simply a matter of enabling a driver.
We had to investigate SmartIO, SPI communication, DMA, GPIOs, interrupts, firmware initialization and the touchscreen's packet format.
At one point, the touchscreen would initialize and return plausible-looking responses, but other packets were corrupted. My coding agent spent hours comparing implementations, testing clock frequencies, transfer lengths, buffer sizes, SPI modes and protocol assumptions.
Eventually, we started getting clean packets.
Then actual touch contacts.
Then drags, swipes, overlapping fingers and proper release events.
And finally, after installing an on-screen keyboard, I could actually type on the iPad under Linux.
Similar work followed for Wi-Fi, Bluetooth, internal storage, battery reporting, charging and power management.
There have been hundreds of kernel experiments along the way, many of them involving a slightly different hypothesis, a newly compiled module and another test on the physical device.
Not everything is solved. GPU acceleration is still missing, charging-source detection remains incomplete, and suspend/resume worked in an earlier minimal environment but isn't reliable in the full system yet.
Still, the hardware has come a long way.
The agents needed their own tools
All of this work was carried out with coding agents.
I used Pi, gave it access to the kernel source and eventually the running iPad over USB networking and SSH, and let it investigate and implement drivers.
But it wasn't as simple as asking an agent to "make the touchscreen work."
In the beginning, every experiment was painfully expensive.
Change the kernel, compile it, assemble another image, reboot the iPad, enter DFU, run the exploit, load PongoOS, load m1n1, boot Linux, reconnect, inspect logs.
Repeat.
And repeat.
So we started building tooling around the process.
Automated builds, boot-image assembly, serial capture, SSH provisioning, diagnostic tools, known-good snapshots, hardware-test harnesses and eventually support for loading and unloading experimental kernel modules without rebooting.
That last part made a massive difference.
Instead of going through the entire boot chain for every experiment, the agent could often compile a module, transfer it to the running iPad, load it, collect results and try again.
Over time, the tools became almost as important as the code they were helping us develop.
Meanwhile, I wanted an actual Omarchy desktop
Running a kernel is nice, but the original goal was to make the iPad useful again — with Omarchy.
Omarchy normally targets a very different class of hardware. My iPad has 2 GB of RAM and no working GPU acceleration under Linux.
Hyprland wasn't a particularly realistic starting point.
So I went with labwc and Quickshell, adapting the Omarchy shell and desktop experience for the tablet.
I developed most of that side in a separate ARM64 virtual machine on my Mac, configured with 2 GB RAM, one virtual CPU and Pixman rendering.
That let another agent work on the Omarchy desktop while the hardware agent continued experimenting with the real iPad.
We added touch-friendly controls, window snapping, an on-screen keyboard, settings and applications.
Eventually Firefox was running on the actual iPad.
It's not as smooth as a GPU-accelerated desktop, but it's usable. On an eight-year-old tablet with 2 GB of RAM, I'll take that, for the time being.
So, what actually works?
At this point, the iPad is running Arch Linux ARM with an Omarchy-inspired desktop, directly on the hardware.
Desktop: labwc, Quickshell, touch-friendly controls and an on-screen keyboard.
- Applications: Firefox and regular ARM64 Linux applications.
- Input: Multitouch, swipes, dragging and physical buttons.
- Connectivity: Wi-Fi and Bluetooth.
- Storage: Persistent Linux installation on the internal NAND, alongside iPadOS.
- Power: Battery reporting and basic, limited charging support.
It's not a daily driver yet. There's no GPU acceleration, suspend/resume still needs work, and booting Linux after a cold restart currently requires a computer.
Then I realized installing Linux was an entirely different problem
At this point, I had Linux running, a growing collection of drivers and an Omarchy desktop.
But everything depended on my development setup.
The kernel was booted from my Mac. The initial root filesystem lived in RAM. Firmware and device-specific configuration had to be prepared manually.
That wasn't something I could reasonably ask other Omarchy users to reproduce.
On a normal PC, a distribution ships an ISO. You boot it, run the installer, and you're done.
On an iPad, that model doesn't really work.
The device doesn't have an unlocked bootloader. You need an exploit, a custom early boot environment, the appropriate device tree, extracted Apple firmware, a compatible kernel and a way to access internal storage.
Even making room for Linux is complicated because the device already has an APFS container occupying the disk, and Linux tooling cannot shrink it.
So bringing Omarchy to these devices requires more than a root filesystem.
It needs to bring its own path into the machine.
One boot, from DFU to Omarchy
This became the next big architectural goal.
I wanted someone to connect an iPad, enter DFU once, and end up in Omarchy.
No repeated reboots between recovery, firmware extraction, partitioning and installation.
No manually copying files between a dozen different tools.
The installer evolved into a multi-stage process.
First, the host identifies the device, resolves its boot method and obtains the necessary images and firmware inputs.
Then it uses checkm8 and PongoOS to enter a minimal recovery environment.
That environment establishes USB networking and SSH, extracts the Apple Device Tree and prepares device-specific firmware.
From there, the installer transitions into a more capable stage that can prepare internal storage, install Omarchy and hand off to the installed system.
All within a single DFU boot.
During installation, the iPad displays the Omarchy logo rather than exposing every intermediate bootloader and recovery environment.
The user doesn't need to know what PongoOS, m1n1 or an ADT is.
There is still a verbose mode for developers, of course.
Recent installation runs completed in under four minutes, with the Linux partition already in place. And there's still plenty of room to make that even faster.
And then the architecture got out of hand
Initially, all of this was being developed specifically for Omarchy on my iPad 6.
But people started asking about other iPads. And iPhones. And whether their devices could run Omarchy too.
Some developers were already attempting their own ports.
And I realized that if I released everything as a collection of J71b-specific scripts, other developers would probably end up repeating much of the same infrastructure work.
The bigger problem was that **there was no standardized way to package and install a Linux distribution on these devices.**
On a regular computer, you can download an ISO, boot it and install the operating system. The distribution doesn't need to know which USB stick you're using or how your motherboard starts the installer.
On Apple devices, things are different. Different generations need different boot methods, kernels, device trees, firmware and recovery environments.
So I started working toward something resembling an ISO for Apple devices: a standardized distribution package that includes everything needed to install and boot the system on supported hardware.
The installer would handle the complicated parts underneath: device detection, boot-method selection, recovery environments, firmware extraction, partitioning, installation and finally booting into the desktop.
Instead of hardcoding the entire process around my iPad 6, the architecture became modular. Different devices could supply their own hardware profiles, kernel patches, bootloader configurations and firmware recipes.
The same installation machinery could then work across different Apple A-series devices, even when their boot requirements differ.
And that meant developers working on another iPad or iPhone wouldn't have to build their own installer from scratch. They could contribute the missing device support and use the existing infrastructure to bring Omarchy to their hardware.
To verify the abstraction, I had another agent build a minimal Alpine Linux image and run it through the same release pipeline.
That was a useful test of whether the standardized format and modular installer actually worked.
Code and tooling
The source code and tooling are available here:
Omarchy A — Distribution build, desktop configuration and release packaging.
The CLI — Device detection, boot, recovery, installation and hardware bring-up utilities.
Hardware support — Kernel patches, device trees, firmware recipes and device-specific configurations.
APFS Resizer  — Tool for shrinking the APFS container to make room for Linux.
So far, the work has been tested on the iPad 6 (J71b). Other devices will require additional hardware support. Contributions are welcome.
There's still a lot of work ahead.
The tablet shell is a barebones proof of concept, and I certainly don't want to pretend I've figured out what the ideal Omarchy tablet experience should look like.
Hardware support on the iPad 6 is still incomplete. GPU acceleration is missing entirely, suspend/resume needs more work, and charging-source detection is still being investigated.
The distribution format is a first draft, and the installer and development tooling still have plenty of rough edges.
It's a starting point that works, and hopefully something others can build on, improve and help shape.
The goal is to make it easier for the community to bring Omarchy to more devices.
One last thing
Huge thanks to DHH and everyone behind Omarchy for bringing back that early Cydia-era excitement of making our devices truly our own.
My timeline is suddenly full of people putting Omarchy on Android phones, smart TVs, refrigerators and probably toasters next.
It feels like everyone is reclaiming their hardware again.
Of course, we're standing on the shoulders of people who've been doing exactly that for years.
None of this would have been possible without the work of the Hoolock Linux developers, the people behind palera1n, PongoOS and m1n1, Project Sandcastle, the iPad 7 Linux work by pauli1go and many others who have been bringing Linux to Apple hardware.
The entire project was built with AI coding agents, from reverse-engineering hardware and writing kernel drivers to building the desktop, installer and release infrastructure.
It's been a long journey from struggling to boot a Linux kernel to running a first glimpse of Omarchy on an eight-year-old iPad with just 2 GB of RAM.
And hopefully, soon, on a lot more iPads and iPhones.
