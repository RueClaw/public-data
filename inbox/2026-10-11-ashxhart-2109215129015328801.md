## Article text

The model heard you, but did it learn?
Tell a local language model that your favourite colour is blue, then ask it again a few messages later: it will often answer correctly. Start a clean session with no saved memory, and it may have no idea. The first answer does not mean the model changed its weights; it may simply have read the earlier message in its context.
LLMs can learn: pretraining, fine-tuning and model editing all change model parameters. They can also adapt their answers from examples in a prompt without a parameter update, commonly called in-context learning. The question behind Living Weights is more specific: can a running local model retain an explicitly taught fact inside its checkpoint and use it after a restart, without requiring the original conversation? [1, 2]
That is what we set out to build in TensorFold. I wanted a practical teaching operation in a local inference engine, with visible progress, checks on what changed and a model folder that carries the result. In version 1.0.7, Living Weights implements a bounded version of that idea for Nemotron 3.5 Lightning on Macs and DGX Spark.
Memory has several meanings
A conversation window supplies tokens to the model. A KV cache keeps intermediate attention computations so the engine can reuse work. A saved prompt cache can survive a restart while still depending on the matching prompt. None of those mechanisms, by itself, changes the model's parameters.
Retrieval-augmented generation stores information outside the model, retrieves relevant material and supplies it when answering. That is useful when information changes frequently or an answer must point back to a source. Fine-tuning and LoRA take a different route by optimizing parameters, with LoRA commonly using low-rank updates that can sometimes be merged into a base model. Living Weights belongs on the parameter-learning side of this distinction. [3, 4]
It is still training: there is a loss, a backward pass and an optimiser. What changes is the amount of trainable capacity, how a lesson is constructed, where that capacity is placed and how the resulting checkpoint is stored. The teaching operation is explicit; this release does not silently train on every chat message.
 
Why simply changing some weights is difficult
Model parameters are shared across many behaviours. An update that helps one question can change an unrelated answer, or make the model attach a taught value to the wrong person or object. Preserving old parameter bytes is not enough to preserve behaviour, because any added computation can still affect downstream states. Catastrophic forgetting and interference are established research problems, and work on feed-forward layers as key-value memories helps explain why selecting where to intervene matters. [8, 9]
Our earlier Living Weights attempts exposed this problem directly. Making a fact come back was easier than making it come back only where it belonged. The rebuilt design allocates new capacity beside the model's existing shared experts and teaches that capacity to stay quiet on examples where the fact should not apply. The checks matter as much as recall.
Living Weights sits within a long research history of model editing. ROME and MEMIT study edits to factual associations, and Transformer-Patcher is especially relevant because it adds trainable neurons to repair mistakes. Living Weights is our implementation and integration of a neuron-expansion approach in a quantised hybrid model and local serving runtime; we have not established superiority over those methods. [5, 6, 7]
A small pocket beside the shared expert
Nemotron 3.5 Lightning combines attention, Mamba recurrence and mixture-of-experts layers. Living Weights reserves a pocket of 64 additional neurons in each MoE layer's shared expert. The learner normally allocates about ten neurons to a fact across eligible layers, rather than changing the original shared-expert weights. Ten is an implementation budget, not a discovered universal size of a fact. [S1]
For a simplified shared expert, let x be its input, U its input projection and V its output projection. Its contribution is y = V ReLU(Ux)^2, where the square is elementwise. Appending input rows A and output columns B gives y_new = V ReLU(Ux)^2 + B ReLU(Ax)^2. Each new neuron has an input vector that determines when it activates and an output vector that determines what it contributes. [S2]
This is ordinary neural-network computation. There is no text lookup table in that equation. During training, the system identifies useful token positions: the reply-decision position for personal facts, or the final token of a named subject for entity facts. At inference, learned activations determine the response; a separate string-matching rule does not switch the fact on.
 
From a sentence to a checked edit
A teaching request first becomes a lesson. The model writes question-and-answer examples, alternative wordings and nearby questions whose answers should remain unchanged. A fact about a sister, for example, needs checks about other family members and other properties of that sister. Examples must not simply give the answer away in the question. For documents, extracted names, numbers and key wording are checked against the submitted text, and facts are taught one at a time. [S3]
The learner reads internal activations and fits input vectors to separate the fact's key positions from protected positions. The implementation uses squared-hinge objectives: encourage a positive activation for the fact and a negative margin elsewhere. Candidate layers are ranked by unwanted firing, coverage of training questions and separation margin. It then fits the new neurons' output vectors through the real model using answer loss, preservation examples and a penalty on output magnitude. [S1, S4]
After a round, the server checks recall, repetition and changes to nearby answers. A failed edit can be revised within a bounded retry loop or removed. Removal clears the current fact's allocated neurons and restores earlier learned input vectors if that attempt refitted them. These are finite acceptance checks, not a guarantee that no possible question will change. [S5]
The code calls some wordings held-out because they do not receive the answer-fitting gradient, but their loss is used for early stopping, and their answers influence acceptance. They therefore serve as validation data, not an untouched final benchmark. A stronger evaluation must reserve another independently written test set until the edit is frozen.
 
What survives a restart
The learned neurons are written into the model's safetensors shards. The writer preserves the original quantised blocks, appends new input rows and output columns, quantises the additions into the checkpoint's 4-bit group-64 format, and updates the shared-expert width in config.json. In this model, the width grows from 3,712 to 3,776. TensorFold also records the pocket width so it can identify the added capacity. [S6]
That makes the saved object a slightly wider model, rather than a model plus a separately loaded adapter. A compatible loader can evaluate the widened shared expert using the same mathematics. The release reports recall after a plain TensorFold restart; that does not by itself establish identical performance or compatibility across every third-party runtime.
The 3D page at /slide shows the system's recorded facts, neuron placements, layers and shards, plus lesson phase and loss. It is an inspection view of the learning process, not a complete map of everything the model knows. Deleting the display graph does not erase learned weights, and the separate --learn prompt-cache option is not the Living Weights learner. [S7]
Why the learner became faster
The faster learner packs several training examples into a pass, reuses the part of each example before the editable computation, arranges activation reads contiguously and tiles the routed-expert and scan backward passes. The CUDA trainer also loads its weights directly. These changes reduce repeated work around the small parameter update. [1, S4]
For the release's 'I like blue' example, reported time spent in learning rounds fell from 217 to 52 seconds on an M3 Ultra and from 200 to 47 seconds on a GB10. Those are approximately 4.17x and 4.26x improvements in the timed rounds, not fourfold faster text generation and not fourfold faster every end-to-end lesson.
Lesson generation and checking still cost time. The release gives roughly 1.5 to 2.5 minutes for a whole fact on M5 Ultra or M3 Ultra, and 2 to 3 minutes on GB10. Its numerical check reports bit-identical packed and separate training passes on CUDA; Metal's larger packed passes use the prompt kernels, so the same bitwise claim should not be applied to Metal.
 
What the released tests show, and what is changing now
The v1.0.7 release reports three personal facts taught sequentially, with both test wordings recalled for each fact on M5 Ultra, M3 Ultra and GB10, live and after a plain restart, and no observed leakage or drift in the checked controls. On GB10 with thinking enabled, four of those six wordings were recalled. These are useful integration checks with small samples, not a general reliability percentage. [1]
Document learning is harder. The published baseline gives three to six answers out of six across six runs of a short handbook; a longer 21-fact handbook produced six answers out of sixteen questions. On a five-fact handbook part, one question on a Mac and two on GB10 received another fact's answer. The release also reports about 16% slower Mac decoding with 21 learned facts.
We are actively improving the document path, and improvements are already showing in current development. Those changes are newer than the pinned 1.0.7 baseline described here; the next results should identify the exact commit, document, questions and repeated runs so readers can see what improved.
The next evaluation needs independent paraphrases, several facts about the same subject, contradictions and corrections, preservation of previously accepted facts, thinking on and off, save/reload checks, and latency as the pockets fill. The teacher and parts of the judge use the same model, so human-written tests and external checking are particularly important.
Why we built it
I want local models that can become more useful through deliberate teaching, with the learned result staying under the user's control. A checkpoint that carries a small set of learned facts gives us another way to personalise a local model, alongside the context and retrieval tools we already use.
There are still engineering tradeoffs: the added capacity is finite, a learned checkpoint can expose the facts it contains, and a malformed or misleading lesson can teach the wrong thing. Use a copy of the original checkpoint and treat teaching as a controlled operation. The current work demonstrates a mechanism and a set of early results; broad continual learning remains a larger problem.
That is the point of publishing the implementation and the failures together. We can show how the system works, make the checks reproducible and improve it with the people using it.
