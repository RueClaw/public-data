How Container Networking Actually Works 🧙‍♂️

It's surprisingly simple once you understand the high-level idea and have some Linux networking experience.

1. To give each container its own network stack, you will need to create a network namespace per container - and it's just one short command. Practice: https://labs.iximiuz.com/challenges/linux-network-namespace

2. By default, a network namespace gets only a loopback device, so it's not very useful. To connect the new network namespace to the host, you will need a pair of connected virtual Ethernet devices (veth) - one on the host and another one in the namespace. In particular, it'll give your container an IP address. Practice: https://labs.iximiuz.com/challenges/connect-two-network-namespaces

3. Turns out, connecting multiple network namespaces to the host creates a routing collision if their host ends are assigned IP addresses in the same subnet. To work around it, you will need a special multi-port device, called a bridge. Practice: https://labs.iximiuz.com/challenges/connect-multiple-network-namespaces

4. Our network namespaces (containers) can now talk to each other right through the bridge (on L2). But to talk to the outside world, the bridge itself needs an IP address and network address translation (NAT) for traffic leaving the container subnet. Practice: https://labs.iximiuz.com/challenges/set-up-nat-for-container

And that's it!

Now you can reproduce a docker/containerd/kubelet bridge network using only basic Linux commands.
