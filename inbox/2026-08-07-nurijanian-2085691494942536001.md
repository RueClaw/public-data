## Article text

Requests often describe symptoms. Something slows down. Users leave before a feature is useful. A stakeholder asks for a feature instead of explaining what the system needs to do. You fix the symptom, but a new symptom appears elsewhere in the system.
A common solution is testing. You release version A and version B. You check the results and keep the better version. 
Bob Moesta says Genichi Taguchi believes A/B testing is job security for engineers. Testing one variable at a time shows which version won. It does not show which version works when the network is poor and the data is messy.
Moesta uses painting cars as an example. Robots caused two defects. Runs happened when paint was too thick and dripped. Orange peel happened when paint was too thin and dried bumpy. Two teams worked on the two problems. Both problems were caused by the same variable: paint thickness. The defects disappeared when the paint thickness stayed the same, even when humidity and temperature changed.
The system must maintain a number; design a prototype to handle unpredictable conditions.
Plan before committing the team.
Restate the ask as a thing the system has to do, with a number in it. 
"Onboarding is broken" is a symptom. "New users reach first value in under 10 minutes" is a function. If the sentence is still unclear, keep refining it.
Write the chain backward. Start with the outcome. Then list the requirements. These requirements should not name any specific technology. Next, list the inputs. Finally, list the build steps.
Teams that choose the input first spend review time selling a technology stack. They do not sell the outcome.
List each variable that moves the number. Mark each one as control or noise.
Control is the factors you set. This includes retry counts, model settings, defaults, and flags.
Noise is the factors the world brings. This includes the network, hardware, and dirty data.
Look for variables you have been filing under control. The world might be setting these for you.

Design the prototype to move several control factors at once. Run each variant at the extremes of your noise factors.
Taguchi's orthogonal arrays are a compact way to do this. An L9 layout uses nine runs to test four factors at three levels. A full grid would need 81 runs. The L9 layout predicts the results of other combinations.
Score the results using signal-to-noise. You want to find the point where the function breaks.
Then sort each scope item into big hire, little hire, and the rest. Big hire makes first use worth it. Little hire brings someone back the next day. Protect the first two and defer the rest with a one-line reason.
Jason Fried says that doing a great job on a small part is better than doing a poor job on the whole thing. Basecamp's first mobile app focused on comments and lists. This was useful for people waiting in a shop. It did not try to copy the desktop version. Usage of the app increased.
Set a date, cost, or both, and its forced tradeoff.
Why is this difficult?
I do not think the blocker is knowledge. You could name your noise factors off the top of your head. You know which scope items no one will open twice.
Teams get credit for fixing problems and releasing new features. This can lead to teams focusing on symptoms rather than root causes. Every step taken might then improve the wrong thing.
Changing how work is named has a cost. For example, saying "big hire" or "little hire" might seem like blocking to someone who asked for an export button. Refusing an A/B test for a build choice might seem like avoiding data. A nine-point plan can feel harder than releasing a split test in one sprint.
If your team has spent a year proving one variable per sprint, the pushback is fair. One design pass takes time. You pay for it once, and it shows you where the system fails under noise. The A/B cadence bills a sprint per learning and only tells you which symptom moved last.
One build ask, then ten
Take the messiest ask on your desk this week. Run the seven steps by hand before someone sizes it. You can finish one pass, and you likely hold most of the answers. The piece you are missing is the order and the time.
Now picture ten of those in a week. I think that becomes normal once agents draft specs, mockups, and test plans every day. Asks arrive faster than you can reframe them. A blank template does not rescue you either, because it hands you the same seven steps in a nicer table.
When you install the skill for the team, an agent runs the sequence the same way each time. It checks the function statement for symptom words. It fills the control and noise table. It lays out the matrix. It applies the hire test to your scope. It writes the wall with its tradeoff named. You keep the two calls it cannot make: which function is worth holding, and which cuts your team can afford.
One PM can carry that sequence in their head for one build. A team of PMs cannot each keep a private version of it and still review each other's build plans against the same bar.
